# Трекер планов

## Прогноз времени агентов

ATLM использует исходное описание задачи и опыт завершённых пригодных планов.
Признаки фиксируются до первого запуска; каждые пять новых пригодных планов
запускают проверяемое переобучение на накопленной истории. Сохранённый прогноз
виден в плане, состояние опыта и обучения — в настройках. Первой модели может
потребоваться больше пяти примеров; недостаток данных не превращается в нулевое
время, а неудачный кандидат не заменяет прежнюю пригодную модель.

[Контракт ATLM и ограничения качества](docs/atlm.md) ·
[Оценки и совместимость](docs/assessments.md) ·
[Проверка и доставка выпуска](docs/atlm-release-readiness.md).
GitHub, Site/MCP и установленный пакет навыков имеют отдельные проверки доставки;
наличие исходников само по себе не подтверждает публикацию или точность на реальных
агентах.


Приватный трекер планирования, оценки и выполнения задач: серверный учёт времени, этапы, попытки и проверки результатов. Несколько планов могут работать одновременно. Общее время считается без двойного учёта пересекающихся интервалов; время каждого плана и их сумма доступны отдельно.

## Обновление

Повторное `marketplace add` не обновляет уже добавленный Git-снимок. Чтобы получить новый выпуск, выполните команды по порядку; при ошибке остановитесь:

```sh
codex plugin marketplace list --json
codex plugin marketplace upgrade plan-time-tracker
codex plugin add dev-9529b49da3708191b8f13f1e1e4b1e01@plan-time-tracker
codex plugin list --marketplace plan-time-tracker --json
```

`upgrade` обновляет Git-снимок marketplace и при его изменении — кэш настроенных плагинов. Повторный `plugin add` переустанавливает пакет из этого источника. В результате последней команды проверьте запись в `installed`: после публикации ожидается версия `0.5.0`. Пакет указывает на актуальный адрес трекера `https://plan-time-tracker.s-e-r-a-f.chatgpt.site`; подготовленная версия API — `0.5.0`. ID проекта и App-привязка сохранились. Завершите предложенное подключение нового App, затем начните новую сессию Codex и повторите проверку MCP-инструментов. Уже установленный пакет со старой App-привязкой необходимо обновить; публикация GitHub сама его не переключает. Отдельной команды `plugin update` нет; вручную удалять кэш не нужно.

Если по-прежнему устанавливается `2.0.0`, проверьте `source` и `ref` в выводе `marketplace list --json`. Это прежний выпуск; текущий манифест содержит `0.5.0`, а marketplace репозитория не закрепляет `2.0.0`. Причиной может быть старый снимок или другой источник. `upgrade` сохраняет настроенный `ref`, а не переключает ветку или тег на `main`. Если источник локальный, сначала обновите его каталог, сохранив свои изменения, затем повторите `plugin add`: `marketplace upgrade` работает с Git-источниками.

## Как работает учёт

[track-plan](plugin/plan-time-tracker/skills/track-plan/SKILL.md) регистрирует план, шаги и оценки при `/plan` и обычном планировании и ведёт учёт исполнения и продолжения без отдельной просьбы использовать трекер. Планирование оставляет реализацию PLANNED и не запускает таймер. Просьба выполнить план разрешает его регистрацию и запуск, просьба продолжить — возобновление. Пауза и завершение требуют соответствующего намерения пользователя; конец ответа и истечение аренды попытки не останавливают время.

MCP и веб-интерфейс используют одни команды. Каждому исполнителю нужен свой контекст плана, этапа, попытки, сессии и очереди. Без аутентифицированного трекера выполнение с обязательным учётом блокируется. MCP не перехватывает работу клиентов, которые его не вызывают. Репозиторий, синхронизация, интеграция с commit/push и внешний токен для учёта не требуются.

`ListPlans({statuses, limit, cursor})` возвращает `{plans, nextCursor, serverNow}`. Размер страницы — 50 по умолчанию, максимум 100; порядок — по убыванию `registeredAt`, затем `planId`. Активных планов может быть несколько. Продолжайте известные PAUSED/PLANNED по явному ID без дубликатов.

`totalActiveMs` и `activeByDay` считают объединение интервалов владельца, `sumPlanActiveMs` — сумму длительностей планов. Например, два часовых плана 10:00–11:00 и 10:30–11:30 дают сумму 120 минут и общее время 90 минут. Проверки привязаны к текущей ревизии результата и снимку исходников; подробные правила завершения — в инструкции агента.

### Локальные скрипты

Тесты запускаются из каталога `plugin/plan-time-tracker`:

```sh
node --test test/*.test.mjs
```

Синтаксис снимка из того же каталога: `node scripts/source-snapshot.mjs <source-directory> [--expect sha256:64hex]`. Замените `<source-directory>` путём к исходникам; необязательный `--expect` принимает digest ранее созданного снимка. Скрипт создаёт детерминированный снимок v2 без внешних программ. Храните доказательства вне каталога исходников, передавайте `sourceSnapshot` без локального `fileCount`. Для проверок используйте `testedSnapshotDigest` и точную ревизию результата. Состав снимка и исключения описаны в [контракте](docs/worktree-evidence.md).

`plugin/plan-time-tracker/scripts/observation-queue.mjs` принимает JSON через stdin и операцию `enqueue`, `next`, `begin`, `acknowledge`, `fail`, `requeue-pending`, `clear-expired` или `list`. Укажите полученный после аутентификации `ownerScope` и `planContext` — ID назначенного плана. Скрипт хранит очередь только локально; не выполняет вход, сетевые вызовы или изменения жизненного цикла. Через семь дней payload удаляется, а в списке остаётся видимый маркер `EXPIRED` до явного `clear-expired`. Старые очереди, привязанные к репозиторию, автоматически не воспроизводятся. Тесты используют синтетические данные и временные каталоги; учётные данные и обход аутентификации в пакет не включены.

## Удаление и восстановление

Кнопка «Удалить» в карточке или деталях плана просит подтверждение и переносит план в «Удалённые». История, этапы и результаты сохраняются. Активный интервал закрывается сервером, открытые попытки завершаются как ABANDONED. Удалённые планы не попадают в обычный список и аналитику; их детали доступны только для чтения.

В разделе «Удалённые» можно восстановить план. Выполнявшийся план вернётся на паузу, остальные сохранят свой статус. Восстановление не запускает таймер и не возвращает старые попытки: для работы нужны явное продолжение и новая попытка. Завершённые результаты и проверки сохраняются. Удалённый период не добавляет активного времени; после восстановления календарная длительность по-прежнему включает прошедшие паузы.

В MCP доступны `DeletePlan` и `RestorePlan`: `schemaVersion: 1`, новый UUID `commandId`, текущая `expectedVersion` и `payload: {planId, reason?}`. Они требуют отдельной просьбы пользователя. `GetPlan` показывает `deletedAt` (null у обычного плана), `ListPlans` по умолчанию исключает удалённые; `deleted: true` выбирает только их. При неизвестном ответе повторяйте тот же конверт, а при конфликте версии перечитайте состояние. Экспорт сохраняет и удалённые планы.

Для выпуска 3.1.0 нужны миграция `0016_plan_deletion.sql`, совместимый Worker и обновление MCP discovery. На существующей параллельной v3-базе применяют только новую миграцию, без сброса данных. Подробный [контракт API](sites/plan-time-tracker/README.md#удаление-и-восстановление-планов-310) описывает ошибки и порядок обновления.

## Сборка и проверки

Нужны Node.js 24, npm, Bash и `tar`. Node.js 24 — проверенная версия; минимальная в `package.json` не задана. Зависимостей и lockfile у приложения нет, поэтому `npm install` и `npm ci` не нужны.

Для нового клона:

```sh
git clone https://github.com/Seraf-seraf/plan-time-tracker.git
cd plan-time-tracker
```

Из корня выбранного checkout:

```sh
git remote -v
git status --short --branch
git rev-parse HEAD
cd sites/plan-time-tracker
npm run build
npm run validate
npm test
node --test ../../plugin/plan-time-tracker/test/*.test.mjs
```

Build пересоздаёт `dist/`: встраивает локальные шрифты из `worker/fonts.js` через `scripts/font-data.mjs` в Worker `dist/server/index.js`, копирует конфигурацию — в `dist/.openai/hosting.json`, SQL и имеющиеся migration metadata — в `dist/.openai/drizzle/`. Это [формат официального Sites packager](https://github.com/openai/sites/blob/7eb9d4b9cf93ad7e64aebc8a5ca70e29ec2cfb94/packages/sites-vite-plugin/README.md). Worker содержит UI и MCP endpoint `/mcp`. `validate` проверяет ESM и экспорт `default.fetch`. Тесты приложения используют SQLite в памяти; тесты плагина проверяют единственный manifest, App-привязку и упаковку через `tar`.

Браузерные проверки требуют Playwright и Chromium; команда и переменные `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE`, `UI_ACCEPTANCE_ARTIFACT_DIR` описаны в [README приложения](sites/plan-time-tracker/README.md#local-verification). Локальные тесты не проверяют вход и рабочую D1 в Sites.

### Миграции

Для новой канонической установки 0.5.0 нужна пустая D1 с привязкой `DB` и полная цепочка [drizzle](sites/plan-time-tracker/drizzle) от `0001_initial.sql` до `0019_atlm.sql`. У существующей канонической базы после подтверждённой 0018 добавляется только `0019_atlm.sql`. Старая база с ограничением на один RUNNING-план этим выпуском не обновляется.

Рабочий Site имеет собственную историю **0000–0004**: в его отдельном исходном checkout сохраняются 0000–0003 и добавляется эквивалентная `0004_atlm.sql`. Нельзя подменять эту историю цепочкой GitHub или снова применять начальные SQL к рабочей базе. Соответствие нового изменения — GitHub `0019_atlm.sql` ↔ Sites `0004_atlm.sql`; номера их старых миграций не взаимозаменяемы.

Sites применяет hosted-миграции перед загрузкой Worker. SQL и существующая Drizzle metadata входят в deployment archive под `.openai/drizzle/`; build только упаковывает их и не изменяет БД. Сохраните прежние SQL, их порядок и ledger. Перед обновлением проверьте фактическую историю выбранного Site и состав добавленной миграции: наличие таблиц через `read_database_overview` само по себе не подтверждает ledger или триггеры. Не создавайте фиктивный journal, не обнуляйте данные и не используйте отдельный shell-запуск hosted SQL.

### Публикация

Дальше используются инструменты подключённого Sites, а не shell-команды:

1. Прочитайте манифест хостинга и проверьте проект через `get_site`. Для обновления используйте его `project_id` и сохраните приватный доступ. Для независимой установки подготовьте отдельную копию без привязки к чужому проекту, создайте свой Site через `create_site`, сохраните возвращённый ID и настройте собственную App-привязку.
2. Проверьте привязку `DB`, схему и соответствующую этому Site историю миграций. Для текущего Site применяется его цепочка 0000–0004, описанная выше.
3. Подготовьте отдельный checkout репозитория исходников, подключённого к выбранному Site. Он отличается от GitHub `origin`; сохраните его `.openai/hosting.json` и собственный ledger. Перенесите исходный `worker/index.js` и требуемые файлы шрифтов/сборки, затем выполняйте штатный build в этом checkout. Не подставляйте уже собранный GitHub Worker в исходник, который повторно встраивает шрифты. При необходимости `create_source_repository_write_credential` вернёт `remote_url`, `branch` и краткоживущий token. Не сохраняйте token в remote URL, документах, логах или архиве; для явной публикации не запрашивайте `publish_on_push`.
4. В рамках выпуска зафиксируйте и отправьте точное состояние в ветку исходников Site. Соберите и проверьте этот checkout командами выше. `commit_sha` должен быть полным SHA текущей HEAD этой удалённой ветки.
5. Из каталога приложения в выбранном Sites checkout упакуйте весь `dist/` с сохранением префикса. Добавьте корневую копию только hosting-манифеста для загрузчика:

   ```sh
   tracker_archive_dir=$(mktemp -d)
   mkdir -p "$tracker_archive_dir/package/.openai"
   cp -R dist "$tracker_archive_dir/package/dist"
   cp dist/.openai/hosting.json "$tracker_archive_dir/package/.openai/hosting.json"
   tar -czf "$tracker_archive_dir/plan-time-tracker.tar.gz" -C "$tracker_archive_dir/package" .
   tar -tzf "$tracker_archive_dir/plan-time-tracker.tar.gz"
   ```

   В архиве должны быть `dist/server/index.js`, `.openai/hosting.json`, `dist/.openai/hosting.json` и `dist/.openai/drizzle/` с неизменёнными SQL и metadata. Миграции не переносите в корневую `.openai/drizzle`: Worker может опубликоваться без применения этих sidecars. Остальные исходники, `.git` и учётные данные в архив не входят. После публикации проверьте ожидаемые новые таблицы через Sites: один статус deployment succeeded не подтверждает миграцию. Сохраните абсолютный путь к архиву до окончания загрузки.
6. Для Site, чья приватность владельцу выбранного аккаунта уже установлена через `get_site`, предпочтителен единый `save_version_and_deploy_private` с `project_id`, полным `commit_sha` и абсолютным путём `archive`. Отдельное разговорное подтверждение развёртывания не требуется; действуют runtime approval и проверка доступа самого сервиса. Не меняйте аудиторию. Сохраните возвращённые `version_id` и deployment `id` отдельно. Если версия уже сохранена, используйте `deploy_private_site_version` с её `version_id`, не сохраняйте и не загружайте тот же выпуск повторно.
7. Если ответ не терминальный, проверяйте `get_deployment_status` по deployment ID до `succeeded` или `failed`: URL публикации ведёт на рабочий сайт. При ошибке с `saved_version_id` сохраните этот ID для повтора развёртывания; при несовпадении доступа перечитайте `get_site`, не переключайте аудиторию молча. Если исправляется сама упаковка, зафиксируйте её изменение новым source commit: тот же SHA переиспользует уже сохранённую версию и её архив.
8. После успеха проверьте вход владельца в UI, `GetTrackerInfo` с `assessments.atlm`, GetTrainingStatus и все страницы `ListPlans`. Для UI используйте реальный опубликованный Worker без добавления фиктивных планов владельца. Обновите плагин и обнаружение инструментов в клиентах отдельно.

Обновление GitHub не развёртывает Worker и не обновляет установленный плагин. Готовой команды `npm run deploy` в репозитории нет. Подробнее: [публикация и доступ в Sites](https://learn.chatgpt.com/docs/sites/publishing-and-sharing).
