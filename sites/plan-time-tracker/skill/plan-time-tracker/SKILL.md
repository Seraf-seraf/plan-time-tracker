# Планы, статусы этапов и время работы

Сохраняйте исходный текст плана, его этапы и оценки в подключённом «Трекере планов». Время работы считает сервер. Для работы нужны доступные MCP-инструменты и аутентифицированный владелец. Берите текущие имена инструментов из discovery. Доступные функции проверяйте через GetTrackerInfo.

## Сохранить план

1. Составьте полный план в Markdown, включая контекст, действия, критерии приёмки и необходимые проверки. Передавайте весь исходный текст в CreatePlan.payload.planText без пересказа в отдельных технических полях.
2. Оформляйте этапы заголовками одного уровня: `## Этап 1. Название`, `## Этап DATA-001. Название` или `## G1. Название`. Заголовки этапов внутри блоков кода не создают этапов. Прикладных лимитов длины плана и числа этапов нет; идентификаторы заголовков должны быть уникальными.
3. Вызовите CreatePlan с `schemaVersion:1`, UUID `commandId`, `payload:{title,planText,planCreatedAt}`. `planCreatedAt` задаёт исходную дату составления с точностью dateOnly или instant и часовым поясом. Источник беседы или задачи можно передать в `sourceReference` на уровне команды.
4. Сохраните возвращённый planId, прочитайте GetPlanProgress и сохраните stepId, текущий статус и version каждого этапа. После создания план остаётся PLANNED, таймер не запускается.

Храните один контекст на planId. Не создавайте дубликат плана после потерянного ответа или передачи задачи другому исполнителю. Перед продолжением найдите и прочитайте существующий план. ListPlans использует стабильную пагинацию nextCursor; при поиске прочитайте все нужные страницы.

В PLANNED до первого запуска используйте UpdatePlan с текущим `expectedVersion`. Для замены исходного Markdown передайте `payload:{planId,planText}`. Для правки отдельных этапов передайте `payload:{planId,stepEdits:[{stepId,markdown}]}`, где `markdown` включает заголовок с прежним идентификатором. Для изменения состава или порядка этапов используйте полный текст. Метаданные меняйте отдельным UpdatePlan. Сервер обновляет исходник и этапы атомарно или сразу отклоняет недоступную правку без сохранения предложения. После обновления перечитайте GetPlanProgress и исходные требования оценки.

## Оценить задачу до первого запуска плана

Получите схему `agent-task-v4` из `GetTrackerInfo.assessments.atlm.agentTaskSchema`. Если доступен навык assess-task, используйте его справочник и пример запроса. Перед анализом вызовите `GetTaskAssessment` с одним `planId` и сохраните `currentRequirementsDigest`. В `SaveTaskAssessment` передайте его как `expectedRequirementsDigest`, заполните `context.agentTask` и добавьте `predictionRequest:{method:"ATLM",methodVersion:1}`. Сервер сохраняет прогноз в `serverEstimation`.

Перед первым `StartPlan` вызовите `GetSavedEstimate`. Статус `assessmentReadiness.status=READY` разрешает запуск независимо от доступности прогнозного числа. В остальных случаях исправьте оценку по коду и путям в `assessmentReadiness`. `GetSavedEstimate` до начала работы рассчитывает текущий прогноз по сохранённым признакам. Первый запуск фиксирует результат на весь план.

## Выполнить работу и обновить статус этапа

Выполняйте работу в пределах поручения пользователя. Просьба выполнить или продолжить задачу разрешает соответствующий StartPlan или ResumePlan. Просьба только составить план оставляет его PLANNED. Не запрашивайте то же разрешение повторно.

Для изменения этапа вызовите SetStepStatus:

```json
{
  "schemaVersion": 1,
  "commandId": "<новый UUID>",
  "expectedVersion": 1,
  "payload": {"stepId": "<UUID этапа>", "status": "RUNNING"}
}
```

Используйте текущую version этапа из GetPlanProgress. Изменение разрешено для RUNNING-плана, который не удалён. Версия этапа и версия плана независимы.

- PENDING — работа по этапу ещё не началась.
- RUNNING — этап выполняется.
- BLOCKED — продолжение этапа зависит от устранения препятствия. Сообщите пользователю, что произошло и что позволит продолжить.
- DONE — фактический результат и необходимые проверки соответствуют критериям плана.

Проверки выполняйте в рабочей среде и сообщайте результат пользователю. Трекер хранит текущее состояние этапа; отдельные записи результатов, проверок, событий смены статуса и назначений исполнителю не создаются. После успешного SetStepStatus сохраните возвращённую version. Не записывайте DONE заранее и не называйте неподтверждённую запись успешной.

Статус этапа не запускает и не останавливает таймер плана. Подтверждённый SetStepStatus со статусом RUNNING открывает интервал этапа, другой статус закрывает его. Повтор RUNNING сохраняет открытый интервал. Если его ещё нет, измерение начинается с текущего момента. Учитывается пересечение с активными интервалами плана. Параллельные этапы измеряются независимо. StartPlan, PausePlan, ResumePlan и FinishPlan работают с серверными интервалами конкретного planId. Несколько планов могут быть RUNNING одновременно; действие по одному не должно менять другой. Общее время владельца — объединение пересекающихся интервалов, сумма времени планов — отдельная величина.

Вызовите PausePlan по намерению пользователя или при остановке всего плана по правилу ниже. Вызывайте FinishPlan по намерению пользователя. Для обычного завершения все этапы должны быть DONE. Завершение с незавершёнными этапами требует явного решения и причины в `allowIncomplete:true, reason`.

### Пауза после BLOCKED

1. Сообщите пользователю причину блокировки и вызовите `SetStepStatus` со статусом `BLOCKED` и текущей версией этапа. В `payload` передайте `stepId` и `status`.
2. Подтвердите свою запись. При потере ответа вызовите `GetCommandResult` с тем же `commandId` или повторите исходный запрос без изменений. В успешном ответе команды или `result` квитанции со статусом `FINAL` проверьте `planId`, `stepId` и `status:'BLOCKED'`. Сохраните подтверждённую версию этапа.
3. После подтверждения вызовите `GetPlanProgress` для того же плана. Если план уже `PAUSED`, сообщите текущий статус. Если по плану есть работа, которую можно продолжить, оставьте `RUNNING`. Если ваша блокировка остановила весь план, этап всё ещё в `BLOCKED` на подтверждённой версии и план в `RUNNING`, вызовите `PausePlan` с текущей версией плана, новым UUID и `payload:{planId,reason}`. В `reason` передайте причину блокировки. В этом случае агент вправе поставить план на паузу самостоятельно.
4. Проверьте статус плана `PAUSED`. При потере ответа `PausePlan` прочитайте квитанцию или точно повторите запрос. При `VERSION_CONFLICT` заново проверьте условия шага 3, прежде чем отправлять новый запрос с новым UUID. При отказе сообщите фактические статусы и причину.

После устранения блокировки возобновляйте план отдельной командой по намерению пользователя. Каждый следующий вызов относится к исходному `planId`.

## Повторить команду после потери ответа

Для каждой команды записи используйте свой UUID в `commandId` и передавайте `expectedVersion`, если этого требует команда. Если ответ потерялся, вызовите `GetCommandResult` с исходным `commandId`. При `status:'FINAL'` поле `result` содержит результат успешной команды, а `error` — сведения об отказе. При `PENDING` или `NOT_FOUND` исход ещё не подтверждён. Точный повтор с тем же `commandId` позволяет получить сохранённый результат без повторного применения команды.

При `VERSION_CONFLICT` снова вызовите `GetPlanProgress` или `GetPlan`, проверьте актуальную версию и убедитесь, что изменение всё ещё нужно. Если трекер отклонил команду и вы исправили запрос, задайте новый `commandId`. Пока результат команды неизвестен, сохраняйте исходный запрос без изменений. При `ASSESSMENT_CONTEXT_CHANGED` заново изучите требования и пересмотрите оценку, сохранив исходную ревизию.

При передаче работы сообщите planId, stepId, текущие версии и статусы, ссылку на исходный документ, assessmentId/revision и ожидаемый результат. При продолжении прочитайте сохранённое текущее состояние и выполните разрешённую задачу. Повторные назначения, продление прав исполнения и фоновые события активности не требуются.

## Удалить или восстановить план

DeletePlan и RestorePlan вызываются по просьбе пользователя для конкретного planId с текущей версией плана. Удаление закрывает его открытый интервал, переводит RUNNING-план в PAUSED и выполнявшиеся этапы в BLOCKED. Исходный текст, текущие состояния и измеренное время сохраняются. Остальные планы продолжают работу независимо.

RestorePlan восстанавливает план без запуска времени. ListPlans по умолчанию скрывает удалённые планы, `deleted:true` показывает только их. Удалённый план доступен для чтения по ID и не принимает изменения до восстановления. Не создавайте его копию и не восстанавливайте его автоматически. Аналитика исключает удалённые планы; восстановление возвращает сохранённые интервалы в отчёты.

## Аналитика

GetTimeReport возвращает факты времени плана за календарный период в заданном часовом поясе: totalActiveMs, activeByDay, sumPlanActiveMs и показатели завершённых планов. GetTimeHistory читает оценки выбранных targets и факты PLAN_ACTIVE, CALENDAR и PAUSED. Для следующей страницы оценок сохраняйте `asOf` и `throughSequence`, а `nextAfterSequence` передавайте как `afterSequence`. Текущая готовность этапов не является историческим состоянием на asOf.

Для прогнозов используйте ATLM и исходные признаки assess-task. Текущие статусы не являются исходными признаками. Трекер хранит записанное активное время и применяемую модель. Для обучения учитель проверяет фактические признаки, замер и пригодность каждой строки по инструкции train-model. Не выводите время этапов из последовательности статусов.

Не сохраняйте секреты, полные логи инструментов или исходники проекта в полях трекера.
