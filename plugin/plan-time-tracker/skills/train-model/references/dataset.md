# Подготовка датасета

## Получить исходные строки

Для новой подготовки вызовите `CreateTrainingSnapshot` с `{schemaVersion:1,mode:'create',commandId}` и новым UUID. При `SOURCES_PENDING` повторите тот же запрос, выждав `details.retryAfterMs`, если интервал указан. Продолжайте со старым `snapshotId` в рамках того же запуска или по явному поручению пользователя. Выгрузите полный снимок. [Передача файлов](transfer.md).

Если пользователь указал датасет, откройте его по ID через `GetDatasetRevision`. Для нового обучения проверьте совместимость формата с рецептом и причины прежних пропусков. Для v4 нужен `atlm-teacher-dataset-v2`. Если в старой ревизии завершённый неудалённый план исключили из-за `ACTUAL_FEATURES_UNVERIFIED` или `ACTUAL_TIME_UNVERIFIED`, вернитесь к первичным данным. Подготовьте исправленную строку в новой ревизии, если пользователь не разрешил пропуск. Для явно порученного точного воспроизведения возьмите архивные входы, версию тренера из `provenance.codeRef` и среду из `run.json`. Сообщите сохранённый состав и причины пропусков.

Составьте список всех `rowId`, `planId`, названий и статусов. Отметьте удалённые и незавершённые планы как `EXCLUDED` с подходящей причиной `PLAN_DELETED` или `PLAN_NOT_COMPLETED`. Проверьте пользовательские решения о пропуске. Для остальных строк подготовьте признаки и время.

## Проверить признаки

Откройте код или другой фактический результат, журнал работы и проверки этого плана. Перепроверьте **каждый признак**, включая вложенные поля. Плановая оценка и старая разметка помогают искать подтверждения. Сверьте найденные значения с тем, что сделано.

В `GetTrackerInfo.assessments.atlm.registry.teacherDataset` поле `featureSchemaPath` указывает на схему. Она задаёт обязательные поля, вложенность, типы и допустимые значения. `featureSource` указывает, куда записать признаки. `featurePolicies` содержит правила заполнения по путям полей. Для связей между полями и проверки оснований используйте справочник признаков. [Границы и операции](../../assess-task/references/features.md#границы-и-операции) · [Основания](../../assess-task/references/features.md#основания).

1. Возьмите подтверждённое значение из материалов этого плана. Если пользователь задал правило для датасета, примените его к указанным полям и планам в пределах схемы. В `annotation.fieldEvidence` запишите основание, в `codeEvidence` укажите, где его проверить.
2. Если значение неизвестно, найдите правило поля в `featurePolicies`. Для разрешённой подстановки возьмите `whenUnconfirmed.value`. Запишите проверенный источник и основание подстановки по пути `whenUnconfirmed.evidencePath` и в `annotation.fieldEvidence`.
3. Когда для поля нет подстановки, используйте разрешённое схемой неизвестное значение, если оно предусмотрено. В `annotation.agentTask.unknownReasons` укажите причину и проверенный источник. Минимум, максимум и примеры описывают допустимые значения. Подстановку задаёт правило поля.
4. Если обязательное поле по-прежнему пусто, оставьте строку в черновике и подготовьте вопрос пользователю.

## Проверить активное время

Сверьте `PLAN_ACTIVE` с интервалами, журналом работы или сообщением пользователя о времени именно этого плана. Если замер `source.actualMs` подтверждён, используйте его. Если замера нет или подтверждено другое время, запишите целое число миллисекунд в `annotation.actualTime.actualMs`, а подтверждение — в `annotation.actualTime.evidence`. Исходное наблюдение остаётся в снимке. Ноль подходит, когда источник подтверждает нулевое активное время.

Например, трекер записал 20 минут и `SCOPE_CHANGED`. Код подтверждает объём работы, а журнал — 42 минуты. Исправьте признаки, укажите `actualMs:2520000` и источник в аннотации и включите план. Если пользователь подтвердил 22 минуты активной работы, укажите `1320000` и ссылку на его сообщение.

При расчёте по интервалам объедините пересекающиеся рабочие интервалы одного `planId` и исключите паузы. Другие планы и число агентов на этот расчёт не влияют. `evidence` принимает непустой текст, объект или массив со строковыми основаниями. Для ссылок на записи трекера передайте `{kind,id}` из доказательств этой строки. Восстановление наблюдений через `mode:'repair'` выполняется по отдельному поручению.

## Разобрать пропуски

Проверьте, о чём говорят `rawEligibility` и `rawReasons` для этого плана. При `SOURCE_NOT_OBSERVED`, `SOURCE_REFRESH_FAILED` или `INCOMPLETE_MEASUREMENT` откройте интервалы и материалы выполнения. Исправьте признаки, если менялся объём работ. Сохраните отдельную строку для каждого подтверждённого плана, в том числе для похожих задач, коротких и долгих работ и больших расхождений прогноза с фактом. Для подготовленной строки укажите `ELIGIBLE`, `groupId:null`, `reasons:[]` и полную аннотацию `ACTUAL`.

Если для обязательного поля или времени по-прежнему нет факта, сохраните черновик локально и обработайте остальные строки. До сохранения и обучения покажите пользователю каждый нерешённый план. Назовите ID, название, поле, что уже проверили и какой ответ нужен. Например, «План “Приёмка оплаты”, ID … . В таймере 4 минуты. В отчёте указано, что часть проверки прошла до старта. Сколько всего минут активной работы занял этот план?» Если пользователь сообщил значение или указал источник, проверьте его и заполните строку. До ответа оставьте её в черновике. В API доступны окончательные решения `ELIGIBLE` и `EXCLUDED`.

Для исключения завершённого неудалённого плана требуется явное решение пользователя по этому `planId`. Передайте `EXCLUDED`, `USER_REQUESTED_SKIP` и указание пользователя в `exclusionEvidence.userDecision`. Оно требуется при каждом использовании этого кода, включая удалённые и незавершённые планы. Для действующего ранее выданного разрешения достаточно уже имеющейся ссылки.

Пройдите страницы истории нативных ревизий через `GetDatasetRevision({schemaVersion:1,view:'list'})` и `view:'rows'`. Передавайте полученный `nextCursor` как `cursor` с теми же фильтрами. В полном экспорте проверьте последнее явное указание по этому плану, учитывая текущее поручение. Код ошибки, прежняя отметка `EXCLUDED` и комментарий агента сами по себе не подтверждают разрешение пользователя. Если пользователь снял пропуск, подготовьте строку и добавьте ссылку на это решение в `codeEvidence`. Пробелы, для которых требуется ответ, покажите пользователю.

## Сверить и сохранить

Сопоставьте каждый `rowId` с его `planId` из снимка. В файле разметки передайте одно решение на каждый `rowId`. Сервер добавит соответствующий `planId` в экспорт. Сумма пригодных и исключённых строк должна совпадать с числом планов снимка. Для v4 сохраните UTF-8 JSON `{schemaVersion:1,contract:'atlm-teacher-annotations-v2',snapshotId,parentDatasetRevisionId,rows}`. Если родителя нет, передайте `parentDatasetRevisionId:null`. Выгрузите сохранённый `atlm-teacher-dataset-v2` через `GetDatasetRevision`. Проверьте SHA-256 по `datasetDigest`, все ID, решения и исправленные значения. [Сохранение и проверка файлов](transfer.md).

До обучения покажите пользователю ID и дату снимка, ID датасета, общее число планов и сколько включено и исключено. Отдельно посчитайте планы, где исправили или дополнили признаки либо время. План с несколькими правками считайте один раз. Перечислите планы, где изменили время. Для каждого исключённого укажите `planId`, название и конкретную причину. Для пользовательского пропуска приведите ссылку на сообщение или цитату и источник. Если строк много, отдайте полный список файлом и числа в сообщении.

## Пример разметки

```js
const rows = [
  {
    rowId: 'row-completed',
    groupId: null,
    eligibility: 'ELIGIBLE',
    reasons: [],
    annotation: {
      scope: 'ACTUAL',
      agentTask,
      fieldEvidence,
      codeEvidence: 'Тест parseDate принимает YYYY-MM-DD и отклоняет неверную дату.',
      actualTime: {
        actualMs: 180000,
        evidence: 'Журнал работы по этому плану подтверждает 3 минуты активного времени.',
      },
    },
  },
  {
    rowId: 'row-user-skipped',
    groupId: null,
    eligibility: 'EXCLUDED',
    reasons: ['USER_REQUESTED_SKIP'],
    annotation: null,
    exclusionEvidence: {
      userDecision: 'Сообщение пользователя №42 о плане plan-demo: «Пропусти этот план, это пробный запуск».',
    },
  },
];
```

В примере подставьте реальные ID строк, проверенные `agentTask` и `fieldEvidence`. Для пропуска укажите настоящее сообщение пользователя и соответствующий ему `planId`. Укажите конкретные записи, которыми подтвердили время. [Пример схемы признаков](../../assess-task/references/examples.md#пример-исходных-признаков).
