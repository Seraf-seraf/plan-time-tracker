# Оцените задачу до начала исполнения

Применяйте при планировании, начале разрешённого исполнения и существенном изменении задачи вместе с соседним track-plan. При capability `assessments.atlm` используйте основной ATLM-сценарий ниже. Это прогноз полного активного времени агентов PLAN_ACTIVE от первого StartPlan; модель, веса и обучающие примеры выбирает сервер. Старый CalculateEstimate остаётся отдельным методом исторической медианы в разделе совместимости.

## Основной сценарий ATLM

### Цель

Описать факты задачи до исполнения, получить серверный прогноз полного PLAN_ACTIVE, сохранить связь с исходными требованиями. Коэффициенты и обучающие данные выбирает сервер. Метод не выдаёт универсальный балл сложности.

### Порядок

1. Найди существующий план или зарегистрируй PLANNED-план и существенные шаги обычным track-plan. Планирование не запускает таймер. Не создавай план ради справочного ответа или обслуживания очереди обучения.
2. Прочитай GetTrackerCapabilities и обнаруженные инструменты. При assessments.atlm используй именно указанные в capability имена. В начале сеанса проверь GetEstimationModelStatus; если training.due=true, вызови один ProcessEstimationTraining. Не создавай рекурсивный план для этого обслуживания и не жди обучения бесконечно.
3. Вызови GetAssessment({planId}) без assessmentId/revision и сохрани currentRequirementsDigest. Анализируй этот контекст, а не старое описание из памяти.
4. До начала исполнения изучи необходимый код/документацию, ожидаемый результат, существующий механизм, обязательные проверки и требуемую границу завершения.
5. Составь AgentTaskV1 строго по схеме и определениям ниже. Для категорий и элементов списков укажи короткие основания/источники. Используй факты, известные в момент оценки.
6. Не включай фактические токены, время, число попыток, будущий diff или итоговое число файлов. Не выбирай признаки по желаемому прогнозу и не меняй их после просмотра исторических длительностей ради нужного числа.
7. Неизвестное отмечай UNKNOWN/null с причиной. Ноль/[] означает проверенное отсутствие. Не угадывай модель агента или reasoning effort, если среда их не раскрывает.
8. Запиши RecordAssessment со всеми действующими обязательными полями, context.agentTask и predictionRequest={method:"ATLM",methodVersion:1}. Для новой серии expectedVersion=0; для ревизии — её текущий номер и reason. expectedRequirementsDigest — полученный до анализа digest.
9. Количественный point записывает сервер в assessment.serverEstimation. При точке без прогнозного интервала старый forecast остаётся UNKNOWN, lowerMs/upperMs=null, confidence=UNKNOWN. Не заполняй эти границы точкой и не называй точку P50/P80.
10. COLLECTING_DATA или иная расчётная недоступность не отменяет запись признаков и не запрещает разрешённую работу. Ошибка источника — отдельная ошибка: не называй её отсутствием похожих планов. При отсутствии capability можно записать признаки без predictionRequest и сохранить UNKNOWN.
11. Соблюдай действующие receipt/CAS правила. При потерянном ответе проверь GetCommandReceipt/состояние серии; не создавай дубль. При конфликте требований перечитай их и пересмотри признаки, а не заменяй digest механически.
12. После записи до первого StartPlan выполняй обычный процесс track-plan. В момент первого запуска сервер фиксирует подходящую уже записанную ревизию. Поздняя оценка не становится исходным обучающим примером.
13. При изменении требований создай новую ревизию и объясни изменения. Не переписывай исходную. В v1 прогноз оставшегося времени не поддержан: не вычитай затраченное время из исходной точки. Для уже начатого плана новая оценка признаков может быть сохранена без predictionRequest; исходный прогноз отмечается устаревшим.
14. По завершении честно запиши результат и обязательные проверки обычными командами. Не сокращай проверки ради прогноза и не исключай неудачные попытки из активного времени. Сервер сам решает, пригоден ли пример, и после пяти новых примеров запускает переобучение.

### Схема исходных признаков

`context.agentTask` содержит обязательные поля:

- `schemaVersion:"agent-task-v1"`;
- `profile:{workKind,reuseState,doneBoundary}` — категории определены ниже;
- `outcomes:null|[{id,description,evidence}]` — не более 20 самостоятельных результатов;
- `changedContracts:null|[{kind,key,description,evidence}]` — не более 20 изменяемых контрактов, kind: API/MCP/EVENT/STORAGE/OTHER;
- `verificationKinds:null|[BUILD_STATIC,UNIT,INTEGRATION,UI_E2E,DEPLOY_SMOKE]` — только выбранные уникальные категории;
- `profileEvidence:{workKind,reuseState,doneBoundary}` — короткие основания каждого выбора;
- `runtimeContext:{modelId,reasoningEffort,environmentId,plannedParallelAgents,provenance}` — неизвестные значения null, provenance CLIENT_REPORTED или UNKNOWN, число исполнителей положительное целое либо null.

id/key — 1–128 символов; description/evidence и основания — 1–400; строки runtimeContext — до 128. Сервер объединяет точные дубли и считает outcomeCount/contractCount/verificationKindCount: не передавай эти счётчики самостоятельно. Разные описания одного ключа — ошибка. UNKNOWN/null не равны нулю или подтверждённому отсутствию. Максимум assessment — 24000 UTF-8 байт, глубина JSON 10, включая серверный прогноз. Не отправляй секреты, исходники и полные журналы.

RecordAssessment сохраняет прежние обязательные поля: assessmentId, planId, expectedRequirementsDigest, context, method {id,version,scale}, complexity {status,value,rationale}, unknowns, assumptions, dependencies, forecast {status,metric,lowerMs,upperMs,confidence,basis,sampleCount}, sources, approach {description,rationale}, phase; reason обязателен при ревизии. Для ATLM нет обязательных story points: complexity может быть UNKNOWN/value:null с причиной. Источники прошлых планов не требуются для серверного ATLM. Пустой sources допустим. Все записи используют schemaVersion=1 и стабильный commandId UUID.

### Определения категорий

- CREATE_MECHANISM: требуемой возможности нет, нужно создать её.
- MODIFY_MECHANISM: требуется изменить поведение существующей возможности.
- RUN_EXISTING_PROCESS: достаточный механизм уже есть, требуется выполнить/настроить предусмотренный процесс без разработки нового поведения.
- VERIFY_EXISTING: самостоятельный результат — проверка существующего состояния.
- MIGRATE_DATA: самостоятельный основной результат — перенос/преобразование сохранённых данных.
- INVESTIGATE: результат — исследование, выводы или решение без реализации.
- MIXED: несколько самостоятельных результатов относятся к разным видам; выбор одного скрыл бы существенную часть задания. Не выбирать вид по предполагаемой длительности.
- UNKNOWN: контекста недостаточно для классификации.

reuseState: ABSENT — необходимого механизма нет; PARTIAL — есть основа, но нужна доработка; READY — достаточно существующих механизмов. Для изменения кода существующего механизма обычно PARTIAL, для запуска готовой процедуры — READY. Название технологии само по себе ничего не определяет.

doneBoundary: ANALYSIS — принят результат анализа; LOCAL_VERIFIED — локальный результат и необходимые проверки; LOCAL_STAGED — дополнительно подготовлен индекс; PUBLISHED — требуемый результат опубликован; DEPLOYED_VERIFIED — развёрнут и проверен. Не считать публикацию и деплой автоматически требуемыми.

### Как считать списки

- outcomes: один пункт на самостоятельный пользовательский результат. «Загрузка по запросу» и «пагинация» — два результата; «изменить обработчик», «поправить клиент», «проверить» — способы исполнения, не три результата.
- changedContracts: одна операция API/MCP, один формат события или одна схема сущности хранения — один элемент. Изменение обработчика и клиента одного endpoint не удваивает счётчик. Использование неизменённого endpoint даёт ноль новых контрактов.
- verificationKinds: только требуемые категории из схемы выше. Три повторных запуска unit suite дают одну UNIT. Не назначать дополнительные тесты для увеличения признака.
- Обоснования ссылаются на требования, существующий интерфейс или доступный код. Число строк и файлов не заменяет основания.

### Калибровочные примеры для проверки инструкции

| Требование и известный контекст | Ожидаемая разметка |
| --- | --- |
| Изменить надпись существующей кнопки, проверить сборку, оставить локально | MODIFY_MECHANISM / PARTIAL / LOCAL_VERIFIED; 1 outcome; 0 contracts; BUILD_STATIC. |
| Запустить уже готовый экспорт и проверить полученный файл | RUN_EXISTING_PROCESS / READY / LOCAL_VERIFIED; 1 outcome; 0 изменяемых contracts; категории проверок только по реальному механизму проверки файла, не автоматически UNIT. |
| Добавить ленивую историю и пагинацию; известен один меняющийся endpoint | MODIFY_MECHANISM / PARTIAL; 2 outcomes; 1 API-contract, даже если меняются клиент и сервер. doneBoundary и verificationKinds — из условий задания. |
| Неизвестно, существует ли нужный API | reuseState=UNKNOWN; changedContracts=null, не []. До оценки выполнить доступный узкий просмотр. |
| Результат уже реализован, исходного снимка не было | Не размечать завершённый план как исходный обучающий пример. Можно сохранить позднюю описательную оценку. |
| План требует 4 независимых результата, агент разбил его на 12 шагов | outcomeCount остаётся 4, если требования не изменились. |

Одна инструкция не гарантирует одинаковую классификацию. Перед выпуском два независимых прохода по одинаковым исходным требованиям без фактического времени должны совпасть в структурных полях на фиксированном наборе примеров; расхождения уточняют определения, не подгоняются под длительности.

## Совместимость с исторической медианой

Следующий процесс относится только к отдельно выбранному reference-class-median/1 либо серверу без ATLM capability. Он не является обязательным предварительным шагом ATLM и не передаёт candidates в CalculateAtlmEstimate. При недостатке данных можно сохранить UNKNOWN; обязательные проверки результата сохраняются.

### Порядок исторической оценки

1. Определите ожидаемый результат, границы, необходимые проверки и ограничения.
   Изучите доступный контекст до оценки; явно назовите неизвестные, допущения и
   зависимости. Уточняйте только то, что мешает выбрать решение, продолжая
   независимую работу в разрешённой области.
2. Через `track-plan` найдите или зарегистрируйте план и его существенные шаги.
   Одна задача — план минимум с одним проверяемым шагом. Планирование оставляет
   PLANNED без StartPlan/StartStep, исполнения и таймера. Продолжение использует
   существующие ID. Существенные новые шаги и изменения объёма записывайте до работы.
3. Вызовите GetTrackerCapabilities и обнаружение инструментов. Требуйте capability
   `assessments` и указанные в ней RecordAssessment/GetAssessment/GetEstimationHistory;
   не делайте вывод о поддержке из номера версии продукта. При недоступности
   сообщите о блокере, остановите зависимую работу, соблюдая уже выданные исключения
   пользователя. Не подменяйте запись оценки текстом в другом поле как успешный вызов.
4. Объявите методику, её версию и шкалу. По умолчанию используйте Scrum-подход к
   относительной оценке: сравните с опорными задачами, рассмотрите объём, сложность
   и неопределённость. Начальная предлагаемая шкала — 1, 2, 3, 5, 8, 13 story points.
   Это заменяемая методика навыка. При необходимости используйте качественную или
   многомерную оценку. Не называйте одиночную оценку командным Planning Poker.
   Крупную или непонятную задачу декомпозируйте либо начните с исследования.
   Перед анализом первой оценки и каждым пересмотром прочитайте
   `GetAssessment({planId, stepId?})` без assessmentId/revision. Этот режим не
   создаёт оценку: он возвращает текущие requirements и currentRequirementsDigest.
   Анализируйте именно этот контекст и сохраните digest вместе с выводами.
5. До запроса истории длительностей зафиксируйте результат и done boundary, наличие
   существующего механизма и профиль `workKind`, `reuseState`, `doneBoundary`.
   Слова «инфраструктура», «PostgreSQL» или «безопасность» сами по себе не определяют
   профиль. Затем прочитайте доступную историю: ListPlans с явными признаками и
   пагинацией, GetPlanExecutionSnapshot для результатов и проверок аналогов,
   GetEstimationHistory для выбранных targets. Объясните сопоставимость: результат,
   условия, проверки и вид времени. COMPLETED не доказывает успешных checks. Для
   следующих страниц сохраните asOf, throughSequence и nextAfterSequence (передавайте
   его как afterSequence); статистики описывают всю выборку фактов, а не только
   текущую страницу ревизий. Проверяйте состав результата, необходимые проверки и
   качество исхода; не добавляйте в полный прогноз тесты или ревью второй раз, если
   они уже входят в измерения аналогов. Выбирайте кандидатов по результату и
   условиям, а не длительности. `ListPlans` раскрывает время, поэтому процедуру нельзя
   называть технически слепым тестом. До `INCLUDE` проверьте известные существенные
   условия: модель и effort, среду и доступы, готовность инструментов, число
   параллельных исполнителей. Не угадывайте их по ownerId, названию проекта или
   результату; при неизвестном существенном условии используйте `DESCRIPTIVE`/
   `EXCLUDE` с причиной. Менее важное различие обоснуйте в rationale. V1 не
   удостоверяет равенство моделей и не нормализует скорость; не требуйте набора тегов
   чужого продукта и не группируйте работу по английским ключевым словам. История
   другого проекта допустима при сопоставимости; одиночная крупная задача и
   демонстрационные JSONL не заменяют выборку пользователя. Например, запуск готового
   процесса (`RUN_EXISTING_PROCESS`) и разработка нового механизма
   (`CREATE_MECHANISM`) имеют разный профиль даже при общей теме. `INCLUDE` оставляйте
   только для завершённых принятых планов с неизменным объёмом, полной метрикой и
   подтверждёнными проверками; изменённые, незавершённые или непринятые исходы не
   превращайте в успешные длительности. Три поля профиля должны совпадать точно;
   несколько, даже пять, неоднородных записей не образуют одну сравнимую группу и
   сами по себе не повышают confidence.
6. Оцените сложность с обоснованием. Прогноз длительности сформируйте отдельно:
   сначала зафиксируйте точный список явных planId для включения и исключения с
   причинами (не более 20 источников), затем, если `GetTrackerCapabilities`
   объявляет `assessments.calculator` и `CalculateEstimate` обнаружен, вызовите
   read-only инструмент. Не меняйте кандидатов ради желаемой медианы. Проверьте
   результат, `accuracy: NOT_VALIDATED`, известные и исключённые источники. Пустая
   выборка означает `INSUFFICIENT_DATA`; ошибка `CalculateEstimate` — отказ источника,
   а не пустой результат. Ошибка `GetEstimationHistory` также не доказывает отсутствия
   полных `PLAN_ACTIVE` интервалов: калькулятор читает их независимо, но не заменяет
   шаговые метрики или историю ревизий. Если новая capability/tool отсутствует, не
   имитируйте её в тексте: при работающем учёте можно продолжить с `UNKNOWN` либо
   отдельной явно экспертной оценкой.
   Рассматривайте наблюдавшийся point как исторический ориентир, не как границы
   интервала и не как вероятность принятия результата. Не переводите SP в часы
   коэффициентом и не смешивайте `PLAN_ACTIVE`, календарное время, паузы,
   атрибуцию шага, попытки или вызовы инструментов. Неизвестное значение — null,
   не ноль.
7. Выберите достаточный способ решения. Качество важнее скорости. Усложнение
   обоснуйте требованием, надёжностью, проверяемостью или сопровождением; упрощение
   сохраняет результат и обязательные проверки. При дополнительной экспертной
   поправке укажите отдельные величину и причину; не заменяйте ею baseline и не
   применяйте скрытый коэффициент риска. `forecast` может быть `KNOWN` только для
   отдельно обоснованного экспертного интервала с указанным экспертным происхождением;
   точечный baseline без такого интервала сохраняет `forecast.status: UNKNOWN`,
   null-границы и `confidence: UNKNOWN`; `forecast.sampleCount` равен baseline
   `sampleCount`. Сообщите, что это исторический ориентир по принятым задачам с
   неизменным объёмом и непроверенной точностью, а не гарантия, вероятность успеха
   или acceptance rate. Не повышайте уверенность из-за числа
   ревьюеров, совпадения SP или размера выборки и не объявляйте автоматическое
   обучение при сохранении новой оценки. Для тривиальной задачи не нужно искусственно
   создавать несколько архитектурных вариантов.
8. Запишите RecordAssessment и подтвердите ответ. Для новой серии используйте новый
   assessmentId UUID и expectedVersion=0; для пересмотра — тот же assessmentId,
   текущую revision в expectedVersion и непустую reason. Поля payload: planId,
   stepId при оценке шага, expectedRequirementsDigest (сохранённый до анализа
   currentRequirementsDigest), context, method {id, version, scale}, complexity
   {status: KNOWN/UNKNOWN, value, rationale}, unknowns, assumptions, dependencies,
   forecast {status, metric, lowerMs, upperMs, confidence, basis, sampleCount},
   sources [{planId, stepId?}], approach {description, rationale}, phase, reason?.
   UNKNOWN complexity.value и UNKNOWN forecast.lowerMs/upperMs требуют null.
   Метрики: PLAN_ACTIVE, CALENDAR, PAUSED, STEP_ATTRIBUTED, ATTEMPT, TOOL.
   Не передавайте секреты, исходники или полные журналы; запись ограничена 24000
   UTF-8 байтами и глубиной JSON 10. Пример методики: {id: "scrum-relative",
   version: "1", scale: {unit: "story-points", values: [1,2,3,5,8,13]}}.
   При сохранении используйте `context.estimation` из §2.7 и `sources` для использованных
   планов. Если лимит мешает, сократите повторяющиеся пояснения вне снимка; не удаляйте
   выбранные аналоги, не меняйте `inputSnapshot` и не утверждайте, что несохранённая
   оценка записана. Если после измерения полного плана прогнозируете остаток, создайте
   отдельную ревизию с `phase="remaining"`; сохраните исходный baseline и не вычитайте
   уже затраченное время из полной медианы.

### Пересмотр исторической оценки и передача

Сохраняйте исходную оценку. GetAssessment возвращает актуальную или указанную
ревизию, needsRevision и digest требований. Изменение существенных требований
требует пересмотра; обычная смена статуса сама по себе его не требует. Для нового
метода можно создать независимую серию, не приводя её к шкале другого агента.
Прогноз остатка оформляйте новой ревизией с phase="remaining" и причиной, явно
отличая его от первоначального полного прогноза.
В режиме чтения сохранённой ревизии requirements относятся к её старому снимку;
для текущего контекста вызывайте GetAssessment без assessmentId. Если запись
вернула ASSESSMENT_CONTEXT_CHANGED, перечитайте контекст и пересмотрите выводы
до новой команды. Не подставляйте свежий digest под старый анализ ради повтора.

Передайте исполнителю planId, stepId, assessmentId/revision, критерии результата
и проверки, методику/шкалу, выбранный способ, допущения, факт времени с качеством
измерения, сохранённый `context.estimation`/calculationDigest и прогноз остатка.
Исходный baseline и неизменяемый снимок остаются в своей ревизии; остаток — отдельный
прогноз, а не новый полный baseline. Исполнитель читает существующий контекст,
проверяет требования и может обоснованно пересмотреть оценку. Существенно изменившиеся
требования требуют чтения актуального контекста и новой ревизии с причиной, а не
подмены прежнего digest. После работы фиксируются
результат, проверки и факты по track-plan, затем сравнивается прогноз с фактом
той же метрики. Это не автоматически обучает методику и не переписывает baseline.

Все записи используют schemaVersion=1 и стабильный commandId UUID. После потери
ответа повторите идентичный конверт либо прочитайте GetCommandReceipt; PENDING
не равен успеху. При CAS-конфликте прочитайте текущую ревизию и согласуйте новые
сведения, не перезаписывайте чужую оценку. Автор и дата принадлежат серверу.

В отчёте различайте наблюдаемое поведение агента, проверки текста навыка, локальный
запуск протокола API и проверку развёрнутого приложения. Успешный текстовый тест
не выдавайте за сквозную работу агента.
