# Оценить задачу до начала работы

Используйте вместе с соседним track-plan при планировании, перед началом разрешённой работы и при существенном изменении задачи. При capability `assessments.atlm` используйте основной ATLM-сценарий ниже. Это прогноз полного активного времени агентов PLAN_ACTIVE от первого StartPlan; модель, веса и обучающие примеры выбирает сервер. Для получения прогноза используй серверный EstimatePlanTime и predictionRequest ATLM. При недоступности ATLM сервер может вернуть явно обозначенный historical-median — ранний ориентир по реальной пригодной истории; проверяй serverEstimation.method и не называй медиану обученной ATLM. Не рассчитывай и не подставляй прогноз самостоятельно. GetSavedEstimate читает сохранённый прогноз и не рассчитывает новый.

## Как получить прогноз ATLM

### Цель

Описать факты задачи до начала работы, получить серверный прогноз полного PLAN_ACTIVE и сохранить связь с исходными требованиями. Коэффициенты и обучающие данные выбирает сервер. Метод не рассчитывает универсальный балл сложности.

### Порядок действий

1. Найди существующий план или зарегистрируй PLANNED-план и существенные шаги обычным track-plan. Планирование не запускает таймер. Не создавай план ради справочного ответа или обслуживания очереди обучения.
2. Прочитай GetTrackerInfo и обнаруженные инструменты. При assessments.atlm используй именно указанные в capability имена. В начале сеанса проверь GetTrainingStatus; если training.due=true, вызови один ContinueTraining. Не создавай рекурсивный план для этого обслуживания и не жди обучения бесконечно.
3. Вызови GetTaskAssessment({planId}) без assessmentId/revision и сохрани currentRequirementsDigest. Анализируй этот контекст, а не старое описание из памяти.
4. До начала работы изучи нужный код и документацию. Уточни ожидаемый результат, существующий механизм, обязательные проверки и условия завершения задачи.
5. Составь AgentTaskV1 строго по схеме и определениям ниже. Для категорий и элементов списков коротко укажи основания и источники. Используй факты, известные в момент оценки.
6. Не включай фактически потраченные токены и время, число попыток, будущий diff или итоговое число файлов. Не выбирай признаки по желаемому прогнозу и не меняй их после просмотра исторических длительностей ради нужного числа.
7. Неизвестное отмечай UNKNOWN/null с причиной. Ноль/[] означает проверенное отсутствие. Не угадывай модель агента или reasoning effort, если среда их не раскрывает.
8. Запиши SaveTaskAssessment со всеми действующими обязательными полями, context.agentTask и predictionRequest={method:"ATLM",methodVersion:1}. Для новой серии expectedVersion=0; для ревизии — её текущий номер и reason. expectedRequirementsDigest — полученный до анализа digest.
9. Количественный point записывает сервер в assessment.serverEstimation. При точке без прогнозного интервала старый forecast остаётся UNKNOWN, lowerMs/upperMs=null, confidence=UNKNOWN. Не заполняй эти границы точкой и не называй точку P50/P80.
10. COLLECTING_DATA или иная расчётная недоступность не отменяет запись признаков и не запрещает разрешённую работу. Ошибка источника — отдельная ошибка: не называй её отсутствием похожих планов. При отсутствии capability можно записать признаки без predictionRequest и сохранить UNKNOWN.
11. Соблюдай действующие receipt/CAS правила. При потерянном ответе проверь GetCommandResult/состояние серии; не создавай дубль. При конфликте требований перечитай их и пересмотри признаки, а не заменяй digest механически.
12. После записи до первого StartPlan выполняй обычный процесс track-plan. В момент первого запуска сервер фиксирует подходящую уже записанную ревизию. Поздняя оценка не становится исходным обучающим примером.
13. При изменении требований создай новую ревизию и объясни изменения. Не переписывай исходную. В v1 нет прогноза оставшегося времени: не вычитай затраченное время из исходной точки. Для уже начатого плана новая оценка признаков может быть сохранена без predictionRequest; исходный прогноз отмечается устаревшим.
14. По завершении выполни необходимые проверки и сообщи результат пользователю. Сохрани текущие статусы этапов через SetStepStatus; готовый этап помечай DONE после фактической приёмки. Не сокращай проверки ради прогноза. Сервер сам решает, пригоден ли пример, и после двух новых примеров запускает переобучение.

### Какие исходные признаки передавать

`context.agentTask` содержит поля ниже; runtimeContext и его отдельные поля необязательны:

- `schemaVersion:"agent-task-v1"`;
- `profile:{workKind,reuseState,doneBoundary}` — категории определены ниже;
- `outcomes:null|[{id,description,evidence}]` — не более 20 самостоятельных результатов;
- `changedContracts:null|[{kind,key,description,evidence}]` — не более 20 изменяемых контрактов, kind: API/MCP/EVENT/STORAGE/OTHER;
- `verificationKinds:null|[BUILD_STATIC,UNIT,INTEGRATION,UI_E2E,DEPLOY_SMOKE]` — только выбранные уникальные категории;
- `profileEvidence:{workKind,reuseState,doneBoundary}` — короткие основания каждого выбора;
- `runtimeContext:{modelId,reasoningEffort,environmentId,plannedParallelAgents,provenance}` — необязательные параметры: отсутствие блока/поля, null и пустые строки modelId/effort означают неизвестно; provenance CLIENT_REPORTED или UNKNOWN, число одновременно работающих исполнителей (включая основного) положительное целое либо null. Неизвестные runtime-параметры не запрещают прогноз.

id/key — 1–128 символов; description/evidence и основания — 1–400; строки runtimeContext — до 128. Сервер обучает agent-v2 по девяти признакам: трём категориям, трём счётчикам и modelId/reasoningEffort/plannedParallelAgents. Входное описание остаётся agent-task-v1, схема вычислителя — agent-task-v2. Сервер объединяет точные дубли и считает outcomeCount/contractCount/verificationKindCount: не передавай эти счётчики самостоятельно. Разные описания одного ключа — ошибка. UNKNOWN/null не равны нулю или подтверждённому отсутствию. Максимум assessment — 24000 UTF-8 байт, глубина JSON 10, включая серверный прогноз. Не отправляй секреты, исходники и полные журналы.

SaveTaskAssessment сохраняет прежние обязательные поля: assessmentId, planId, expectedRequirementsDigest, context, method {id,version,scale}, complexity {status,value,rationale}, unknowns, assumptions, dependencies, forecast {status,metric,lowerMs,upperMs,confidence,basis,sampleCount}, sources, approach {description,rationale}, phase; reason обязателен при ревизии. Для ATLM нет обязательных story points: complexity может быть UNKNOWN/value:null с причиной. Источники прошлых планов не требуются для серверного ATLM. Пустой sources допустим. Все записи используют schemaVersion=1 и стабильный commandId UUID.

### Что означают категории

- CREATE_MECHANISM: требуемой возможности нет, нужно создать её.
- MODIFY_MECHANISM: требуется изменить поведение существующей возможности.
- RUN_EXISTING_PROCESS: достаточный механизм уже есть, требуется выполнить/настроить предусмотренный процесс без разработки нового поведения.
- VERIFY_EXISTING: самостоятельный результат — проверка существующего состояния.
- MIGRATE_DATA: самостоятельный основной результат — перенос/преобразование сохранённых данных.
- INVESTIGATE: результат — исследование, выводы или решение без реализации.
- MIXED: несколько самостоятельных результатов относятся к разным видам; выбор одного скрыл бы существенную часть задания. Не выбирать вид по предполагаемой длительности.
- UNKNOWN: контекста недостаточно для классификации.

reuseState: ABSENT — необходимого механизма нет; PARTIAL — есть основа, но нужна доработка; READY — достаточно существующих механизмов. Для изменения кода существующего механизма обычно PARTIAL, для запуска готовой процедуры — READY. Название технологии само по себе ничего не определяет.

doneBoundary: ANALYSIS — принят результат анализа; LOCAL_VERIFIED — локальный результат и необходимые проверки; LOCAL_STAGED — дополнительно подготовлен индекс; PUBLISHED — требуемый результат опубликован; DEPLOYED_VERIFIED — развёрнут и проверен. Не считать публикацию и деплой автоматически требуемыми.

### Как считать списки

- outcomes: один пункт на самостоятельный пользовательский результат. «Загрузка по запросу» и «пагинация» — два результата; «изменить обработчик», «поправить клиент», «проверить» — способы исполнения, не три результата.
- changedContracts: одна операция API/MCP, один формат события или одна схема сущности хранения — один элемент. Изменение обработчика и клиента одного endpoint не удваивает счётчик. Использование неизменённого endpoint даёт ноль новых контрактов.
- verificationKinds: только требуемые категории из схемы выше. Три повторных запуска unit suite дают одну UNIT. Не назначать дополнительные тесты для увеличения признака.
- Обоснования ссылаются на требования, существующий интерфейс или доступный код. Число строк и файлов не заменяет основания.

### Примеры для проверки разметки

| Требование и известный контекст | Ожидаемая разметка |
| --- | --- |
| Изменить надпись существующей кнопки, проверить сборку, оставить локально | MODIFY_MECHANISM / PARTIAL / LOCAL_VERIFIED; 1 outcome; 0 contracts; BUILD_STATIC. |
| Запустить уже готовый экспорт и проверить полученный файл | RUN_EXISTING_PROCESS / READY / LOCAL_VERIFIED; 1 outcome; 0 изменяемых contracts; категории проверок только по реальному механизму проверки файла, не автоматически UNIT. |
| Добавить ленивую историю и пагинацию; известен один меняющийся endpoint | MODIFY_MECHANISM / PARTIAL; 2 outcomes; 1 API-contract, даже если меняются клиент и сервер. doneBoundary и verificationKinds — из условий задания. |
| Неизвестно, существует ли нужный API | reuseState=UNKNOWN; changedContracts=null, не []. До оценки выполнить доступный узкий просмотр. |
| Результат уже реализован, исходного снимка не было | Не размечать завершённый план как исходный обучающий пример. Можно сохранить позднюю описательную оценку. |
| План требует 4 независимых результата, агент разбил его на 12 шагов | outcomeCount остаётся 4, если требования не изменились. |

Одна инструкция не гарантирует одинаковую классификацию. Перед выпуском два независимых прохода по одинаковым исходным требованиям без фактического времени должны совпасть в структурных полях на фиксированном наборе примеров; расхождения уточняют определения, не подгоняются под длительности.


Ручной запуск: вызывайте обнаруженный инструмент StartTraining только по прямой просьбе пользователя запустить или повторить обучение. Он может запустить попытку до накопления двух новых планов, но не гарантирует достаточности данных или принятия модели. Сообщите пользователю возвращённый статус; при необходимости продолжайте только запрошенное обучение через ContinueTraining. Автоматическое серверное переобучение остаётся включённым.


Ранний прогноз может иметь accuracy=EXPERIMENTAL: это доступная точка без подтверждённого качества. Передавайте пользователю sampleCount и evaluation.caseCount отдельно. При нуле проверок ошибка не оценена (null), а не равна нулю. confidence остаётся UNKNOWN; не обещайте интервал или точность по малой выборке. Модель хранится на сервере, preview применяет готовые коэффициенты; GetSavedEstimate только читает сохранённую оценку.
