# План реализации гибридного прогноза ATLM

## 1. Контекст и описание задачи

Этот раздел справочный: он объясняет задачу и не разрешает начинать все этапы. Пользователь поручил реализовать весь план H1–H5. Разрешена локальная реализация и подготовка индекса своих изменений; коммиты, отправка изменений и публикация не входят в поручение.

Трекер прогнозирует полное активное время плана PLAN_ACTIVE по девяти исходным признакам. Завершённый пригодный план даёт фактический результат actualMs из серверных рабочих интервалов. Сохранённый прогноз результат обучения не подменяет.

Исследование 13 ноября 2026 года подтвердило для снимка datasetRevision=263: 25 пригодных уникальных планов, матрица нынешнего OLS 25×22, ранг 17. Последняя серверная попытка использовала 24 плана и остановилась при ранге 16. Активной модели нет. Это результаты конкретного снимка, а не постоянные константы приложения и не обязательные числа следующего запуска.

Причина блокировки: обычный метод наименьших квадратов (OLS) требует независимо определимых коэффициентов. В этой истории вид работы совпадает с готовностью решения, число проверок определяется профилем, а известные modelId/reasoningEffort встречаются только у задач создания серверов. Повторение таких сочетаний само по себе зависимости не устраняет.

Требуемый результат — гибрид, который использует OLS или ridge с учётом ошибок на прошлых задачах и сохраняет явно обозначенную медиану как запасной ориентир. Полный ранг разрешает расчёт OLS, но не даёт ему безусловный приоритет. Все исходные признаки и сохранённые прогнозы начатых планов сохраняются. Код, пользовательское объяснение, MCP-описание и документация должны соответствовать одному поведению.

Основные существующие участки:

- `sites/plan-time-tracker/worker/index.js`: нормализация AgentTaskV1; fitAtlm/predictAtlm; хронологическая проверка; сборка и хранение samples; очередь обучения; получение текущего/frozen-прогноза; UI_ATLM.
- `sites/plan-time-tracker/drizzle/0019_atlm.sql`, `0021_simple_steps.sql`, `0023_atlm_diagnostics.sql`, `0024_current_plan_forecast.sql`: существующие таблицы, очередь, неизменяемые исходные снимки и артефакты.
- `sites/plan-time-tracker/scripts/evaluate-atlm.mjs`: существующая локальная проверка истории.
- `docs/atlm.md`, README и инструкции пакета: существующие описания OLS agent-v2, неизвестных значений, раннего прогноза и сохранения исходной оценки.

Простое объяснение результата для пользователя: «Трекер учится на измеренном времени завершённых задач. Он сравнивает способы прогноза на более ранних результатах. Когда обычный расчёт не может разделить влияние совпадающих признаков, доступен ridge. Если подходящей обученной оценки нет, показана медиана прошлых длительностей. Ошибка прошлых проверок не гарантирует длительность следующей задачи».

## 2. Решения, границы и правила исполнения

### 2.1. Состав реализации и неизменяемые данные

Реализация ограничена репозиторием, локально собранным Worker, документацией и проверками в изолированной среде. Работать в `main`. Перед началом выполнения проверить состояние рабочей копии и выполнить `git pull --ff-only`, сохранив чужую работу. Не применять принудительный сброс или перезапись ветки.

Трекер для управления этой работой не использовать. Не создавать, запускать, завершать или менять планы владельца; не вызывать StartTraining/ContinueTraining в рабочем трекере; не менять рабочую D1; не обновлять hosted-плагин и опубликованный Site. Разрешено переиспользовать локальную копию реальной истории. При необходимости свежего снимка — только read-only GetTrainingStatus/GetTrainingData с полной пагинацией одного datasetRevision/asOf. Чтение данных для проверки не является учётом этой работы через трекер.

Сохранить все девять признаков:

1. workKind;
2. reuseState;
3. doneBoundary;
4. outcomeCount;
5. contractCount;
6. verificationKindCount;
7. modelId;
8. reasoningEffort;
9. plannedParallelAgents.

Не удалять признаки для получения полного ранга, не менять исходные значения, не размечать старые планы задним числом. Не добавлять длительности, прогнозы, текущие статусы или результаты проверяемой задачи в её исходные признаки. Средние, масштабы, индикаторы пропуска и преобразования — внутреннее состояние новой модели; они не записываются вместо исходных значений.

Источник результата остаётся прежним: объединение полных серверных интервалов Start/Resume → Pause/Finish. Явные паузы исключаются; ожидание при включённом таймере входит в PLAN_ACTIVE. Изменять таймеры, условия пригодности, исходные требования и смысл actualMs не требуется.

Один план даёт один текущий обучающий пример и не более одной единицы нового опыта. Latest выбирается среди всех версий, затем применяется eligibility. Повторяющиеся реальные задачи не удаляются и не получают изменённый вес. Для интерпретации качества отдельно показывается число групп одинаковых шести основных признаков; этот показатель не становится десятым признаком и не меняет обучение.

### 2.2. Численный контракт двух обучаемых ветвей

**OLS:** выделить существующий agent-v2 в явно именованные fitAtlmOls/predictAtlmOls и независимые OLS-константы версии. Сохранить прежние преобразования identity/log/sqrt, reference-кодирование категорий, численные результаты и явные причины отказа. Условия n>=p и полного ранга относятся только к этой ветви. Существующие проверки OLS не превращать в проверки ridge посредством замены ожиданий. Функции проверки протокола 1 должны вызывать именно fitAtlmOls/predictAtlmOls и возвращать прежний method, независимо от переключения текущего метода приложения.

**Ridge:** отдельные fitAtlmRidge/predictAtlmRidge. Используются те же девять входов и правило выбора identity/log/sqrt на обучающей истории. Заранее установленная политика первой версии:

- Функция потерь: средний квадрат ошибки преобразованного времени плюс lambda × сумма квадратов коэффициентов поправок. Свободный член не штрафуется.
- lambda=1. Нормирование ошибки на n обязательно: lambda не должна менять смысл только из-за числа планов.
- Не подбирать lambda по всей проверяемой истории и не добавлять в эту реализацию автоматический подбор сетки. Исследование не подтвердило устойчивое преимущество такого усложнения. Другая lambda/подбор требуют новой версии политики и новой проверки целого гибрида.
- Все наблюдавшиеся уровни каждой категории представлены столбцами, включая неизвестный уровень runtime, если он наблюдался. Ridge устраняет вычислительную неоднозначность полного кодирования. Переименование/перестановка уровней не должно менять прогноз при согласованном преобразовании артефакта.
- Числовые столбцы после преобразования центрируются и делятся на стандартное отклонение обучающей истории с делителем n. Для постоянного столбца масштаб равен 1, центрированный обучающий столбец равен 0. Категориальные индикаторы не делить на их частотное стандартное отклонение.
- plannedParallelAgents сначала обрабатывается по 2.3; масштаб числового отклонения вычисляется на обучающем столбце. Параметры заново вычисляются при каждом обучении/проверочном префиксе.
- Решать через QR расширенной системы с диагональным штрафом sqrt(n×lambda) для поправок; не вычислять обратную матрицу X'X. Дополнительные строки — математическое представление штрафа, не обучающие планы; n, manifest и actualMs их не включают.
- Исходный ранг вычислять корректно и при n<p, отдельно от ранга расширенной системы. Зависимость исходных столбцов диагностируется и не запрещает ridge. На текущем снимке полное кодирование добавит столбцы; не требовать от ridge именно p=22.
- Обратное преобразование, округление до целых ms и проверки конечного неотрицательного безопасного числа сохраняются. Не превращать отрицательное/NaN в нулевой прогноз. Нулевой измеренный факт допустим; log для нуля не выбирать, скрытое +1 не добавлять.
- Ресурсные пределы — 5000 реальных обучающих строк и 64 столбца каждой ветви. Нет скрытого усечения, удаления категорий, выбора удобного поднабора или внешнего ML-сервиса. Отказ одной ветви не запрещает другую, если та укладывается в ограничения.

Все обучающие строки и артефакты детерминированы, не мутируют входные объекты, используют устойчивый порядок и сохраняют digest/manifest.

### 2.3. Неизвестные значения

Первые шесть обязательных признаков сохраняют существующие проверки полноты. Неизвестные modelId, reasoningEffort и plannedParallelAgents допустимы независимо друг от друга.

- null/отсутствующее поле modelId или reasoningEffort — наблюдаемый неизвестный уровень. Новая непредставленная runtime-категория использует неизвестный уровень, если он был; иначе — взвешенное обучающими частотами представление известных уровней до обратного преобразования времени.
- Неизвестное plannedParallelAgents даёт нулевое отклонение от среднего преобразованных известных значений и отдельный индикатор пропуска. Если известных значений нет — отклонение и соответствующий коэффициент равны нулю. Константность не означает удаление исходного признака.
- Новая обязательная категория workKind/reuseState/doneBoundary остаётся UNSUPPORTED_CATEGORY для обучаемой ветви. Не угадывать её эффект. Применяется разрешённая цепочка запасных методов.
- Не подменять null нулём исполнителей, названием предполагаемой модели или уровнем размышлений по умолчанию.

### 2.4. Политика выбора и прогнозирования

Названия: новый метод `{id:"atlm",version:"agent-v3-hybrid"}`, `policyVersion:1`; вход AgentTaskV1 и `predictionRequest:{method:"ATLM",methodVersion:1}` остаются прежними. featureSchemaVersion остаётся agent-task-v2, поскольку состав девяти исходных признаков не меняется; кодирование и решатели версионируются в артефакте.

На момент T применяется одна серверная процедура выбора, без LLM и клиентских весов:

1. Получить допустимую историю на T и до 20 последних проверочных случаев с уже доступными фактами. Полнота времени и исходные признаки проверяемого плана не используются для настройки его собственного прогноза.
2. Для каждого случая q рассчитать OLS и ridge(lambda=1) только на истории до q по 2.5. Сохранить собственные результаты обеих ветвей и медиану того же префикса. Для сравнения стратегий применить точные цепочки: OLS → ridge → медиана и ridge → медиана.
3. Сравнивать среднюю абсолютную ошибку в ms на одном наборе случаев, где доступна медиана. Учитывать ошибки запасных прогнозов. Случай без более раннего факта не превращать в нулевой прогноз и одинаково исключать из расчёта ошибок всех стратегий.
4. Обучаемая ветвь участвует в подтверждённом выборе, если сейчас успешно обучается и имеет минимум пять собственных исторических прогнозов, сравнимых с медианой. Для OLS считаются именно собственные OLS-прогнозы, а не его подстраховка ridge. Пять — минимальный технический порог, не доказательство независимости или будущей точности.
5. Среди допущенных стратегий и медианы выбрать меньшую ошибку. Разница не более 1 ms средней ошибки считается равенством. Сначала определяется общий минимум; среди вариантов в пределах 1 ms от него порядок предпочтения: медиана, ridge, OLS. Порядок фиксирован и не подбирается на текущем снимке.
6. Пока ни одна обучаемая ветвь не набрала пяти собственных сравнений, первой экспериментальной ветвью служит доступный ridge, затем доступный OLS, затем медиана. Качество помечается EXPERIMENTAL. Это сохраняет нынешнюю возможность ранней математически корректной модели без заявления о проверенной полезности.
7. Если выбран OLS, прогнозировать по OLS, при расчётной неприменимости его прогноза — по сохранённому ridge, затем по медиане. Если выбран ridge — ridge, затем медиана. Сам по себе успешный OLS не переключает метод, выбранный по прошлым ошибкам.

Прогнозирование не переобучает модель и не меняет её выбор. Медиана вычисляется существующим read-only механизмом по актуальным допустимым фактам владельца; historical-median/version1, modelId=null и HISTORICAL_BASELINE остаются явно отличимыми от обученной ATLM.

Если на этапе выбора предпочтительна медиана, новый обученный кандидат не активировать: записать отклонённую попытку с диагностикой MEDIAN_BASELINE_NOT_WORSE и результатами обеих ветвей. При отсутствии применимой активной модели вернуть медиану. Уже действующая пригодная модель сохраняется по существующему правилу защиты incumbent; не удалять и не переключать её только из-за отказа нового кандидата.

Сбой источника, авторизации, БД, повреждённый артефакт и превышение общего предела данных остаются ошибками/явными отказами своего контракта. Их нельзя выдавать за успешно рассчитанную медиану. Расчётный INVALID_PREDICTION от проверенного корректного артефакта после исчерпания разрешённых ветвей допускает явно обозначенную медиану; INVALID_ARTIFACT/INVALID_FEATURES/SOURCE_UNAVAILABLE — нет. Список canUseHistoricalMedian обновить именно под это различие и MEDIAN_BASELINE_NOT_WORSE. При модельном пределе обеих ветвей сохранить существующую явную ресурсную диагностику, не обходить её скрытым запасным расчётом.

Примеры приёмки:

| Состояние | Действие | Ожидаемый результат |
| --- | --- | --- |
| OLS имеет недостаточный ранг; ridge рассчитан | Получить прогноз до старта | Ridge либо явно обозначенная медиана по правилам качества; все девять признаков сохранены |
| OLS рассчитан, но на прошлых случаях хуже ridge | Получить прогноз | Ridge; полный ранг не даёт приоритета OLS |
| OLS рассчитан, имеет >=5 собственных сравнений и лучшую ошибку | Обучить локального кандидата и получить прогноз | Выбор OLS после проверки целой политики и защиты incumbent |
| Небольшая история, нет подтверждённых сравнений | Получить первую оценку | Математически корректный ridge/OLS с EXPERIMENTAL либо медиана; нет ложного подтверждения качества |
| Медиана не хуже обучаемых стратегий; активной модели нет | Завершить локальную попытку | Кандидат не активирован; пользователю доступна historical-median |
| Выбранный OLS даёт расчётно некорректную точку, ridge применим | Получить прогноз | Ridge с указанием фактически использованного решателя |
| Не встречалась обязательная категория | Получить прогноз | Без угадывания категории; явная медиана, если её разрешает текущий контракт |
| Повреждён artifact_json или недоступна БД | Получить прогноз | Ошибка источника с существующими requestId/retryable; не успешный fallback |
| План уже RUNNING/PAUSED/COMPLETED | Прочитать сохранённую оценку | Прежний frozen-прогноз без пересчёта и смены метода |

### 2.5. Хронологическая проверка целого гибрида

Версия протокола — 2; протокол 1 сохраняется для воспроизведения прежних результатов. Времена capturedAt и sourceAvailableAt сохранённых строк не переписываются.

Для прогноза q доступны только версии примеров с observedAt<q.capturedAt. Сначала выбрать последнюю доступную версию каждого плана среди всех статусов, затем применить eligibility и sourceAvailableAt<q.capturedAt. Текущий planId исключить. Равенство границе означает недоступность. Такое же правило действует для внутренних сравнений при выборе решателя. Параллельно запущенный сосед без готового факта не является обучающим примером.

Нельзя брать нынешнюю последнюю версию строки и выдавать её за доступную в прошлом. Для протокола 2 сервер использует существующий неизменяемый журнал estimation_samples, а локальный CLI — полный журнал одного экспортного снимка. Исторические версии допустимы в проверочном префиксе, но окончательное обучение использует только актуальные пригодные версии на T.

Для каждого внешнего проверочного случая q выполнить всю процедуру выбора из 2.4 на более ранней истории, затем сохранить её прогноз. Реальный результат q применяется только после этого для расчёта ошибки. Выбирать лучшую ветвь по её ошибке на q или выбирать победителя по всему внешнему окну и объявлять эти же ошибки независимой проверкой запрещено.

Внутренние таблицы сравнения ограничены 20 предыдущими допустимыми случаями. Повторно используемые расчёты кэшируются по префиксу/digest, решателю и версии политики. Кэш одного cutoff не используется для другого набора фактов. Не вводить рекурсивное обучение модели внутри самой процедуры обучения: внутреннее сравнение работает с результатами двух фиксированных базовых решателей.

Отчёт сохраняет:

- до 20 внешних случаев; число доступных/пропущенных, причины отказов;
- MAE полного доставленного прогноза и медианы на одинаковых случаях;
- собственное покрытие OLS/ridge и число реально использованных обученных прогнозов гибрида;
- прежние paired-метрики как отдельные диагностические данные;
- выбранные/использованные решатели, policyVersion, cutoff, digest источников;
- число групп одинаковых основных признаков и пояснение ограниченности похожих серий.

Для совместимости cases сохраняют поля atlm и median: atlm содержит собственный обученный прогноз либо UNAVAILABLE; отдельное prediction содержит окончательный результат с подстраховкой. metrics.atlm остаётся метрикой собственных прогнозов, metrics.operational добавляет метрику всей политики. paired не включает случай, где фактически использована только медиана. candidateReady/qualityConfirmed нового протокола определяются ошибкой всей политики, минимумом пяти внешних обученных прогнозов и сохранённым сравнением с incumbent, а не минимумом из ошибок отдельных решателей.

Публичная evaluation нового метода получает metricsScope="FULL_POLICY", caseCount полного сравнения, modelCaseCount, coverage собственных прогнозов, operationalCoverage и сравнимые maeMs/medianBaselineMaeMs. Старые оценки протокола 1 читаются в прежнем смысле; их paired-ошибку не переименовывать задним числом в ошибку всей политики.

При K<5 сохраняется только экспериментальная ранняя активация, если нет пригодной подтверждённой модели. Подтверждённый incumbent не заменяется экспериментальным. При достаточной проверке худшая целая политика отклоняется; действующая пригодная модель сохраняется. Сравнение с incumbent использует предусмотренные существующим кодом минимум пять новых, не входивших в его обучение случаев и сопоставимое покрытие.

Это проверка алгоритма при обучении на доступном префиксе перед задачей. Она не воспроизводит точное расписание очереди через каждые два плана. Ошибки реально выданных frozen-прогнозов учитываются отдельно по 2.7; только они отражают фактическую задержку обновления рабочей модели.

### 2.6. Артефакт, совместимость и очередь

Новый верхний артефакт: formatVersion=2, kind=HYBRID, method=atlm/agent-v3-hybrid, featureSchemaVersion=agent-task-v2, metric=PLAN_ACTIVE, policyVersion=1, selectedEngine=OLS|RIDGE, общий n/manifest/datasetDigest/trainCutoff, блок selection с причиной/сводкой прошлых сравнений и candidates с состоянием, диагностикой и доступными неизменяемыми артефактами ветвей. Вложенный ridge-артефакт имеет formatVersion=1, kind=RIDGE, внутренний method=atlm-ridge/1; он отдельно хранит lambda=1, objective="mean-square-plus-l2", полное кодирование, частоты уровней, центры/масштабы, неизвестные значения, преобразования, коэффициенты и версию QR-решателя. Вложенный OLS сохраняет исходный formatVersion=1/method=atlm/agent-v2 без обязательного kind. Приватные подробные случаи остаются в metrics_json, а не в публичной диагностике.

Схему артефакта валидировать строго по kind/version. Ограничение rank=p и residualDegreesOfFreedom=n-p сохраняется только для старого OLS. В ridge исходный rank может быть меньше p, а n меньше p; n-p не обозначает оценённую неопределённость ridge. Не публиковать доверительные интервалы, P50/P80 или новые обещания точности.

Поддержать чтение корректных agent-v2/agent-task-v2 артефактов отдельным OLS-декодером до замены новым кандидатом. Обновить SQL выбора activeModel и защитные предикаты согласованно: нельзя разрешить чтение v2, но запретить его подтверждение в CAS, либо наоборот. Исходные прогнозы любых сохранённых версий остаются читаемыми как frozen-значения; их не пересчитывать новым кодом.

Новые артефакты и метрики помещаются в существующие JSON-поля estimation_models и estimation_jobs. Новые таблицы, столбцы и миграции D1 не требуются. Старые SQL, snapshots, artifact_json, manifest и metrics_json не переписываются.

Сохранить поколения, lease=60 s, fencing token, ограниченный проход до 10 s wall time, задержки повторов, порог двух новых уникальных пригодных планов и ручной запуск. Расчёт внутренних/внешних случаев разбить на возобновляемые единицы, сохраняя progressRevision и компактные результаты в checkpoint_json. Не хранить копию всех матриц или полный артефакт каждого префикса в checkpoint.

Snapshot фиксирует два разных набора: trainingManifest актуальных пригодных источников для итоговой модели и ссылки на неизменяемые исторические версии, использованные при проверке. Для всего исторического чтения фиксируются asOf и historyThroughSequence; при возобновлении новые строки за этой границей не добавляются. Для компактности допустимы граница журнала и cutoff отдельных единиц вместо повторения всех префиксных manifest. Старые исторические ссылки не обязаны быть текущими ELIGIBLE на момент активации; их нельзя проверять предикатом актуальности trainingManifest. Актуальность итоговых обучающих источников, отсутствие dirty refresh, поколение и fence проверяются при активации как прежде. Исходный snapshot и его временные границы не должны расширяться при возобновлении. Старый несовместимый checkpoint не интерпретировать как новый протокол: пересоздать вычисление под существующей защитой поколения/владения, без двойного учёта опыта.

Во время расчёта не блокировать FinishPlan и не изменять остальные планы. Успех записи времени не зависит от успеха фонового обучения. Read-only получение прогноза не запускает очередь.

### 2.8. Проверки, данные и режим Git

Использовать правила плагинов software-engineering:write-implementation-plan, analyze-change, verify-change и ci-cd. Готовое исследование переиспользовать. Не проводить новый общий аудит и не вводить новые службы, зависимости времени выполнения или механизм публикации.

Для нового поведения — значимый падающий тест/точное воспроизведение, затем исправление и тот же успешный тест. Для выделения неизменяемого OLS — сохранение прежних численных ожиданий без искусственного RED. Для документации RED не требуется. Предстоящие проверки не объявлять уже выполненными.

Не придумывать новые обучающие планы и длительности. Постоянные численные/контрактные тесты переиспользуют существующие фикстуры проекта и управляемые ответы решателей. Метрики реальной полезности считаются только на частной копии фактической истории. Частные JSON, названия/ID планов и исходные данные владельца в Git не включать. Одноразовую диагностику хранить вне репозитория, например в /tmp/atlm-hybrid-verification; текущие материалы исследования находятся в /workspace/scratch/atlm-research и не являются частью поставки.

Проверки новых ветвей выбора могут управлять ответами решателей на существующих фикстурах, когда реальная история не содержит нужного состояния. Это проверяет переключение, а не реальную точность OLS. Не выдавать такой тест за подтверждение полезности на владельческой истории. Отсутствие пяти реальных пригодных OLS-сравнений не компенсировать выдуманными фактами.

Правила ограниченного выполнения:

- По умолчанию один запуск выполняет один назначенный этап. Поручение реализовать весь этот план охватывает H1–H5 последовательно без подтверждения между внутренними действиями. При действительно неясном назначении уточнить этап до изменений; само чтение общего описания не разрешает реализацию.
- Действия назначенного этапа выполнить до его конца, включая RED→GREEN и проверки. Тесты этапа не должны требовать реализации последующих этапов.
- Локальные детали можно адаптировать без изменения зафиксированных контрактов. Изменение бизнес-правила, публичного контракта, данных, зависимостей или области требует пересмотра относящейся части плана. Новый HEAD или несвязанные изменения сами по себе не блокируют выполнение.
- При продолжении сопоставить фактическое состояние с началом/концом этапа. Готовое проверить, частичное продолжить, повторных файлов/пустых коммитов не создавать. Сохранять имена и пути из плана.
- Все этапы последовательно меняют worker/index.js, поэтому назначен один исполнитель и владелец общего индекса. Самостоятельное параллельное редактирование этого файла не предусмотрено. При отдельно порученной параллельной работе — отдельные рабочие копии либо один владелец индекса и сведения изменений.
- В будущем выполнении режим фиксации — только добавление собственных изменений законченного этапа в индекс, без коммитов: пользователь коммиты не поручал. Смешанные файлы добавлять по своим фрагментам; `git add .`/`git add -A` запрещены. Не очищать чужой индекс, учитывать накопленные изменения своих предыдущих этапов. Если коммиты будут отдельно поручены, один локальный коммит законченного этапа объединяет его код, постоянные тесты и нужные контракты после проверок.
- Коммит не разрешает следующий этап, push, PR, публикацию или запуск рабочего обучения. Текущая подготовка плана не добавляет в индекс даже файл плана.

Критерии ниже относятся ко всей задаче. Локальный успех H1 не подтверждает очередь, интерфейс и итоговый артефакт.

| ID | Критерий | Подтверждение |
| --- | --- | --- |
| A01 | Все девять исходных признаков и допустимость независимых runtime-пропусков сохранены | H1 kernel + H3 public-path tests; сравнение сохранённых JSON |
| A02 | Результат обучения — полный actualMs без явных пауз, прогноз его не подменяет | H3 source/storage/lifecycle; реальная копия |
| A03 | OLS сохраняет прежний численный контракт, ridge работает при зависимости и n<p | H1 эталоны и новый kernel; локальное воспроизведение исследованной блокировки |
| A04 | Масштабы, категории, константы, unknown и домены преобразований корректны и сериализуются | H1, перенос артефакта в H3 |
| A05 | Выбор учитывает ошибки; полный ранг не даёт приоритета OLS; tie/минимум сравнений определены | H2 policy tests; H3 активация |
| A06 | Весь гибрид проверен без будущих фактов/версий/результатов и с реальной временной доступностью параллельных задач | H2 протокол 2 + H3 журнал/as-of snapshot |
| A07 | Сравнение с медианой использует одинаковые случаи и ошибки подстраховки; покрытие не скрыто | H2 метрики + итоговый реальный отчёт H5 |
| A08 | Никакого обещания улучшения; при худшем кандидате срабатывают медиана/защита incumbent | H2/H3 отказ и UI H4; документация H5 |
| A09 | Следующий факт попадает в следующее полное обучение; версии одного плана не создают новый опыт | H3 очередь/счётчики/latest-before-eligibility |
| A10 | Legacy-модель и прежние frozen-прогнозы читаются без переписывания | H3 old/new artifacts, CAS и digest/readback |
| A11 | Технические ошибки не маскируются запасным числом; изоляция owner сохранена | H3 MCP/HTTP/error tests |
| A12 | Lease/fence/checkpoints и активация сохраняют целостность при прерывании/конкуренции | H3 управляемые отказы и возобновление |
| A13 | Новые issuedPrediction различают заранее выданный прогноз и факт, включая медиану | H3 storage/readback; старые строки не изменены |
| A14 | UI показывает фактически использованный метод, experimental/confirmed и подходящую ошибку | H4 браузер исходного и собранного Worker |
| A15 | Код, инструкции, документация и CLI описывают один контракт | H5 чтение/ссылки/plugin tests |
| A16 | Штатные общие проверки и запуск итогового артефакта завершены; ограничения честно перечислены | H5 npm test/validate/test:ui/plugin/built-UI + verification.md |
| A17 | Нет удаления признаков, выдуманных фактов, частных данных в Git, новых продовых записей или публикации | H3 immutability + H5 diff/index/read-only отчёт |

Для текущего реального набора достаточным результатом является устранение вычислительной блокировки через ridge с честной оценкой полезности и корректным запасным вариантом. Достижение заданной меньшей MAE, активация на рабочем сервере и доказанное превосходство на будущих задачах не являются выдуманными условиями приёмки. Будущая полезность подтверждается новыми реальными результатами, а не заполнением трекера тестовыми планами.
