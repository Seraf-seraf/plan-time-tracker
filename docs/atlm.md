# ATLM: прогноз активного времени

ATLM прогнозирует `PLAN_ACTIVE`: полное время рабочих интервалов плана без пауз, начиная с первого StartPlan. Это не календарный срок и не сумма времени параллельных исполнителей. До запуска GetSavedEstimate читает текущий прогноз без записи; первый StartPlan атомарно фиксирует его. После запуска показывается сохранённый снимок и признак устаревания при изменении источника.

До начала работы заполните признаки по схеме `agent-task-v4`. Полную схему с вложенными полями, допустимыми значениями и ограничениями возвращает `GetTrackerInfo` в `assessments.atlm.agentTaskSchema`. Её используют оба входа, `EstimatePlanTime.agentTask` и `SaveTaskAssessment.payload.context.agentTask`. Если клиент сокращает объявление инструмента, читайте сам ответ `GetTrackerInfo`. [Справочник признаков и примеры](../plugin/plan-time-tracker/skills/assess-task/references/features.md).

Сервер рассчитывает счётчики и долю операций WRITE, кодирует категории и отличает неизвестные значения от подтверждённых нулей. Интерфейс показывает названия признаков, их значения и сохранённые причины неизвестности. Для первого `StartPlan` требуется оценка со статусом `READY`. Снимок может содержать доступный прогноз или `UNAVAILABLE`, если данных для него недостаточно. [Запись оценки и проверка готовности](assessments.md).

## Расчёт

Метод `atlm/agent-v5-operations` использует преобразование `log1p(actualMs / 60000)` и сравнивает OLS, Ridge и Bayesian с исторической медианой. Ridge и Bayesian могут работать при числе признаков не меньше числа наблюдений; OLS требует полного ранга. Точечный метод выбирается отдельно от интервального. При нулевой истории прогноза нет; при одном пригодном плане возвращается `historical-median` без интервала. Начиная с двух примеров возможен экспериментальный прогноз модели.

Bayesian использует normal-inverse-gamma и прогнозное распределение Student-t с фиксированными приорами: precision 1 для стандартизованных коэффициентов и 0,000001 для свободного члена, shape 2, scale 1. `BAYESIAN_PREDICTIVE` выдаёт квантили 0,10 и 0,90. `BAYES_QUANTILE` обучает регуляризованные квантильные регрессии 0,10/0,50/0,90 на стандартизованных остатках исторического Bayesian; для каждого остатка и преобразования признаков используются только факты, доступные до начала задачи. Нужно не менее пяти таких остатков. Пересечённые квантили упорядочиваются, а границы расширяются до выбранной точки.

В `serverEstimation` находятся `pointMs`, `pointEngine` и `interval` с `status`, `lowerMs`, `upperMs`, `nominalCoverage`, `engine`, `calibrationSampleCount`, `validationStatus`, `unavailableReason`. При недоступном диапазоне границы null и указана причина. Номинальный охват 0,80 — цель, а не гарантия будущего результата. EXPERIMENTAL и HISTORICALLY_EVALUATED описывают наличие исторической проверки, а не обещание точности.

## Обучение по запросу

Worker собирает сведения о планах и измерения `PLAN_ACTIVE`. Обучение запускает агент по поручению пользователя. Ему нужны подключённый MCP с авторизацией владельца, code-mode с прямой передачей файлов, checkout проекта и Node.js 24. Схемы шести операций версии 1 и лимиты возвращают `GetTrackerInfo.assessments.atlm.registry` и `tools/list`. Рецепт по умолчанию возвращает `registry.defaultTeacherRecipeId`. Перед новой разметкой и регистрацией проверьте, что `registry.teacherRecipeIds` содержит `atlm-teacher-hybrid-v2`. [Инструкция для агента](../plugin/plan-time-tracker/skills/train-model/SKILL.md).

1. Для новой подготовки датасета вызовите `CreateTrainingSnapshot` в `mode:'create'` с новым UUID команды. Сохранённый `snapshotId` используйте при возобновлении той же подготовки. Команда фиксирует исходную оценку, прогноз первого старта, факт, поколения источников и доказательства. В снимок входят незавершённые и удалённые планы, исключения и источники со сбоем. При `SOURCES_PENDING` ограниченно повторяйте тот же запрос после `details.retryAfterMs`, если указан интервал.
2. Разметьте все строки. Исходные признаки `PLANNED` отражают сведения до первого старта. Для каждого признака `ACTUAL` укажите подтверждение по итоговому коду или другим материалам выполнения конкретного плана. Расхождения с `PLANNED` исправляйте в `annotation.agentTask`. Для `ELIGIBLE` нужны проверенный источник, аннотация `ACTUAL` и `reasons:[]`. Укажите `groupId:null`. Для `EXCLUDED` укажите хотя бы одну конкретную причину. Причины — строки печатного ASCII до 128 символов, каждая содержит хотя бы один непробельный символ. Проверьте прежние исключения по первичным записям и получите свежий снимок, если источники удалось исправить. В актуальном снимке неполное измерение, удаление, отсутствие завершения и терминальный сбой источника исключают строку из обучения. Изменившийся объём допускает новую разметку при подтверждённом факте. Для восстановленных фактических признаков укажите дату доступности и подтверждение в `annotation.historicalAvailability`. Измеренный ноль допустим. [Формат и примеры разметки](../plugin/plan-time-tracker/skills/train-model/SKILL.md#снимок-и-преподавательская-разметка).
3. `SaveDatasetRevision` сохраняет полный набор решений и добавляет серверные поля. Ранее проверенную аннотацию можно перенести из родительской ревизии, если в обеих строках известны и попарно совпадают `planId`, `source.sourceGeneration` и `source.sourceDigest`. Иначе заново проверьте признаки и обновите доказательства. Выгрузите сохранённую ревизию через `GetDatasetRevision` и сверьте `datasetDigest` с SHA-256 файла.
4. Локально запишите рецепт и выполните `train-atlm.mjs`. Сверьте `manifest.json` (`provenance.fitRowIds`) и манифест артефакта со списком всех `ELIGIBLE` строк по ID. При порученной регистрации передайте `registration.bundle.json` через `RegisterModelRevision`. Результат `REGISTERED` сохраняет выпуск и проверку. Указатель публикации меняется через `ActivateModelRevision`.

### Диагностика и восстановление

`rawEligibility`, `rawReasons` и `source.actualMs` описывают сведения трекера в снимке. `eligibility` и `reasons` в ревизии датасета описывают решение учителя. Сравнивайте решения по `planId`. Старое учительское `INCOMPLETE_MEASUREMENT` перепроверьте по текущему наблюдению и первичным записям. Явный `USER_REQUESTED_SKIP` сохраняйте по `planId` на основе истории нативных ревизий, включая ревизии вне текущей цепочки. Меняйте его по подтверждённому указанию пользователя.

Для завершённого неудалённого плана с `SOURCE_NOT_OBSERVED` или `SOURCE_REFRESH_FAILED` прочитайте `source.refreshError`, интервалы и события завершения. `CreateTrainingSnapshot` в `mode:'repair'` принимает `commandId` и до 25 уникальных `planIds` владельца. Команда идемпотентно ставит отсутствующие и сбойные наблюдения в очередь. `mode:'create'` обрабатывает очередь и фиксирует актуальные строки в новом снимке. Проверяйте результат восстановления по этому снимку и учитывайте причины по каждому плану. В отчёте подготовки укажите ID и дату снимка, ID датасета, число пригодных, исключённых и восстановленных планов и список нерешённых строк с причинами. [Порядок восстановления](../plugin/plan-time-tracker/skills/train-model/SKILL.md#восстановить-наблюдения).

### Файлы и восстановление

Снимки, ревизии и отчёты выгружаются по неизменяемому ID. `view:'rows'` у снимка и датасета возвращает компактный перечень. Полный файл со строками и доказательствами подготовьте через `view:'download'`. При выгрузке модели и чтении её частей передавайте один и тот же `fileKind`. `BUNDLE` используется по умолчанию, `ARTIFACT` выдаёт артефакт без остальных файлов пакета.

Для загрузки возьмите новый `commandId` и подготовьте `file:{sha256,byteLength}` через `atlm-transfer.mjs manifest`. На всех фазах сохраняйте эти аргументы, а также `snapshotId` и `parentDatasetRevisionId` для `SaveDatasetRevision` или `datasetRevisionId` для `RegisterModelRevision`.

- **Отправить недостающие части.** После `prepare` при `UPLOADING` пропустите диапазоны `receivedPartRanges` и передайте остальные части через `putPart`, затем вызовите `commit`. При `UPLOAD_INCOMPLETE` или `UPLOAD_EXPIRED` повторите `prepare` с исходными аргументами. Отправьте части, отсутствующие в новом `receivedPartRanges`, и повторите `commit`. Полная часть содержит 49 152 байта, лимит загрузки 16 МиБ. В code-mode передавайте base64 из `atlm-transfer.mjs read-part` в `putPart` после проверки длины. Для вывода helper задайте `max_output_tokens:80000`. Пользователю выводите метаданные и прогресс.
- **Повторить запрос.** При `MATERIALIZING` повторите `download`, при `VALIDATING` повторите `commit` с теми же аргументами. Дождитесь `retryAfterMs` в обоих случаях. При потере ответа на запись читайте `GetCommandResult` с исходным `commandId`. При `FINAL` используйте `result` или `error`, при `PENDING` или `NOT_FOUND` точно повторите запрос по сохранённым локально аргументам. Подтверждённый отказ содержимого может оставить квитанцию в `PENDING`. Для исправленного файла вычислите новый manifest и используйте новый `commandId`.
- **Забрать готовый результат.** При `READY` прочитайте части через `view:'filePart'` по `partIndex` и запишите их по позиции через `atlm-transfer.mjs write-part` в `.partial`. После проверки длины и SHA-256 через `verify` переименуйте файл. При `SAVED` для датасета или `REGISTERED` для модели сохраните ID ревизии. После успешного commit любая из трёх фаз при точном повторе возвращает итог с `replayed:true`. [Команды переноса и возобновления](../plugin/plan-time-tracker/skills/train-model/SKILL.md#передача-файлов).

### Рецепт локального запуска

В `recipe.json` задайте поля рецепта, подставив ID ревизии и digest полного экспорта.

```json
{
  "schemaVersion": 1,
  "recipeId": "atlm-teacher-hybrid-v2",
  "datasetRevisionId": "ID из GetDatasetRevision",
  "datasetDigest": "sha256:SHA-256 исходных байтов",
  "selection": { "mode": "ALL_ELIGIBLE" },
  "backtestUse": "UNKNOWN",
  "backtestUseNote": "История просмотра результатов неизвестна"
}
```

В v2 `ALL_ELIGIBLE` — единственный режим. Используйте `FIRST_REPORTED` при известной первой проверке и `REUSED_AFTER_REVIEW`, если результаты по той же истории уже видели. Идентичный запуск воспроизводит результат.

```sh
cd sites/plan-time-tracker
node scripts/train-atlm.mjs --dataset /path/dataset.json --recipe /path/recipe.json --out /path/run
```

Каталог результата содержит `run.json` с версиями, digest и диагностикой, `manifest.json` с составом выборки и `evaluation.json` с режимами проверки. Код выхода `0` означает готовые `artifact.json` и `registration.bundle.json`, `2` — сохранённый отчёт о недоступном кандидате, `1` — ошибку входа или исполнения. Повтор проверяет digest выходов и переиспользует полный результат с теми же входами. Каталог публикуется атомарно. Признаки и строки сохраняются полностью, в том числе при отказе solver по пределам ресурсов. Артефакт HYBRID хранит веса, число строк и дайджест финального состава. Реестр сверяет его с полным набором пригодных строк в сохранённой ревизии датасета.

## Как читать оценку качества

Финальные веса v2 рассчитываются на всех подтверждённых строках. Один пригодный завершённый и не удалённый план даёт одну строку. Каждый исторический кейс использует только другие планы, доступные строго до первого старта проверяемого плана. Порядок дней недели, похожесть задач и пересечение интервалов не влияют на финальный состав.

Для восстановленных признаков укажите `annotation.historicalAvailability:{availableAt,evidence}`. Эффективная дата доступности примера — более поздняя из `sourceAvailableAt` и даты подтверждения. При явно неизвестной дате подтверждения строка остаётся в финальном наборе, а историческая проверка пропускает её как источник. Если отдельного подтверждения нет, дата источника достаточна для подтверждённых исходных признаков при неизменном объёме. Для восстановленных значений безопасной границей служит время сохранения аннотации, если оно доступно.

| Режим | Что проверяет |
| --- | --- |
| `ROLLING_PLAN_ACTUAL` | Прогноз по фактическим признакам и истории, доступной до старта конкретного плана. |
| `ROLLING_PLAN_PLANNED` | Прогноз по исходным признакам в той же истории. Ошибка учитывается при подтверждённом неизменном объёме. |
| `ISSUED_FORECASTS` | Сохранённые до первого старта прогнозы из снимка. Возможны выдачи прежних ревизий, историческая медиана и планы без доступного прогноза. |

Точечный метод и интервал выбираются отдельно по предыдущим доступным историческим случаям. Пропуск исходных признаков исключает пару из плановой проверки. Подтверждённая фактическая строка остаётся в финальном наборе.

Ошибки считаются только на сопоставимых фактах. `forecastRate` и `intervalAvailabilityRate` измеряют доступность точки и интервала. `intervalCoverage` показывает долю фактов внутри доступного интервала. MAE, MedAE, смещение, ширина и interval score считаются в миллисекундах, WAPE — в процентах. Ошибка со знаком равна прогнозу минус факт. Парное сравнение использует одни и те же строки для кандидата и медианы. Широкие интервалы могут давать высокий охват, поэтому учитывайте охват вместе с шириной и interval score.

В v2 исторические точки регрессии вычисляет локальный тренер. Реестр сверяет состав каждого среза, медиану, сравнимость и сводные числа. Источником немедианных точек остаётся отчёт из пакета владельца. Для воспроизведения этих точек используйте сохранённые исходники, рецепт и выдержку датасета с теми же дайджестами.

В разделе «Модель прогноза» источник «Контрольная проверка» показывает сохранённый отчёт о процедуре обучения и выдачи из исходного снимка. Источник «Выданные прогнозы» показывает качество уже опубликованной ревизии по мере завершения планов, которым она выдала прогноз. Архивные отчёты рецепта `atlm-teacher-hybrid-v1` сохраняют прежние показатели `ROLLING_GROUPED_ACTUAL`, `INTERNAL_HOLDOUT_ACTUAL` и `INTERNAL_HOLDOUT_PLANNED`.

## Активация и история

Реестр показывает «Выдаёт прогнозы» для ревизии, доступной для новых прогнозов, «Не назначена» для зарегистрированных и ранее использовавшихся ревизий, «Недоступна» с причиной для архивных ревизий и ревизий с нарушенными источниками. Указатель «Назначенная ревизия» может ссылаться на недоступную модель. Отчёты о точности доступны отдельно от статуса ревизии.

Сравните `activeModelRevisionId` и `servingModelRevisionId` в `ListModelRevisions({schemaVersion:1,view:'list'})`. Первый хранит назначение для CAS, второй показывает модель, доступную для новых прогнозов. Для активации передайте `modelRevisionId`, `expectedActiveModelRevisionId`, `expectedActivationVersion`, новый `commandId` и причину. Для допуска v2 нужен доступный `ROLLING_PLAN_PLANNED` с минимум пятью разными сопоставимыми планами. MAE кандидата должна быть не выше MAE медианы на тех же парах. Для v1 сохраняются прежние правила планового holdout и минимального числа групп.

Если регистрация вернула `activationEligibility.status:'REQUIRES_EXPERIMENTAL_ACK'` или активация вернула `EXPERIMENTAL_CONFIRMATION_REQUIRED`, для активации требуется явное согласие пользователя и `acceptExperimental:true`. Это же правило действует при откате. Значение `serverEstimation.accuracy:'EXPERIMENTAL'` в `GetSavedEstimate` описывает проверку прогноза и возможно при `ELIGIBLE`. Неверный артефакт или изменившийся источник блокируют активацию независимо от подтверждения.

Изменение поколения любого использованного источника сразу делает выпуск непригодным для новых прогнозов. Для v1 правило включает источники прежнего HOLDOUT и PURGED. Сохранённый прогноз начатого плана остаётся прежним. Новый план вне выборки и новая ревизия разметки сами по себе не меняют пригодность модели. Для отката выберите прежнюю пригодную ревизию и повторите `ActivateModelRevision` с текущими CAS-значениями. Причина и результат останутся в истории.

Исторические ревизии сохраняют исходные байты артефакта, отчёт и известную историю публикаций. Например, `atlm-11-r2` хранит прежний результат `REJECTED/INSUFFICIENT_INCUMBENT_CASES` рядом с фактом публикации. Неизвестные даты и источники остаются `null`. `BUNDLE` импортированной модели выдаёт архив для аудита. Для нативной модели `BUNDLE` возвращает исходный пакет регистрации. Если обучение по импортированной выгрузке вернуло `HISTORICAL_PROVENANCE_INCOMPLETE`, подготовьте новый нативный снимок с проверенной разметкой.

Если после сброса истории исходный снимок отсутствует, `GetSavedEstimate` возвращает `HISTORY_RESET`. Возобновление начатого плана по-прежнему доступно.
