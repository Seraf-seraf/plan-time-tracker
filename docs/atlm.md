# Прогноз времени агентов по ATLM

ATLM прогнозирует полное активное время плана от первого `StartPlan` до принятого результата. Агент описывает задачу до исполнения; сервер вычисляет прогноз и накапливает пригодные завершённые планы. После каждых двух новых пригодных планов он проверяет новую модель на всей накопленной истории.

Метод: `atlm/agent-v2`, схема обучаемых признаков: `agent-task-v2`, входное описание: `agent-task-v1`, метрика: `PLAN_ACTIVE`, область: `FULL_FROM_FIRST_START`. Подготовка оценки до запуска не входит во время. Ожидание инструментов при RUNNING входит, пользовательские паузы исключены только при записанном `PausePlan`. Параллельные попытки и вызовы инструментов не прибавляются отдельно к интервалам плана. Ошибочные попытки и исправления внутри принятого плана остаются в его времени.

Это условный прогноз по принятым задачам с неизменным объёмом. Он не оценивает вероятность успеха, человеко-часы, расход токенов или остаток работы. Вычитание затраченного времени из первоначальной точки не даёт прогноз остатка.

## Какие сведения задаёт агент

`SaveTaskAssessment.payload.context.agentTask` содержит следующие поля. runtimeContext и его поля необязательны. Неизвестность разрешена при сохранении: категория `UNKNOWN`, список `null`, неизвестные метаданные `null`. Известное отсутствие записывается как пустой список `[]`.

| Поле | Смысл |
| --- | --- |
| `schemaVersion` | `agent-task-v1` |
| `profile.workKind` | CREATE_MECHANISM, MODIFY_MECHANISM, RUN_EXISTING_PROCESS, VERIFY_EXISTING, MIGRATE_DATA, INVESTIGATE, MIXED или UNKNOWN |
| `profile.reuseState` | ABSENT, PARTIAL, READY или UNKNOWN |
| `profile.doneBoundary` | ANALYSIS, LOCAL_VERIFIED, LOCAL_STAGED, PUBLISHED, DEPLOYED_VERIFIED или UNKNOWN |
| `outcomes` | До 20 самостоятельных требуемых результатов: `{id,description,evidence}` |
| `changedContracts` | До 20 меняющихся операций/форматов/схем: `{kind,key,description,evidence}`, kind — API, MCP, EVENT, STORAGE или OTHER |
| `verificationKinds` | Уникальные требуемые виды проверок: BUILD_STATIC, UNIT, INTEGRATION, UI_E2E, DEPLOY_SMOKE |
| `profileEvidence` | Краткие основания для workKind, reuseState и doneBoundary |
| `runtimeContext` | `{modelId,reasoningEffort,environmentId,plannedParallelAgents,provenance}`; provenance — CLIENT_REPORTED или UNKNOWN |

id/key — 1–128 символов; description/evidence и каждое основание профиля — 1–400; строки runtimeContext — до 128. plannedParallelAgents — положительное целое или null. Общий assessment, включая результат сервера, ограничен 24 000 UTF-8 байтами и глубиной JSON 10. Переполнение отклоняется без обрезания.

Сервер сортирует списки и объединяет точные дубли. Разные описания одного ключа отклоняются. Из разных ключей сервер не угадывает, что агент дважды описал один результат: это предотвращает инструкция assess-task. Число шагов, файлов или запусков одного теста не заменяет число результатов и видов проверки. Клиентские outcomeCount/contractCount/verificationKindCount не принимаются: три числа сервер получает из списков. С тремя категориями профиля и тремя runtime-параметрами они образуют девять признаков.

modelId и reasoningEffort — категориальные признаки, plannedParallelAgents — числовой. Отсутствующий runtimeContext, пропущенные поля и null означают неизвестно; пустые строковые значения нормализуются в null, effort — в нижний регистр. Неизвестное количество исполнителей не подменяется нулём или единицей. environmentId и provenance остаются метаданными. Девять признаков — гипотеза для задач агентов. Публикация ATLM не доказывает полезность именно такого набора или точность на этой базе.

## Определения девяти признаков

| Поле | Что учитываем и допустимые варианты |
| --- | --- |
| workKind | Создание нового механизма; изменение существующего; запуск готового процесса; самостоятельная проверка; миграция данных; исследование; смешанная задача. Исправление ошибки, рефакторинг, оптимизация и доработка интерфейса — примеры изменения. Запуск сборки, экспорта, настройки или доставки готовой процедуры — запуск процесса. Диагностика причины, изучение вариантов и проектное решение без реализации — исследование. Смешанный тип применять только при самостоятельных разных результатах. Машинные категории сохраняются: CREATE_MECHANISM, MODIFY_MECHANISM, RUN_EXISTING_PROCESS, VERIFY_EXISTING, MIGRATE_DATA, INVESTIGATE, MIXED. |
| reuseState | ABSENT — необходимой основы нет; PARTIAL — основа есть, требуется разработка/исправление; READY — достаточно готового механизма. Примеры: новый сервис; расширение существующего API; запуск готового переноса. Размер репозитория не заменяет готовность нужного решения. |
| doneBoundary | ANALYSIS — приняты выводы/решение; LOCAL_VERIFIED — локальная реализация с проверками; LOCAL_STAGED — дополнительно подготовлен Git index; PUBLISHED — результат опубликован; DEPLOYED_VERIFIED — развёрнут и проверен. Коммит, публикация кода и проверенное развёртывание различаются. |
| outcomeCount | Число уникальных самостоятельных результатов из outcomes: например экспорт, пагинация, восстановление данных. Технические действия «изменить обработчик», «написать тест», «проверить» не превращаются в дополнительные пользовательские результаты. |
| contractCount | Число уникальных изменяемых контрактов из changedContracts: API-операции, MCP-инструменты, форматы событий, схемы хранения; через OTHER — CLI, конфигурационные форматы, обязательства UI-сценария или взаимодействия сервисов. Косметическая правка сама по себе не считается новым контрактом. Один контракт у нескольких потребителей не удваивается. Машинные kind остаются API/MCP/EVENT/STORAGE/OTHER. |
| verificationKindCount | Число уникальных видов из verificationKinds: BUILD_STATIC — сборка/статика; UNIT — модульные проверки; INTEGRATION — взаимодействие компонентов/данных; UI_E2E — полный пользовательский веб-сценарий; DEPLOY_SMOKE — проверка опубликованного результата. Безопасность, производительность, доступность и миграция могут быть целью этих проверок; в этой версии они не становятся новыми enum или дополнительными признаками. Ручной браузерный проход и автотест различать в свидетельствах, не удваивать один вид проверки за повторы. |
| modelId | Фактически известный идентификатор основной модели агента либо null. Не угадывать из названия чата, качества ответа или выбранного reviewer. Идентификаторы разных моделей не сводить к придуманному баллу скорости/качества. |
| reasoningEffort | Подтверждённое настройкой значение, например none/minimal/low/medium/high/xhigh/max/ultra, либо null. Это открытая строка, а не универсальная числовая шкала между провайдерами. Нормализовать пробелы и регистр, не придумывать значение по умолчанию. |
| plannedParallelAgents | Плановое максимальное число одновременно работающих агентов, включая основного: положительное целое либо null. Один исполнитель без параллельной работы — 1. Последовательные подзадачи, повторные попытки и запущенные процессы не являются дополнительными параллельными агентами. |


## Сохранение исходной оценки

1. Зарегистрировать PLANNED-план и необходимые шаги обычным track-plan.
2. Обнаружить `assessments.atlm` через GetTrackerInfo. Прочитать `GetTaskAssessment({planId})` без assessmentId и сохранить currentRequirementsDigest до анализа.
3. Записать обычный SaveTaskAssessment с context.agentTask и `predictionRequest:{method:"ATLM",methodVersion:1}`. Все прежние обязательные поля assessment сохраняются. predictionRequest разрешён только для целого плана до первого запуска.
4. Сервер сохраняет прогноз в `assessment.serverEstimation`. Это поле нельзя прислать клиентом. Недостаток данных сохраняет признаки и явную причину UNAVAILABLE; ошибка БД остаётся ошибкой протокола.
5. При первом StartPlan триггер в той же транзакции фиксирует последнюю уже записанную подходящую ревизию с совпадающими текущими требованиями. Отсутствие такой ревизии не блокирует запуск, но план не становится обучающим примером.

Поздняя запись, ResumePlan, восстановление и новая ревизия не заменяют исходный снимок. Старые планы без проверяемого исходного снимка не размечаются задним числом. При ASSESSMENT_CONTEXT_CHANGED нужно прочитать требования и пересмотреть описание; нельзя механически подставить свежий digest. Неопределённый результат записи восстанавливается точным повтором commandId или GetCommandReceipt.

Когда ATLM даёт только точку, старый `forecast` остаётся `status:UNKNOWN`, `lowerMs:null`, `upperMs:null`, `confidence:UNKNOWN`. Точка находится в serverEstimation и не превращается в гарантированный интервал. Сложность и выбранный способ решения остаются отдельными полями агента.

## MCP и HTTP

Инструменты объявляются в `assessments.atlm`; поддержка определяется discovery, а не одним номером приложения. Обычные командные конверты сохраняют schemaVersion=1.

| Инструмент | Назначение и HTTP |
| --- | --- |
| EstimatePlanTime | Предпросмотр по активной модели: `{planId,expectedRequirementsDigest,agentTask}`. POST `/api/tracker/atlm-estimate` |
| GetSavedEstimate | Сохранённый прогноз `{planId}`; после запуска возвращается исходный снимок, без создания прогноза задним числом. GET `/api/tracker/plans/:planId/estimate` |
| GetTrainingStatus | `{}`: накопление опыта, действующая модель, очередь и причины недоступности. GET `/api/tracker/estimation-model` |
| StartTraining | `{}`: по просьбе пользователя запросить попытку обучения, не дожидаясь двух новых планов. |
| ContinueTraining | `{}`: один ограниченный идемпотентный проход очереди владельца. POST `/api/tracker/estimation-model/process` |
| GetTrainingData | Приватная выгрузка frozen sample-версий `{limit?,cursor?}`, default 50, max 100. POST `/api/tracker/atlm-dataset` |

ContinueTraining и StartTraining изменяют состояние очереди; StartTraining вызывается только по прямой просьбе пользователя. Чтение не обучает модель. Все пути используют аутентифицированного владельца, не принимают чужие owner/model/sample IDs, заданные клиентом веса, длительности или список предпочитаемых аналогов.

serverEstimation содержит formatVersion=1, metric/forecastScope, status AVAILABLE/UNAVAILABLE, nullable pointMs, method, nullable modelId/modelVersion, серверные requirementsDigest/featureDigest/calculatedAt, sampleCount, evaluation либо null, accuracy HISTORICALLY_EVALUATED/NOT_VALIDATED, interval=null и confidence=UNKNOWN. Точка не обозначается P50/P80. evaluation включает caseCount, coverage, maeMs, medianBaselineMaeMs, cutoff и protocolVersion.

GetSavedEstimate возвращает `{formatVersion:1,planId,assessmentId,assessmentRevision,source,serverEstimation,isStale,staleReasons,serverNow}`. source — FROZEN_INPUT после старта, LATEST_ASSESSMENT до старта либо NONE; отсутствующая оценка явно равна null. Состояние обучения отдельно от сохранённого прогноза: отклонение нового кандидата не скрывает доступную прежнюю оценку. Неполные признаки и отсутствие модели различаются с ошибками авторизации, устаревшим digest, БД и ресурсными отказами; у последних остаётся обычный ошибочный ответ с requestId/retryable.

GetTrainingStatus возвращает datasetRevision, eligibleSampleCount, excludedSampleCount, newPlansSinceTraining, retrainEveryNewPlans, причины исключений, activeModel или null, lastReason/lastError и training. В training находятся status, generation, due, attempts, nextAttemptAt, pendingRefreshCount, progressRevision и progress. Статусы: IDLE, QUEUED, RUNNING, RETRY_WAIT, COLLECTING_DATA, REJECTED, FAILED. `due` означает возможность ограниченного прохода сейчас, включая восстановление примеров; ожидание nextAttemptAt не считается due.

GetTrainingData возвращает formatVersion=1, datasetRevision, asOf, rows, hasMore, nextCursor и serverNow. rows содержат неизменяемые версии примеров в порядке sequence. sampleId — строковое представление числового sequence; eligibility — ELIGIBLE либо EXCLUDED, reasons — список причин. features содержит шесть вычисленных признаков; actualMs, capturedAt, sourceAvailableAt и observedAt находятся на верхнем уровне строки. Также возвращаются inputAssessmentSequence, sourceDigest/sourceGeneration, issuedPrediction и firstEligible. Каждая ревизия не считается новым опытом. Первая страница фиксирует datasetRevision/asOf. Изменение набора между страницами возвращает DATASET_CHANGED; выгрузку нужно начать заново. Данные владельца не должны попадать в Git или постоянные синтетические фикстуры. Аналитический [JSON-отчёт](json-report.md) сохраняет context.agentTask и serverEstimation в истории assessment, но не является архивом очереди и всех моделей.

## Локальная проверка выгрузки

CLI `scripts/evaluate-atlm.mjs` — отдельный инструмент разработчика; для обычной работы MCP он не нужен. Он принимает нормализованный JSON, а не сырой ответ GetTrainingData. Сначала запросите все страницы, каждый раз передавая nextCursor предыдущей страницы; datasetRevision и asOf должны совпадать. При DATASET_CHANGED начните выгрузку заново. Затем выберите последнюю числовую sampleId **среди всех версий** каждого planId и только после этого разделите ELIGIBLE и EXCLUDED. Если сначала убрать EXCLUDED, можно ошибочно вернуть удалённый или изменённый источник в обучение.

Пример преобразования массива `pages` из полных ответов одной выгрузки:

```js
const first = pages[0];
if (!first || pages.some(p => p.datasetRevision !== first.datasetRevision || p.asOf !== first.asOf)
    || pages.at(-1).hasMore || pages.at(-1).nextCursor !== null) {
  throw new Error("Нужны все страницы одного снимка");
}
const latest = new Map();
for (const row of pages.flatMap(p => p.rows)) {
  const previous = latest.get(row.planId);
  if (!previous || Number(row.sampleId) > Number(previous.sampleId)) latest.set(row.planId, row);
}
const samples = [...latest.values()];
const normalized = {
  formatVersion: 1, sourceAuthority: "OWNER_EXPORT", asOf: first.asOf, nextCursor: null,
  rows: samples.filter(r => r.eligibility === "ELIGIBLE").map(r => ({
    sampleId: r.sampleId, planId: r.planId, capturedAt: r.capturedAt,
    sourceAvailableAt: r.sourceAvailableAt, features: r.features, actualMs: r.actualMs,
  })),
  excluded: samples.filter(r => r.eligibility === "EXCLUDED").map(r => ({
    sampleId: r.sampleId, planId: r.planId, reasons: r.reasons,
  })),
};
```

Сохраните normalized как UTF-8 JSON вне Git и выполните `node scripts/evaluate-atlm.mjs <normalized-dataset.json>` из sites/plan-time-tracker. Предел CLI — 8 МиБ; входы SYNTHETIC остаются явно синтетическими. Хронологические cutoff проверяются ядром; отдельный sourceExcludedCount в результате сохраняет число исключённых источников. При пустой пригодной выборке MAE остаётся null и candidateReady=false; ноль не подставляется. CLI не обучает активную модель сервера и не меняет историю владельца.

## Накопление опыта и обновление модели

Пригоден только завершённый план с полными обязательными исходными признаками (runtime-параметры могут быть неизвестны), текущим DONE у всех этапов, полными серверными интервалами, неизменным объёмом и без удаления. Выполнение проверок из исходного плана подтверждает агент перед DONE. Изменение требований A→B→A также меняет объём; запись того же значения без изменения — нет. Долгие планы не отбрасываются из-за длительности. Один план даёт не более одной единицы нового опыта за всё время; повтор Finish, восстановление и ревизии не создают новые планы.

Через каждые **2 новых пригодных уникальных планов** ставится TRAIN-задание. Это частота попытки, а не достаточный размер первой модели. Неудачная проверка или нехватка данных фиксирует рассмотренную пару: следующая автоматическая попытка ждёт следующие два новых примера. История, исходные прогнозы и версии сохраняются. Обучение использует все пригодные данные текущей версии; при превышении предела v1 в 5000 строк возвращается DATASET_LIMIT_REACHED без скрытого усечения или удаления истории.

Изменение использованного источника делает зависящую модель непригодной для свежих прогнозов и ставит пересборку независимо от пары. Изменения источника и постановка задания атомарны. Задания и поколения хранятся в D1; lease 60 секунд и fencing token не позволяют старому исполнителю активировать результат после передачи работы другому. Проход ограничен 10 секундами wall time; это не заменяет фактический CPU-лимит платформы.

Worker запускает обработку после успешной команды через ctx.waitUntil. Ошибка обучения не отменяет уже подтверждённый FinishPlan. После аварии очередь сохраняется, а следующий сеанс навыка или открытие интерфейса продолжает due-работу. Без новых обращений гарантированного повторного запуска после аварии нет. Периодический cron или LLM-задача не устанавливаются.

Временный сбой допускает первую попытку и ещё три повтора с задержками 1/5/15 минут. До nextAttemptAt обработка не запускается. После исчерпания попыток состояние FAILED остаётся видимым; пригодная текущая модель сохраняется. Два новых плана могут создать следующее поколение.

## Математика и проверка качества

Основа — [Whigham, Owen, MacDonell: A Baseline Model for Software Effort Estimation](https://arxiv.org/abs/2102.02933): OLS с выбором identity/log/sqrt и кодированием категорий. В agent-v2 расчёт внутри использует минуты, API — ms. Выбор преобразования использует только обучающие значения. log допустим для положительных значений, sqrt — для неотрицательных; скрытого +1 нет. Константные предикторы не добавляют столбцов, QR с pivoting проверяет ранг, скрытого ridge нет.

Искусственный запас n-p>=5 снят. Достаточно n>=p и полного ранга. При n=p точечный прогноз допустим, но остаточную дисперсию и доверие по нему не оцениваем. Пустая история, недостаточный ранг, отрицательный или неконечный результат остаются явными причинами недоступности. Ресурсный предел — 64 коэффициента и 5000 обучающих строк: MODEL_CAPACITY_LIMIT/DATASET_LIMIT_REACHED сохраняют данные и явно сообщают предел, не скрывают усечение.

modelId/effort учатся как номинальные категории. null — самостоятельный уровень, если он встречался в обучении. Для неизвестной/новой категории без такого уровня используется взвешенный по обучающим частотам линейный предиктор уровней до обратного преобразования времени; это не среднее голых dummy-коэффициентов и не угадывание названия модели. Число исполнителей центрируется по среднему преобразованному известному количеству. Неизвестное получает нулевое отклонение от этого среднего и отдельный индикатор пропуска, когда он меняется в истории. Все неизвестные не добавляют лишних коэффициентов. Уровни, частоты, средние и преобразования сохраняются в артефакте.

Историческая проверка выбирает не более 20 последних пригодных случаев. Для каждого использует только примеры, доступные строго до его исходной оценки; текущий план исключается. Все преобразования заново учатся на этом префиксе. K считает случаи с доступными ATLM и медианой, а не обработанные записи. Пропуски и coverage учитываются.

При K<5 первая математически корректная модель может активироваться с accuracy=EXPERIMENTAL. Смена одной экспериментальной модели другой также не ждёт пяти случаев. При K>=5 сохраняются проверки MAE против медианы и независимое сравнение с incumbent. Подтверждённую модель нельзя заменить неподтверждённой только из-за большего числа примеров; худший кандидат оставляет прежнюю модель. HISTORICALLY_EVALUATED требует достаточных проверок и прохождения сравнений. В отчёте CLI candidateReady означает выполнение критерия исторической проверки, а не запрет ранней модели.

Коэффициенты окончательно пересчитываются на допустимом снимке, затем сохраняются с версиями agent-v2/agent-task-v2 в estimation_models. Там же хранятся manifest, N, preprocessing и метрики/qualityConfirmed. Указатель активной модели хранится в estimation_owner_state. Инференс применяет сохранённый артефакт и не обучается заново на запрос; GetSavedEstimate читает исходный сохранённый прогноз. Старые артефакты не используются новым вычислителем, исходные оценки и история не переписываются. Текущая вставка явно задаёт версии, без SQL defaults v1; чужой по версии checkpoint пересчитывается под действующим lease.

В API доступны sampleCount=N, evaluation.caseCount=K, evaluation.qualityConfirmed и accuracy. При K=0 MAE=null, а не 0. В UI N/K относятся к конкретной модели/сохранённой оценке, не к общему числу планов и не к прогрессу очереди. EXPERIMENTAL показывается как «Качество не подтверждено»; отсутствие ошибки — «Ошибка пока не оценена». Даже подтверждённая историческая MAE не гарантирует будущую длительность; confidence остаётся UNKNOWN, интервал не выдумывается.

## Интерфейс и проверки реализации

В карточке плана показана сохранённая оценка полного активного времени, версия модели, N обучающих планов, K проверенных прогнозов, пометка качества и историческая ошибка при наличии. Устаревшая оценка помечена; отсутствие оценки не превращается в ноль. Настройки показывают число новых пригодных планов до следующей попытки, накопленные данные, очередь и её последнюю причину отказа. Раскрываемое пояснение показывает причины исключения планов, в том числе отсутствие исходных признаков до первого запуска. При due-работе интерфейс запускает ограниченное обслуживание; обновление статуса само по себе остаётся чтением. Автоматически допускается не более восьми проходов за сеанс и один проход для неизменного ключа datasetRevision/generation/progressRevision/pendingRefreshCount/nextAttemptAt. После прохода выполняются не более трёх контрольных чтений; ручное «Продолжить обработку» начинает новый ограниченный цикл. Ошибка обработки остаётся видимой при контрольном чтении. Поздний ответ плана не попадает в уже открытый другой план.

Целевые проверки: `node --test test/atlm-*.test.js`, `node test/ui-atlm.mjs` из sites/plan-time-tracker, `node --test test/atlm-instructions.test.mjs` из plugin/plan-time-tracker. CLI проверки истории: `node scripts/evaluate-atlm.mjs <dataset.json>`. Общая проверка сайта — `npm test`, `npm run validate`, `npm run test:ui`. Синтетические примеры проверяют реализацию; реальная точность требует отдельной накопленной выборки. Результаты конкретного выпуска фиксируются в release readiness, а не выводятся из наличия этих команд.

Новая GitHub-миграция — `0019_atlm.sql`. Для существующего Sites источника сохраняется отдельный ledger и добавляется эквивалентная `0004_atlm.sql`; старые миграции не переписываются. Обновление GitHub само по себе не подтверждает публикацию Sites или установку нового пакета навыков. Исторические оценки и данные сохранены. Старый инструмент CalculateEstimate удалён; для нового прогноза используется ATLM.

## Ручной запуск с сайта

В настройках кнопка «Начать обучение» вызывает `POST /api/tracker/estimation-model/start` с пустым объектом. Это тот же серверный процесс, что и MCP `StartTraining`: порог новых планов не применяется. После ответа интерфейс показывает состояние и при необходимости ограниченно продолжает обработку. При потере ответа повторный запуск не выполняется автоматически: сначала можно обновить состояние. Автоматическое обучение после двух новых пригодных планов и проверки качества модели сохраняются.

В обычном состоянии настроек отображается одна основная кнопка. «Начать обучение» создаёт ручную попытку; при активной очереди та же кнопка проверяет состояние или продолжает ограниченную обработку. После неизвестного исхода запуска сначала выполняется только чтение состояния. Обработанные примеры не равны успешно проверенным случаям: качество и принятие модели показываются отдельно.
