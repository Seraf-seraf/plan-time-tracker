# ATLM: прогноз активного времени

ATLM прогнозирует `PLAN_ACTIVE`: полное время рабочих интервалов плана без пауз, начиная с первого StartPlan. Это не календарный срок и не сумма времени параллельных исполнителей. До запуска GetSavedEstimate читает текущий прогноз без записи; первый StartPlan атомарно фиксирует его. После запуска показывается сохранённый снимок и признак устаревания при изменении источника.

До начала работы заполните признаки по схеме `agent-task-v4`. Полную схему с вложенными полями, допустимыми значениями и ограничениями возвращает `GetTrackerInfo` в `assessments.atlm.agentTaskSchema`. Её используют оба входа, `EstimatePlanTime.agentTask` и `SaveTaskAssessment.payload.context.agentTask`. Если клиент сокращает объявление инструмента, читайте сам ответ `GetTrackerInfo`. [Справочник признаков и примеры](../plugin/plan-time-tracker/skills/assess-task/references/features.md).

Сервер рассчитывает счётчики и долю операций WRITE, кодирует категории и отличает неизвестные значения от подтверждённых нулей. Интерфейс показывает названия признаков, их значения и сохранённые причины неизвестности. Для первого `StartPlan` требуется оценка со статусом `READY`. Снимок может содержать доступный прогноз или `UNAVAILABLE`, если данных для него недостаточно. [Запись оценки и проверка готовности](assessments.md).

## Расчёт

Метод `atlm/agent-v5-operations` преобразует активное время в минуты по формуле `log1p(actualMs / 60000)`. В рецепте v4 это время из проверенной учителем строки. Тренер выбирает первый доступный точечный метод в порядке Ridge, Bayesian, OLS. Сравнение с исторической медианой встречается в отчётах прежних рецептов. Ridge и Bayesian допускают число признаков не меньше числа наблюдений. Для OLS нужна матрица полного ранга. При отсутствии истории прогноз недоступен. Один пригодный план даёт ранний ориентир `historical-median` без интервала.

Bayesian использует normal-inverse-gamma и прогнозное распределение Student-t с фиксированными приорами: precision 1 для стандартизованных коэффициентов и 0,000001 для свободного члена, shape 2, scale 1. `BAYESIAN_PREDICTIVE` выдаёт квантили 0,10 и 0,90. V4 использует этот интервал, когда он доступен. В прежних рецептах `BAYES_QUANTILE` обучает регуляризованные квантильные регрессии 0,10/0,50/0,90 на стандартизованных остатках исторического Bayesian; для каждого остатка и преобразования признаков используются только факты, доступные до начала задачи. Нужно не менее пяти таких остатков. Пересечённые квантили упорядочиваются, а границы расширяются до выбранной точки.

В `serverEstimation` находятся `pointMs`, `pointEngine` и `interval` с `status`, `lowerMs`, `upperMs`, `nominalCoverage`, `engine`, `calibrationSampleCount`, `validationStatus`, `unavailableReason`. При недоступном диапазоне границы null и указана причина. Номинальный охват 0,80 — цель, а не гарантия будущего результата. EXPERIMENTAL и HISTORICALLY_EVALUATED описывают наличие исторической проверки, а не обещание точности.

## Обучение по запросу

Агент готовит датасет и обучает модель по поручению пользователя. Worker выдаёт исходный снимок и хранит решения учителя, пакет модели и указатель активной ревизии. Тренер запускается локально в Node.js 24. Схемы операций, лимиты и рецепт по умолчанию возвращают `GetTrackerInfo.assessments.atlm.registry` и `tools/list`. Для работы с файлами нужны checkout проекта и code-mode с прямой передачей файлов. [Инструкция для агента](../plugin/plan-time-tracker/skills/train-model/SKILL.md).

1. Получите свежий снимок через `CreateTrainingSnapshot` в `mode:'create'` с новым UUID команды. Используйте сохранённый `snapshotId` при возобновлении той же подготовки или по явному указанию пользователя. Если пользователь указал готовую ревизию датасета, выгрузите её и сверьте формат с рецептом.
2. Учитель сверяет каждый признак `agentTask` с фактически выполненной работой, включая вложенные поля. В `annotation.agentTask` сохраняются исправленные значения. `fieldEvidence` объясняет значения признаков, `codeEvidence` позволяет проверить их по коду, журналам и другим результатам конкретной задачи. Для `execution.plannedParallelAgents` учитель сохраняет подтверждённый максимум одновременно работавших над планом агентов, включая основного. Если точное число неизвестно, учитель ставит `1`, отмечает подстановку и проверенный источник в основаниях признака. При подтверждённом времени и заполненных остальных признаках план входит в обучение. Явное указание пользователя для конкретного датасета или плана имеет приоритет в указанной области.
3. Учитель подтверждает активное время `PLAN_ACTIVE`. Рабочие интервалы одного плана объединяются без пауз, каждое пересечение учитывается один раз. Если подтверждённое время расходится со снимком или в снимке его нет, учитель записывает `annotation.actualTime:{actualMs,evidence}`. Передайте целое неотрицательное число миллисекунд и конкретное подтверждение. Ноль допустим при подтверждённом нулевом замере. Если проверка выявила ошибку таймера и полного замера нет, учитель выясняет фактическую длительность у пользователя до сохранения датасета. Тренер использует время из аннотации, когда оно задано, или проверенный замер из снимка. Исходное `source.actualMs` остаётся доступно для сверки.
4. По умолчанию учитель готовит к обучению каждый завершённый неудалённый план. Неполную карточку и ошибки исходного наблюдения учитель исправляет. Похожие задачи остаются отдельными строками. Большое расхождение прогноза с подтверждённым фактом сохраняется в данных. Учитель исправляет строку по коду, журналу, проверкам и явным уточнениям пользователя. Если после этого и предусмотренных схемой подстановок обязательное значение по-прежнему неизвестно, учитель показывает пользователю `planId`, название, недостающее поле и проверенные источники. До ответа можно готовить другие строки. Сохранение и обучение начинаются, когда по каждому такому плану получен факт или явное разрешение на пропуск.
5. Для удалённого или незавершённого плана укажите применимую причину `PLAN_DELETED` или `PLAN_NOT_COMPLETED`. Если подходят обе, достаточно одной. Завершённый неудалённый план можно пропустить по явному указанию пользователя. При любом `USER_REQUESTED_SKIP`, включая статусные исключения, сохраните ссылку на указание пользователя по этому плану в `exclusionEvidence.userDecision`. Ранее выданное разрешение учитывается, пока пользователь его не снимет. Сверьте `rowId` и `planId` всех строк со снимком, чтобы каждый план встретился ровно один раз. Сохраните решения через `SaveDatasetRevision` в файле с `schemaVersion:1` и `contract:'atlm-teacher-annotations-v2'`. Выгрузите сохранённый `atlm-teacher-dataset-v2`, проверьте состав и SHA-256 по `datasetDigest`. В итогах укажите число исправленных планов и полный список исключённых с ID, названием, причиной и источником пользовательского решения при пропуске. Рецепт v4 использует этот экспорт. Рецепты v1–v3 используют прежний формат.
6. Выполните `train-atlm.mjs`. До порученной регистрации сравните `provenance.fitRowIds` и манифест артефакта со списком всех `ELIGIBLE` строк по ID. Для регистрации передайте `registration.bundle.json` через `RegisterModelRevision`. Назначение ревизии меняется отдельной командой `ActivateModelRevision`.

### Файлы и восстановление

Снимки, ревизии и отчёты выгружаются по неизменяемому ID. `view:'rows'` у снимка и датасета возвращает компактный перечень. Полный файл со строками и доказательствами подготовьте через `view:'download'`. При выгрузке модели и чтении её частей передавайте один и тот же `fileKind`. `BUNDLE` используется по умолчанию, `ARTIFACT` выдаёт артефакт без остальных файлов пакета.

Для загрузки возьмите новый `commandId` и подготовьте `file:{sha256,byteLength}` через `atlm-transfer.mjs manifest`. На всех фазах сохраняйте эти аргументы, а также `snapshotId` и `parentDatasetRevisionId` для `SaveDatasetRevision` или `datasetRevisionId` для `RegisterModelRevision`.

- **Отправить недостающие части.** После `prepare` при `UPLOADING` пропустите диапазоны `receivedPartRanges` и передайте остальные части через `putPart`, затем вызовите `commit`. При `UPLOAD_INCOMPLETE` или `UPLOAD_EXPIRED` повторите `prepare` с исходными аргументами. Отправьте части, отсутствующие в новом `receivedPartRanges`, и повторите `commit`. Полная часть содержит 49 152 байта, лимит загрузки 16 МиБ. В code-mode передавайте base64 из `atlm-transfer.mjs read-part` в `putPart` после проверки длины. Для вывода helper задайте `max_output_tokens:80000`. Пользователю выводите метаданные и прогресс.
- **Повторить запрос.** При `MATERIALIZING` повторите `download`, при `VALIDATING` повторите `commit` с теми же аргументами. Дождитесь `retryAfterMs` в обоих случаях. При потере ответа на запись читайте `GetCommandResult` с исходным `commandId`. При `FINAL` используйте `result` или `error`, при `PENDING` или `NOT_FOUND` точно повторите запрос по сохранённым локально аргументам. Подтверждённый отказ содержимого может оставить квитанцию в `PENDING`. Для исправленного файла вычислите новый manifest и используйте новый `commandId`.
- **Забрать готовый результат.** При `READY` прочитайте части через `view:'filePart'` по `partIndex` и запишите их по позиции через `atlm-transfer.mjs write-part` в `.partial`. После проверки длины и SHA-256 через `verify` переименуйте файл. При `SAVED` для датасета или `REGISTERED` для модели сохраните ID ревизии. После успешного commit любая из трёх фаз при точном повторе возвращает итог с `replayed:true`. [Команды переноса и возобновления](../plugin/plan-time-tracker/skills/train-model/SKILL.md#передача-файлов).

### Рецепт локального запуска

В `recipe.json` задайте поля рецепта, подставив ID ревизии и digest полного экспорта.

```json
{
  "schemaVersion": 1,
  "recipeId": "atlm-teacher-hybrid-v4",
  "datasetRevisionId": "ID из GetDatasetRevision",
  "datasetDigest": "sha256:SHA-256 исходных байтов",
  "selection": { "mode": "ALL_ELIGIBLE" }
}
```

В v4 `ALL_ELIGIBLE` — единственный режим. Одинаковые исходные файлы и версия тренера воспроизводят состав и результат.

```sh
cd sites/plan-time-tracker
node scripts/train-atlm.mjs --dataset /path/dataset.json --recipe /path/recipe.json --out /path/run
```

Каталог результата содержит `run.json` с версиями, digest и диагностикой, `manifest.json` с составом выборки и `evaluation.json` с решениями по строкам и пустым `modes` у v4. Код выхода `0` означает готовые `artifact.json` и `registration.bundle.json`. При `2` проверьте `run.json.reason` и диагностику. Код `1` означает ошибку входа или исполнения. Повтор проверяет digest выходов и переиспользует полный результат с теми же входами. Каталог публикуется атомарно. Признаки и строки сохраняются полностью, в том числе при отказе solver по пределам ресурсов. Артефакт HYBRID хранит веса, число строк и дайджест финального состава. Реестр сверяет его с полным набором пригодных строк в сохранённой ревизии датасета.

## Как читать оценку качества

Рецепт v4 рассчитывает финальные веса на всех пригодных строках проверенного датасета. Один план даёт одну строку. Даты, порядок выполнения и похожесть задач не делят финальный набор. Точечный метод выбирается по доступности в порядке Ridge, Bayesian, OLS. Когда доступен прогнозный интервал Bayesian, используется `BAYESIAN_PREDICTIVE`. Рецепт не рассчитывает отложенную или историческую проверку.

Раздел «Модель прогноза» показывает число планов в финальном обучении и сводку фактически выданных прогнозов выбранной ревизии. Сводка сопоставляет прогноз, сохранённый при первом старте, с активным временем завершённого плана по учёту трекера. Пока сопоставимых фактов нет, оценка точности отсутствует. Смотрите на MAE, медиану ошибки, смещение и охват интервала вместе с числом наблюдений. MAE и MedAE выражены в миллисекундах в API и минутах на сайте. Ошибка со знаком равна прогнозу минус факт.

Прежние ревизии открываются с теми данными, которые сохранились при обучении. v1 использует группы и отложенную проверку. v2 проверяет отдельные планы на исторических срезах и обучает финальную модель на полном пригодном составе. v3 обучает на подтверждённых наблюдениях снимка и показывает фактически выданные прогнозы. В интерфейсе v1 и v2 «Контрольная проверка» показывает сохранённый отчёт, а «Выданные прогнозы» показывают фактическое качество работы выбранной ревизии.

## Активация и история

Реестр показывает «Выдаёт прогнозы» для ревизии, доступной для новых прогнозов, «Не назначена» для зарегистрированных и ранее использовавшихся ревизий, «Недоступна» с причиной для архивных ревизий и ревизий с нарушенными источниками. Указатель «Назначенная ревизия» может ссылаться на недоступную модель. Отчёты о точности доступны отдельно от статуса ревизии.

Сравните `activeModelRevisionId` и `servingModelRevisionId` в `ListModelRevisions({schemaVersion:1,view:'list'})`. Первый хранит назначение для CAS, второй показывает модель, доступную для новых прогнозов. Для активации передайте `modelRevisionId`, `expectedActiveModelRevisionId`, `expectedActivationVersion`, новый `commandId` и причину. Для v4 реестр проверяет пакет, полный набор строк и актуальность источников. Порученная активация использует текущую версию указателя и причину. Для допуска v2 нужен доступный `ROLLING_PLAN_PLANNED` с минимум пятью разными сопоставимыми планами. MAE кандидата должна быть не выше MAE медианы на тех же парах. Для v1 сохраняются прежние правила планового holdout и минимального числа групп.

Если регистрация вернула `activationEligibility.status:'REQUIRES_EXPERIMENTAL_ACK'` или активация вернула `EXPERIMENTAL_CONFIRMATION_REQUIRED`, для активации требуется явное согласие пользователя и `acceptExperimental:true`. Это же правило действует при откате. Значение `serverEstimation.accuracy:'EXPERIMENTAL'` в `GetSavedEstimate` описывает проверку прогноза и возможно при `ELIGIBLE`. Неверный артефакт или изменившийся источник блокируют активацию независимо от подтверждения.

Изменение поколения любого использованного источника сразу делает выпуск непригодным для новых прогнозов. Для v1 правило включает источники прежнего HOLDOUT и PURGED. Сохранённый прогноз начатого плана остаётся прежним. Новый план вне выборки и новая ревизия разметки сами по себе не меняют пригодность модели. Для отката выберите прежнюю пригодную ревизию и повторите `ActivateModelRevision` с текущими CAS-значениями. Причина и результат останутся в истории.

Исторические ревизии сохраняют исходные байты артефакта, отчёт и известную историю публикаций. Например, `atlm-11-r2` хранит прежний результат `REJECTED/INSUFFICIENT_INCUMBENT_CASES` рядом с фактом публикации. Неизвестные даты и источники остаются `null`. `BUNDLE` импортированной модели выдаёт архив для аудита. Для нативной модели `BUNDLE` возвращает исходный пакет регистрации. Если обучение по импортированной выгрузке вернуло `HISTORICAL_PROVENANCE_INCOMPLETE`, подготовьте новый нативный снимок с проверенной разметкой.

Если после сброса истории исходный снимок отсутствует, `GetSavedEstimate` возвращает `HISTORY_RESET`. Возобновление начатого плана по-прежнему доступно.
