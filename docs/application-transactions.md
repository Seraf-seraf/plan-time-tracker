# Транзакции приложения и наблюдатели

Команды исполняются в JavaScript. После `0029_application_transactions.sql` в БД нет триггеров, которые создают, изменяют или удаляют записи. Схема сохраняет ограничения, индексы, внешние ключи и проверочные триггеры: они могут отклонить недопустимую операцию, но не выполняют её побочные действия.

## Владельцы поведения

| Компонент | Ответственность |
| --- | --- |
| `SqlTransaction` | Собрать prepared statements и передать весь набор в один `db.batch` |
| `TransactionalEvents` | Вызвать явно перечисленных наблюдателей в заданном порядке |
| `CommandReceipt` | Решение команды, условие применения, окончательный результат и защита от повторных эффектов |
| `PlanLifecycleHandler` | Создание и переходы состояния плана |
| `MetadataCommandHandler` | Метаданные плана и история изменения его даты |
| `StepStatusHandler` | Статус и версия этапа |
| `AssessmentCommandHandler` | Неизменяемая ревизия оценки с проверкой требований и источников |
| `WorkIntervalObserver` | Интервалы работы плана |
| `StepIntervalObserver` | Интервалы этапов |
| `RequirementsObserver` | Изменение представленных в плане полей требований |
| `AtlmPlanObserver` | Снимок первого запуска, очередь обновления источника, инвалидирование использованной модели |
| `AtlmSampleObserver` | Ревизия датасета и число впервые пригодных планов |
| `AtlmCheckpointObserver` | Удаление частей завершённого или сменившегося поколения обучения |
| `AtlmOwnerRepository` | Явная инициализация состояния владельца с `schema_version=4` |

Разбор Markdown и его обновление используют существующие функции документа. Формулы, признаки и артефакты модели ATLM не изменены.

## Одна команда — одна транзакция

Приложение проверяет вход, подготавливает прогноз или разбирает документ. Затем формирует один атомарный пакет:

1. Вставить квитанцию с новым `execution_nonce`.
2. Определить исход по текущему состоянию и версии в БД. Предварительного чтения для этого недостаточно.
3. Добавить обязательные записи наблюдателей.
4. Изменить основную сущность и окончательный результат квитанции.
5. Зафиксировать весь пакет.

Наблюдатели синхронно **подготавливают SQL** до вызова `commit`. SQL выполняется последовательно уже внутри транзакции БД. Они не выполняют отдельные сетевые запросы и не запускают фоновую работу. Для событий жизненного цикла порядок задан в `command-handlers.js`: ATLM читает прежние значения, затем записываются интервалы и требования, после них — новое состояние сущности. Все действия проверяют успешную квитанцию с тем же владельцем, `commandId` и nonce.

События: `plan.starting`, `plan.pausing`, `plan.resuming`, `plan.finishing`, `plan.deleting`, `plan.restoring`, `plan.metadata-changing`, `step.status-changing`. Учёт образцов и очистка checkpoint используют отдельные `sample.persisting` и `training.checkpoint-discarding`.

D1 предоставляет атомарный `batch`; remote-sqlite выполняет тот же набор statements в `BEGIN IMMEDIATE`. Пакет не разбивается на независимые `run`. Ошибка любого SQL откатывает квитанцию и все эффекты. Ошибка подготовки наблюдателя запрещает commit частично собранной транзакции.

Известный отказ команды, например конфликт версии, остаётся квитанцией с прежним кодом ошибки; её повтор не пересматривает уже принятое решение. При потере ответа нельзя считать команду невыполненной: клиент читает `GetCommandResult` или повторяет тот же конверт с тем же `commandId`. Новый nonce повторной попытки не совпадает с сохранённой квитанцией и не разрешает повторные записи. Сам `SqlTransaction` не повторяет пакет автоматически.

## ATLM и прямой SQL

Одна успешная команда, реально изменившая источник, создаёт или обновляет `REFRESH_SAMPLE` один раз. Повтор команды, прежние метаданные, повторный RUNNING этапа и смена только даты составления не создают лишней версии источника. Внутренний `generation` теперь отражает логические команды, а не число отдельных изменений строк.

Счётчики образцов записываются перед вставкой sample под тем же предикатом lease, fence, поколения и digest. Обе записи принадлежат одному batch: при отказе вставки счётчики откатываются. Новая версия того же плана не становится новым независимым опытом. Смена поколения обучения и очистка его checkpoint также атомарны и проверяют владение исполнителя.

Прямая административная запись SQL теперь изменяет только указанные данные. Она не обновляет автоматически требования, интервалы, очередь или модель. Для поддерживаемых действий нужен application service; инструмент обслуживания должен явно включить относящиеся наблюдатели в свою транзакцию. Исторические migration tests создают данные старым SQL-протоколом до обновления схемы; текущие runtime tests работают на полной схеме.

## Переключение с 0028 на 0029

Схема и Worker составляют согласованный выпуск. Новый Worker требует колонку `execution_nonce`; старый Worker после миграции не должен продолжать запись.

1. Остановить приём записей и фоновых исполнителей выбранной БД. Сохранить проверяемую резервную копию штатным SQLite Backup API, учитывающим WAL.
2. Применить `0029_application_transactions.sql` штатным мигратором. Она удаляет 24 изменяющих триггера, добавляет nonce и проверочные guards. Планы, интервалы, оценки, samples, модели, история попыток и части checkpoint сохраняются.
3. Миграция отзывает право прежних исполнителей на запись: увеличивает `fence` и повышает `executor_epoch` у RUNNING jobs. Статус и срок lease сохраняются. После истечения lease штатное восстановление закрывает незавершённую попытку и либо назначает повтор, либо завершает задачу ошибкой при исчерпании попыток. Это сохраняет историю и не оставляет четвёртую попытку в недоступной для запуска очереди. Новый протокол claim/release использует `+3`; старый `+2` отвергается. Устаревшая работа не может записать sample или активировать модель с прежним fence.
4. Установить соответствующий Worker и проверить создание, оценку, запуск, повтор команды и обработку очереди в предназначенной для проверки среде. Затем возобновить приём записей.

Квитанции без nonce из прежней истории остаются читаемыми и повторяемыми. Новые команды старого writer отвергаются `APPLICATION_WRITER_REQUIRED`. Старое создание состояния ATLM с другой версией и прежний протокол lease отвергаются `ATLM_CLIENT_RETIRED`.

Возврат только старого Worker после миграции несовместим со схемой. До возобновления записи можно вернуть согласованный комплект из резервной копии и прежнего Worker. После принятия новых записей восстановление старой копии потеряет их; предпочтителен исправленный выпуск с новой схемой. Обратный переход схемы требует отдельной процедуры сохранения новых данных.

## Проверки

`npm test` включает сохранённые сценарии команд, ATLM, миграций и новые проверки транзакции. `application-commands.test.js` проверяет откат на snapshot, очереди, интервале и квитанции с последующим повтором. `application-migration.test.js` проверяет сохранность истории, отзыв leases и отсутствие изменяющих триггеров. `atlm-observers.test.js` проверяет учёт samples и защищённую очистку checkpoint. `remote-transactions.test.js` запускает реальный Python SQLite-сервис с временной БД и проверяет откат, потерю ответа, повтор и изоляцию владельцев через Worker.

Штатные `npm run validate`, plugin tests и `npm run test:ui` проверяют собранный entrypoint, контракт MCP и существующие пользовательские сценарии. Эти локальные проверки не являются подтверждением production deploy.
