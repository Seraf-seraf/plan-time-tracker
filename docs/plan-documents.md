# Исходный план и текущее состояние этапов

CreatePlan принимает `title` и `planCreatedAt`. Дату передайте как `{precision:"dateOnly",on:"YYYY-MM-DD",timeZone}` или `{precision:"instant",value:"<ISO 8601 с часовым смещением>",timeZone}`. С `planText` сервер сохраняет Markdown и выделяет этапы по заголовкам одного уровня, например `## Этап 1. Название`, `## Этап DATA-001. Название` или `## G1. Название`. Идентификаторы заголовков уникальны без учёта регистра, длина заголовка ограничена 200 символами. Заголовки в блоках кода игнорируются. Ошибка импорта не оставляет частичного плана.

GetPlan возвращает исходный документ без пересказа. GetPlanProgress возвращает текущие этапы с текстом, ordinal, статусом и version. SetStepStatus атомарно меняет статус и версию этапа, сохраняя минимальную квитанцию для точного повтора. Допустимы PENDING, RUNNING, BLOCKED, FAILED, DONE. План должен быть RUNNING и не удалён.

Статус DONE — утверждение агента о выполнении этапа и проверок из исходного плана. Сервер не запускает проверки и не ведёт отдельный журнал исполнения. Статус не меняет таймер. Для обычного FinishPlan все этапы должны быть DONE; явное досрочное завершение требует причины.

`StartPlan` открывает первый активный интервал при готовой оценке. `PausePlan` закрывает интервал, `ResumePlan` открывает новый, `FinishPlan` завершает план. Для завершения с незавершёнными этапами передайте `allowIncomplete:true` и `reason`. Все четыре команды принимают `planId` и текущую версию плана. [Оценка перед запуском](assessments.md).

`DeletePlan` перемещает план в удалённые. Если он выполняется, сервер закрывает активный интервал, переводит план в PAUSED, а выполняемые этапы в BLOCKED. `RestorePlan` возвращает план со сохранённым статусом. `ListPlans` по умолчанию показывает обычные планы, с `deleted:true` — удалённые. Сохранённые интервалы восстановленного плана снова учитываются в аналитике.

Команда, её квитанция, интервалы, изменения требований и обязательные эффекты ATLM записываются одной транзакцией приложения. Наблюдатели добавляют SQL в тот же пакет; ошибка любого действия откатывает его целиком. SQL-триггеры только проверяют ограничения и не выполняют прикладных записей. [Архитектура и протокол повтора](application-transactions.md).

## Обновление до первого запуска

UpdatePlan принимает текущую версию плана `expectedVersion` и один режим:

| Режим | Поля payload | Действие |
| --- | --- | --- |
| Метаданные | `planId` и одно или несколько полей `title`, `description`, `acceptanceCriteria`, `planCreatedAt` | При переносе даты на момент после первого запуска передайте `confirmDateAnomaly:true`. |
| Весь документ | `planId`, `planText` | Заменяет Markdown целиком, пересобирает этапы. |
| Правка этапов | `planId`, `stepEdits: [{stepId, markdown}]` | Заменяет выбранные разделы Markdown по UUID из GetPlanProgress. Для каждого требуется полный раздел с прежним идентификатором в заголовке. |

Документ и этапы редактируются только у неудалённого PLANNED-плана до первого запуска. Для добавления, удаления и перестановки этапов используйте `planText`. Этап с прежним идентификатором в заголовке сохраняет `stepId`; при изменении его текста, названия или позиции растёт его версия. Этап с сохранённой оценкой или учтённым временем удалить нельзя.

Markdown, этапы, текущие требования к оценке и версия плана меняются в одной транзакции. Сохранённые оценки не переписываются: при смене требований перед запуском нужна новая ревизия оценки. Недоступная правка отклоняется сразу. Предложенный текст команды не хранится в квитанции. Для точного повтора используйте тот же commandId; GetCommandResult читает квитанцию, если команда была записана.

## Записанное время этапов

Успешный `SetStepStatus` с RUNNING атомарно открывает серверный интервал этапа. Другой статус закрывает интервал, повтор RUNNING сохраняет уже открытый. Завершение плана с исключением закрывает интервалы. При удалении открытые интервалы закрываются, а выполняемые этапы переходят в BLOCKED. Для расчёта времени этапа учитывается только пересечение с активными интервалами плана. Возобновление плана продолжает измерение открытого интервала этапа.

Если у этапа в статусе RUNNING ещё нет открытого интервала, повтор RUNNING начинает измерение с текущего момента. График отражает только записанные интервалы.

`GET /api/analytics/plans/:planId/steps?from=YYYY-MM-DD&to=YYYY-MM-DD&timeZone=...&asOf=...` возвращает `planId`, `period`, `asOf`, `steps` в порядке ordinal. В этапе: stepId, ordinal, title, activeMs и firstMeasuredAt. `null` означает отсутствие измерений на срезе; 0 — известные интервалы без активного времени в периоде. Даты включительны в указанном часовом поясе; asOf ограничивает интервалы и состав этапов. Метаданные этапов остаются текущими. Итоги времени и число завершённых планов в общем отчёте также ограничены asOf; завершение после среза не включается в медиану и счётчик завершений. Данные читаются одним снимком SQLite с проверкой владельца; удалённые планы исключаются. Параллельные этапы измеряются независимо, их сумма может превышать активное время плана.

В аналитике план раскрывает горизонтальный график с полными названиями и точными длительностями. Загрузка отложена до раскрытия; новый отчёт обновляет снимок графиков.
