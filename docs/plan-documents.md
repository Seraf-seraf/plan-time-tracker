# Исходный план и текущее состояние этапов

CreatePlan принимает исходный `planText` в Markdown до 60 000 символов. Этапы выделяются по заголовкам одного уровня: `## Этап 1. Название`, `## Этап DATA-001. Название` или `## G1. Название`. Заголовки внутри fenced code blocks игнорируются; повторяющиеся идентификаторы и неоднозначная иерархия отклоняются. Ошибка импорта не оставляет частичного плана.

GetPlan возвращает исходный документ без пересказа. GetPlanProgress возвращает текущие этапы с текстом, ordinal, статусом и version. SetStepStatus атомарно меняет статус и версию этапа, сохраняя минимальную квитанцию для точного повтора. Допустимы PENDING, RUNNING, BLOCKED, FAILED, DONE. План должен быть RUNNING и не удалён.

Статус DONE — утверждение агента о выполнении этапа и проверок из исходного плана. Сервер не запускает проверки и не ведёт отдельный журнал исполнения. Статус не меняет таймер. Для обычного FinishPlan все этапы должны быть DONE; явное досрочное завершение требует причины.

Исходный текст после создания неизменен. UpdatePlan редактирует метаданные и дату. Версии этапа и плана независимы. GetCommandResult позволяет восстановить известный commandId после потери ответа. Контроль версии и проверка владельца защищают параллельные записи.

Миграция 0021 переносит сохранённый текст раздела в `plan_steps.content`; для прежнего этапа без исходного Markdown сохраняется его существующий ожидаемый результат как текст. Идентификаторы, порядок, статус, версия и время создания не меняются. Дальше все этапы используют одну модель текущего состояния.

Требования оценивания копируются в текущую таблицу `assessment_targets` без изменения JSON. Исходные оценки, их digest, frozen inputs, обучающие примеры и модели ATLM сохраняются. Из схемы удаляются старое исполнение и его история; API и инструкции не содержат путей их продолжения.

## Записанное время этапов

Миграция 0022 добавляет `step_work_intervals`, не возвращая попытки, аренды или журнал статусов. Успешный `SetStepStatus` с RUNNING атомарно открывает серверный интервал этапа; другие статусы его закрывают. Повтор RUNNING сохраняет открытый интервал. Завершение плана с исключением закрывает интервалы, удаление закрывает их при переводе этапов в BLOCKED; восстановление не запускает их. Пауза плана исключается при пересечении интервалов, а возобновление продолжает измерение этапа, если его статус остаётся RUNNING.

Исторические интервалы не создаются при миграции. У уже выполняемого этапа следующий подтверждённый RUNNING начинает измерение с текущего момента. График показывает записанную часть, а не реконструированное полное время.

`GET /api/analytics/plans/:planId/steps?from=YYYY-MM-DD&to=YYYY-MM-DD&timeZone=...&asOf=...` возвращает `planId`, `period`, `asOf`, `steps` в порядке ordinal. В этапе: stepId, ordinal, title, activeMs и firstMeasuredAt. `null` означает отсутствие измерений на срезе; 0 — известные интервалы без активного времени в периоде. Даты включительны в указанном часовом поясе; asOf ограничивает интервалы и состав этапов. Метаданные этапов остаются текущими. Итоги времени и число завершённых планов в общем отчёте также ограничены asOf; завершение после среза не включается в медиану и счётчик завершений. Данные читаются одним снимком SQLite с проверкой владельца; удалённые планы исключаются. Параллельные этапы измеряются независимо, их сумма может превышать активное время плана.

В аналитике план раскрывает горизонтальный график с полными названиями и точными длительностями. Загрузка отложена до раскрытия; новый отчёт обновляет снимок графиков. JSON-экспорт v2 дополнительно содержит `steps[].intervals` с startMs/endMs, включая незакрытые интервалы.
