# План целиком и статусы этапов

Основной флоу: агент составляет план по Software Engineering и передаёт исходный Markdown в `CreatePlan.payload.planText`. Трекер сохраняет текст без пересказа и выделяет этапы по заголовкам одного уровня: `## Этап 1. Название`, `## Этап DATA-001. Название`, `## G1. Название`. До 60 000 символов и 100 этапов. Заголовки внутри fenced code blocks игнорируются; повторные ID и смешанные уровни этапов отклоняются. Ошибка разбора не создаёт частичного плана.

`GetPlan` возвращает `plan.planText`. `GetPlanProgress` также возвращает исходное `steps[].content`, `step_id`, `version` и статус. `CreatePlan` с текстом не требует отдельных `CreateStep`, `expectedResult`, `requiredChecks` или копии критериев приёмки. Общая приёмка, команды проверок и условия остановки остаются в самом плане. Исходный документ участвует в контексте и digest оценивания.

Для изменения состояния агент вызывает `SetStepStatus` с обычным конвертом команды: `schemaVersion:1`, UUID `commandId`, текущим `expectedVersion` этапа и `payload:{stepId,status}`. Допустимы `PENDING`, `RUNNING`, `BLOCKED`, `FAILED`, `DONE`. План должен быть RUNNING и не удалён. Команда атомарно меняет статус и версию этапа, сохраняет историю и квитанцию; точный повтор возвращает прежнюю квитанцию. Другой владелец не может читать или изменять запись.

Статус не управляет таймером. Создание оставляет план PLANNED; Start/Pause/Resume/Finish сохраняют существующие правила серверных интервалов. Для обычного завершения документа все его этапы должны быть DONE. Статус DONE означает утверждение агента о выполнении плана и его проверок; сервер не запускает тесты. Для документа не нужны аренды попыток, снимки исходников, digest и отдельные записи результатов проверок.

Текст после создания остаётся исходным. `UpdatePlan` меняет метаданные, не переписывает документ; `CreateStep`/`UpdateStep` не создают отдельную конкурирующую структуру этапов документа. Изменение исходного Markdown этой версией команды не поддерживается и явно отклоняется.

В интерфейсе документ показывается с разделами, списками, таблицами и кодом. Raw HTML и исполняемые URL не исполняются. Исходный текст доступен для копирования. Для исторических планов остаются текст этапа, статус и сохранённый итог работы. Технические формы полностью удалены из UI. Старые API доказательств, неизменяемая история и прежняя проверка готовности исторических планов сохраняются; SetStepStatus не позволяет обойти их.

Экспорт включает `planText` и исходный `content` этапов. Это тот же согласованный snapshot экспорта, который включает результаты, проверки и историю старых планов.

## Обновление базы

Каноническая миграция `0020_plan_documents.sql` добавляется после `0019_atlm.sql`. Она создаёт таблицы исходных документов и разделов, команду статуса и расширяет views готовности и требований. Строки старых планов и JSON их требований не переписываются; результаты, проверки, квитанции и интервалы сохраняются. Миграция не переводит старые планы в новый формат и не выдумывает исходный документ по историческим полям.

Новая установка применяет цепочку 0001–0020. Для существующей базы 0019 нужна только 0020. У рабочего Sites своя история миграций: необходима эквивалентная добавочная миграция в его собственном исходнике и ledger, без повторного применения канонической начальной цепочки. Этот репозиторий и локальная проверка не обновляют развёрнутый Site или отдельно установленный hosted-плагин.

Проверки: `npm test`, `npm run validate`, `npm run test:ui` и тесты `plugin/plan-time-tracker/test/*.test.mjs`. Браузерный сценарий `test/ui-plan-document.mjs` работает с реальным Worker и изолированной SQLite, проверяет создание, точный повтор после потери ответа, сохранение статусов и исходного текста, безопасность Markdown и иерархию шрифтов при ширинах 320–1920 px.
