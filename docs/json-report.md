# Аналитический JSON-отчёт, формат 1

`GET /api/export` скачивает `plan-time-tracker-export.json` владельца. Это отчёт
для анализа работы, а не резервная копия для восстановления базы. Он включает
все планы, в том числе удалённые, и всю выбранную содержательную историю.
Экспорт ничего не записывает, в том числе при первом обращении нового владельца.

Формат заменяет прежний неверсионированный документ. Потребителям старого JSON
нужно перейти с `plans[].events` на `plans[].timeline` и использовать camelCase.
Остальные API и MCP-инструменты не меняются.

## Структура

| Поле | Содержание |
| --- | --- |
| `formatVersion` | `1`, версия структуры отчёта |
| `exportedAt` | Момент, на который рассчитаны открытые интервалы |
| `timezone` | Сохранённый часовой пояс владельца; UTC для нового владельца |
| `summary` | `planCount`, `deletedPlanCount`, `measuredPlanCount`, `totalActiveMs`, `sumPlanActiveMs` |
| `plans` | Все планы владельца в порядке регистрации, затем `planId` |

Временные отметки — Unix в миллисекундах; длительности — миллисекунды.
`planCreatedAt` и `dateHistory[].previous` сохраняют исходную точность:
`{precision:"dateOnly",on,timeZone}` либо `{precision:"instant",value,timeZone}`,
где `value` — ISO 8601 UTC. Дата без времени не превращается в полночь.

Каждый план содержит `planId`, название, описание, критерии приёмки, исходную
дату, даты регистрации/первого запуска/завершения/удаления, статус и
`sourceReference`. `completion` показывает включение контроля этапов,
число незавершённых этапов и готовность к завершению. Остальные разделы:

| Раздел плана | Содержание |
| --- | --- |
| `activeMs`, `calendarMs`, `pausedMs` | Время плана; до первого запуска — `null` |
| `unattributedMs`, `ambiguousMs` | Время без однозначной привязки к этапу и его часть с перекрытием этапов |
| `intervals` | `intervalId`, `startMs`, `endMs`; у открытого интервала `endMs:null` |
| `dateHistory` | Предыдущее значение даты, момент и причина изменения |
| `assessments` | Все ревизии оценок самого плана |
| `steps` | Все этапы по `ordinal`, затем `stepId` |
| `finishExceptions` | Причина, дата и зафиксированные незавершённые этапы при явном исключении завершения |
| `timeline` | Объединённая содержательная хронология плана и трекера |

Этап содержит `stepId`, `ordinal`, название, ожидаемый результат,
`requiredChecks`, статус, даты создания/обновления, `currentResultRevision`,
`readyToFinish`, `activeMs`, `ambiguousMs` и следующие полные коллекции:

- `attempts`: идентификатор, сохранённый статус, `executionState`, `claimedAt`,
  подтверждённый `startedAt`, `closedAt`, `executionEndAt`, причина доработки
  и тип/метка исполнителя. Назначение попытки не означает начало исполнения.
  `executionEndAt` ограничен закрытием, истечением аренды и `exportedAt`;
  фактическое время дополнительно пересекается с рабочими интервалами плана.
- `results`: идентификатор, попытка, ревизия, исход, содержательное резюме,
  дата записи и разрешённые сведения об источнике результата.
- `checks`: идентификатор, ревизия результата, ключ, статус, exit code,
  описание/URL свидетельства, разрешённый digest проверенного снимка,
  `matchesResult`, дата и признак сокрытия исторического свидетельства.
- `assessments`: все ревизии оценок этого этапа.

Оценка содержит `assessmentId`, `revision`, `recordedAt`, сохранённые
`requirements`, признак `needsRevision` относительно текущих требований
и объект `assessment`. В нём сохраняются метод/шкала, сложность, контекст,
неизвестные, допущения, зависимости, прогноз, источники, подход, фаза и причина
пересмотра. Убираются только поля конверта: повторные идентификаторы цели/серии
и digest предусловия записи. Произвольные поля контекста, шкалы и других
пользовательских структур не фильтруются по совпадению с техническими именами.
Ссылки `sources` сохраняют идентификаторы целевых планов/этапов.

## Правила анализа

- Общая сводка исключает удалённые планы, но их строки и история присутствуют
  в `plans`. `planCount` — число неудалённых; `deletedPlanCount` — удалённых.
- `totalActiveMs` объединяет пересекающиеся интервалы неудалённых планов;
  `sumPlanActiveMs` суммирует время этих планов. Параллельная работа может
  делать сумму больше объединения. Без измеренных планов оба значения `null`.
- Время этапа считается только после серверного `STEP_STARTED`, до закрытия
  или истечения аренды и только внутри рабочих интервалов. Паузы не начисляются.
  При перекрытии разных этапов время не распределяется произвольно:
  оно входит в `ambiguousMs` и `unattributedMs`. Полностью неоднозначное время
  этапа обозначается `activeMs:null`; частично измеренное сохраняется вместе
  с `ambiguousMs`. Измеренный ноль отличается от отсутствия измерения.
- Удалённый план сохраняет замороженную длительность. После восстановления
  активное время не увеличивается до явного запуска таймера.
- Оценки разных методик, шкал и метрик не усредняются. Исторические снимки
  требований нужны для анализа причин пересмотра прогнозов.

## Хронология и исключённый шум

Событие содержит `eventId`, `eventType`, `occurredAt`, `recordedAt`,
содержательные `details`, а при наличии — цель этапа/попытки, `actorType`,
классификацию наблюдения и `correctionOfEventId`. Порядок определяется временем
регистрации, затем внутренним серверным порядком. Дубли события плана и трекера
объединяются по команде и типу; разные события одной команды не теряются.
Результаты и проверки представлены в событиях ссылками, их полный текст —
в соответствующих коллекциях.

Обычные `heartbeat` и `LEASE_RENEWED` исключены. Аномальные события и цели
исправлений сохраняются, даже когда исходное событие обычно считается шумом.
Наблюдения об инструментах/ходах, разрывы и исправления сохраняются.

Отчёт не включает идентификатор владельца, email, идентификаторы команд/сессий,
хеши доставки, fencing, версии конкурентной записи, разрешения UI, содержимое
квитанций, устаревшие интерфейсы Git и таблицы служебной синхронизации.
Идентификаторы сущностей, ревизии результатов/оценок и digest источника
сохраняются там, где нужны для связи и интерпретации свидетельств.
Ограничения видимости исторических источников совпадают с текущим API:
для отозванного приватного источника скрыты digest и URL свидетельства,
при этом статус и результат проверки остаются доступны.

## Полнота и согласованность

Все коллекции читаются одним SQL-запросом из одного снимка владельца,
без экранных лимитов на количество результатов, попыток или событий.
Каждая исходная строка передаётся отдельно, без одного гигантского JSON-поля
в SQLite. При ошибке чтения возвращается ошибка, а не частичный отчёт.
Большой отчёт по-прежнему ограничен ресурсами D1 и Worker; потоковая выгрузка
и восстановление базы этим форматом не предусмотрены.
