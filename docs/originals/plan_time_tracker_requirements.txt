

Учёт времени реализации планов

Техническое задание для приложения в ChatGPT Sites
Версия 1.0 · 12 октября 2026 года · Основа для последующего плана реализации
Приложение должно показывать, сколько активного времени заняла реализация каждого плана, сохранять явные начала и паузы работы и связывать результат с выбранными репозиториями GitHub. Главная единица анализа — завершённый план. Коммиты дают контекст и проверяемые ссылки, но сами по себе не измеряют трудозатраты или качество работы.

Обязательные требования пользователя
- Весь интерфейс, постоянные данные и серверная логика приложения размещаются в Sites. GitHub остаётся внешним источником данных. Отдельный собственный backend не допускается.
- Можно выбрать публичные и приватные репозитории GitHub и период дат, видеть аналитику длительности реализации функциональности.
- GPT, другие агенты и dot получают единый skill для регистрации плана, даты его составления и явного начала реализации. Доступны пауза, продолжение и завершение.
- У владельца приложения одновременно выполняется не больше одного плана. Кнопка «Завершить» фиксирует итоговое активное время.
- Интерфейс должен быть аккуратным и понятным: без перегруженной панели показателей и без вида незавершённого прототипа.

Предлагаемые границы первой версии
Один владелец и приватное приложение; один план может охватывать один или несколько подключённых репозиториев. Учёт ведётся по ручным или агентским командам Start, Pause, Resume и Finish. Источник истины — сохранённые на сервере интервалы, а не часы вкладки. Название в документе рабочее.
Один владелец, несколько репозиториев на план и остальные границы MVP ниже — предлагаемые проектные решения. От автоматического рабочего расписания пользователь отказался: сохраняются явные Start, Pause, Resume и Finish; включённый таймер продолжает идти ночью и в выходные.

За пределами MVP
Командные роли, оплата труда, рейтинги разработчиков, календарь праздников, автоматическое распознавание фич по тексту коммитов, запись экрана, контроль присутствия, постоянные webhooks и незапрошенные уведомления. Никакой фиктивной оценки прогресса в процентах по числу коммитов.

Коды требований для приёмки
R01 — репозитории и период; R02 — регистрация плана; R03 — жизненный цикл; R04 — один RUNNING; R05 — точный расчёт времени; R06 — связь коммитов; R07 — аналитика; R08 — skill и общий контракт; R09 — интерфейс; R10 — приватность и надёжность.

Как использовать документ
Сначала проверить ограничения платформы в разделе 1. Затем согласовать открытые продуктовые вопросы и составить план реализации по проверенным возможностям. Контракты и названия операций ниже описывают требуемое поведение; они не заявляют, что такие API уже существуют в Sites.


1 Проверка возможностей Sites

Ограничение «всё приложение в Sites» является обязательным. Базовый путь платформы: интерфейс Vinext, серверный Worker, база D1, идентификация ChatGPT для конкретного Site, runtime-секреты и Site MCP через POST /mcp с платформенной авторизацией. Этот набор позволяет проектировать приложение без собственного внешнего backend; работоспособность конкретной интеграции ещё требуется доказать.
Проверка | Что требуется доказать | Что делать при отрицательном результате
G1 Приватность | Одинаковый owner в UI и MCP; серверная проверка каждой записи; отсутствие доступа к чужим данным в опубликованной версии. | Остановить часть с приватными данными; не подменять приватность скрытой ссылкой.
G2 D1 и конкуренция | Атомарная смена плана, интервала, события и command receipt; уникальное ограничение RUNNING и тест двух конкурентных команд в D1. | Не заменять блокировку проверкой в браузере; пересогласовать архитектуру.
