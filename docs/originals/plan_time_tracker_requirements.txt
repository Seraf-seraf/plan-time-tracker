

Учёт времени реализации планов

Техническое задание для приложения в ChatGPT Sites
Версия 1.0 · 12 октября 2026 года · Основа для последующего плана реализации
Приложение должно показывать, сколько активного времени заняла реализация каждого плана, сохранять явные начала и паузы работы и связывать результат с выбранными репозиториями GitHub. Главная единица анализа — завершённый план. Коммиты дают контекст и проверяемые ссылки, но сами по себе не измеряют трудозатраты или качество работы.

Обязательные требования пользователя
- Весь интерфейс, постоянные данные и серверная логика приложения размещаются в Sites. GitHub остаётся внешним источником данных. Отдельный собственный backend не допускается.
- Можно выбрать публичные и приватные репозитории GitHub и период дат, видеть аналитику длительности реализации функциональности.
- GPT, другие агенты и dot получают единый skill для регистрации плана, даты его составления и явного начала реализации. Доступны пауза, продолжение и завершение.
- У владельца приложения одновременно выполняется не больше одного плана. Кнопка «Завершить» фиксирует итоговое активное время.
- Интерфейс должен быть аккуратным и понятным: без перегруженной панели показателей и без вида незавершённого прототипа.

Предлагаемые границы первой версии
Один владелец и приватное приложение; один план может охватывать один или несколько подключённых репозиториев. Учёт ведётся по ручным или агентским командам Start, Pause, Resume и Finish. Источник истины — сохранённые на сервере интервалы, а не часы вкладки. Название в документе рабочее.
Один владелец, несколько репозиториев на план и остальные границы MVP ниже — предлагаемые проектные решения. От автоматического рабочего расписания пользователь отказался: сохраняются явные Start, Pause, Resume и Finish; включённый таймер продолжает идти ночью и в выходные.

За пределами MVP
Командные роли, оплата труда, рейтинги разработчиков, календарь праздников, автоматическое распознавание фич по тексту коммитов, запись экрана, контроль присутствия, постоянные webhooks и незапрошенные уведомления. Никакой фиктивной оценки прогресса в процентах по числу коммитов.

Коды требований для приёмки
R01 — репозитории и период; R02 — регистрация плана; R03 — жизненный цикл; R04 — один RUNNING; R05 — точный расчёт времени; R06 — связь коммитов; R07 — аналитика; R08 — skill и общий контракт; R09 — интерфейс; R10 — приватность и надёжность.

Как использовать документ
Сначала проверить ограничения платформы в разделе 1. Затем согласовать открытые продуктовые вопросы и составить план реализации по проверенным возможностям. Контракты и названия операций ниже описывают требуемое поведение; они не заявляют, что такие API уже существуют в Sites.


1 Проверка возможностей Sites

Ограничение «всё приложение в Sites» является обязательным. Базовый путь платформы: интерфейс Vinext, серверный Worker, база D1, идентификация ChatGPT для конкретного Site, runtime-секреты и Site MCP через POST /mcp с платформенной авторизацией. Этот набор позволяет проектировать приложение без собственного внешнего backend; работоспособность конкретной интеграции ещё требуется доказать.
Проверка | Что требуется доказать | Что делать при отрицательном результате
G1 Приватность | Одинаковый owner в UI и MCP; серверная проверка каждой записи; отсутствие доступа к чужим данным в опубликованной версии. | Остановить часть с приватными данными; не подменять приватность скрытой ссылкой.
G2 D1 и конкуренция | Атомарная смена плана, интервала, события и command receipt; уникальное ограничение RUNNING и тест двух конкурентных команд в D1. | Не заменять блокировку проверкой в браузере; пересогласовать архитектуру.
G3 GitHub | Вызовы GitHub из runtime Sites с доступом к выбранным приватным репозиториям, пагинацией и обновлением полномочий. | Подключение GitHub к чату не считать автоматическим доступом приложения; запросить поддерживаемый путь.
G4 MCP и skill | Реальный вызов Site MCP из поддерживаемого клиента; платформенная авторизация, тождество владельца, общий командный слой с UI и идемпотентность. | Skill не объявлять рабочим. Демо с ручным вводом допустимо лишь после отдельного согласования сокращённого объёма.
G5 Секреты и отзыв | GitHub credentials не попадают во frontend, журнал или экспорт; проверен отзыв доступа и отключение. | Не хранить токен в localStorage, HTML или файле skill; приватный GitHub блокирован.
G6 Эксплуатация | Лимиты запросов, объём данных, длительность операций, журналирование и восстановление; работа после публикации. | Снизить объём первой загрузки или дать явное ограничение; не обещать фоновые функции без проверки.

Допустимая логическая архитектура
Веб-интерфейс Sites и внешние агенты вызывают единый командный слой в Sites. Он проверяет личность, версию и инварианты, сохраняет события и интервалы, возвращает серверное время. Модуль синхронизации читает GitHub через поддерживаемую авторизацию. Модуль аналитики читает те же интервалы и метаданные коммитов.
Ни прокси-сервер вне Sites, ни отдельная база, ни клиентский секрет не являются допустимой незаметной заменой. D1 является исходным выбором хранилища, Site MCP — каналом для агентов. Точная схема атомарных операций, права и связь идентичностей фиксируются по G1–G5. Возможность приватного GitHub из runtime пока не установлена; ручное чтение в чате её не доказывает.

Важно для внешнего skill
Skill описывает протокол поверх Site MCP; он не заменяет авторизацию. Планируемый путь — приватный плагин с MCP и инструкцией skill, без ключей в тексте. Совместимость каждого требуемого клиента, установка и доступ владельца проверяются отдельно; нельзя обещать универсальную работу во всех GPT и агентах.


2 Модель данных и источники истины

Сущность | Основные поля и ограничения
Owner | ownerId; IANA timeZone; locale; настройки. ownerId определяется аутентификацией, не доверяется входному полю.
Plan | planId UUID; ownerId; title; description; acceptanceCriteria; planCreatedAt; registeredAt; status; firstStartedAt; finishedAt; version; createdBy; sourceReference.
PlanRepository | planId + repositoryId; выбранная ветка или ref; один или несколько репозиториев. Привязка по GitHub ID; набор и refs фиксируются первым Start.
WorkInterval | intervalId; planId; startAt; endAt nullable; openedBy; closedBy. Полуинтервал [startAt, endAt); endAt ≥ startAt; не более одного открытого.
PlanEvent | eventId; commandId; planId; actorId/type; eventType; serverOccurredAt; versionBefore/After; причина. События не перезаписываются.
CommandReceipt | ownerId + commandId UNIQUE; payloadHash; outcome; resultVersion; result snapshot; recordedAt. Нужен для безопасных повторов.
Repository и SyncState | GitHub repositoryId; owner/name; private; selected; refs; accessState; lastSuccessfulSyncAt; cursor/checkpoint; completeness; lastError.
Commit | repositoryId + SHA UNIQUE; authorAt; committerAt; observedAt; author/committer GitHub ID когда доступен; message; URL; parents; refs.
PlanCommitLink | planId + repositoryId + SHA; status confirmed/candidate/excluded; basis marker/manual/time; reason; reviewedBy/At; history.

Даты составления и регистрации
planCreatedAt — фактическая дата составления плана, явно переданная пользователем или агентом. registeredAt — неизменяемый момент регистрации в приложении по серверным часам. Они могут различаться. Если точный момент неизвестен, сохраняется точность dateOnly и исходная зона; приложение не придумывает время 00:00 как точный факт.
Изменение planCreatedAt сохраняет старое значение, автора и причину в истории. Дата после первого старта вызывает проверку: подтвердить ошибку дат или скорректировать запись. Метрика ожидания старта выводится только при достаточной точности и согласованности дат.

Обязательные инварианты
- Все пользовательские записи привязаны к ownerId; связи между разными владельцами невозможны. Для ownerId число RUNNING ≤ 1.
- RUNNING имеет ровно один открытый интервал; остальные состояния не имеют открытых интервалов. Интервалы одного плана не пересекаются.
- firstStartedAt задаётся только первым Start и больше не меняется. finishedAt задаётся успешным Finish. Итоги вычисляются из интервалов, кэш проверяем и восстанавливаем.
- Идентификаторы событий, интервалов и команд стабильны. Повтор синхронизации GitHub не создаёт новый коммит для той же пары repositoryId + SHA.


3 Состояния и согласованность команд

Из состояния | Команда | В состояние | Атомарные изменения
Нет плана | Create | PLANNED | Создать план и событие; не создавать интервал.
PLANNED | Start | RUNNING | Проверить глобальный слот; занять его; установить первый старт; открыть интервал.
RUNNING | Pause | PAUSED | Закрыть открытый интервал; освободить слот; записать событие.
PAUSED | Resume | RUNNING | Проверить и занять глобальный слот; открыть новый интервал.
RUNNING | Finish | COMPLETED | Закрыть интервал; освободить слот; зафиксировать finishedAt и итог.
PAUSED | Finish | COMPLETED | Не добавлять активное время после паузы; зафиксировать finishedAt и итог.
Start для уже запущенного плана с новым commandId — ошибка перехода, а не новый интервал. Resume для PLANNED и Finish для PLANNED также отклоняются. В MVP COMPLETED терминален: новое продолжение работы регистрируется отдельным планом. Редактирование описания не меняет историю времени.

Атомарность и конкуренция
Проверка состояния, версии, глобального слота, запись события, изменение плана и интервала выполняются в одной транзакции или эквивалентной доказанной атомарной операции. Уникальное ограничение действует на сервере. Два одновременных старта разных планов дают один успех и один ACTIVE_PLAN_EXISTS. Существующий план автоматически не ставится на паузу.
Каждая изменяющая команда содержит expectedVersion. После любого изменения версия растёт. Устаревшая версия даёт VERSION_CONFLICT вместе с текущей версией и состоянием; клиент перечитывает план и не повторяет опасное действие вслепую. Агент не завершает чужую сессию только потому, что его локальное состояние устарело.

Идемпотентность
commandId создаётся один раз на конкретное намерение и повторяется при сетевых повторах. Повтор того же ID с тем же payloadHash возвращает исходный результат без нового события; тот же ID с другим содержимым даёт IDEMPOTENCY_KEY_REUSED. Новый цикл Pause/Resume получает новые ID. Ключ вида «пользователь + план + действие» запрещён: он склеивает законные повторные циклы.
Сохранённый ответ проверяется до повторного применения expectedVersion: сетевой повтор уже выполненной команды должен успешно вернуть прежний результат даже после следующих изменений. Для MVP предлагается хранить журнал commandId без автоматического удаления; срок хранения можно уменьшать только после определения безопасного горизонта повторов.

Исправление пропущенных пауз
Предлагаемое расширение после MVP — отдельная команда корректировки интервалов с причиной, проверкой пересечений и историей до/после. До её появления таймер отражает зафиксированные команды. Длительная непрерывная сессия помечается для проверки; приложение не вычитает ночь или выходные самостоятельно.


4 Время и фильтры дат


Единицы и формулы
Все точные моменты сохраняются в UTC с миллисекундами, передаются как ISO 8601 с Z или явным смещением. Настройка IANA timeZone используется для ввода календарных дат и отображения. Сервер выдаёт serverNow; клиентский таймер между ответами служит только визуализацией. Итоги хранятся или вычисляются в целых миллисекундах, округляются один раз при показе.
Для интервала [sᵢ, eᵢ) и момента расчёта t открытый конец принимается равным t. Active(t) = Σ max(0, eᵢ* − sᵢ), где eᵢ* = eᵢ для закрытого интервала и t для открытого. Calendar(t) = конечный момент − firstStartedAt. Paused(t) = Calendar(t) − Active(t). Для PLANNED эти значения не определены, а не равны нулю.
Конечный момент — finishedAt для COMPLETED и t для RUNNING/PAUSED. Ожидание начала = firstStartedAt − planCreatedAt; оно показывается отдельно и только при точной непротиворечивой дате составления. План без выполненных интервалов не включается в выборку длительности завершённых планов.

Единая семантика периода
Выбор дат «с A по B» включает весь день B в выбранной зоне: запрос превращается в UTC-полуинтервал [начало A, начало дня после B). Нельзя прибавлять ровно 24 часа в зоне с переходом летнего времени. Пустой или обратный диапазон даёт валидационную ошибку.
Главный график «Активное время за период» обрезает каждый рабочий интервал по границам периода: Σ max(0, min(eᵢ*, B) − max(sᵢ, A)). «Завершено за период» отбирает планы по finishedAt ∈ [A,B); медиана в этой карточке использует полную активную длительность этих планов. Подписи исключают смешение двух выборок.
Фильтр репозиториев отбирает планы, имеющие хотя бы одну связь с выбранным набором. Часы такого плана учитываются один раз. Для MVP распределение времени многорепозиторного плана между репозиториями не вычисляется. Смена фильтра никогда не меняет сохранённые интервалы или итог плана.

Пример с паузой на выходные
Событие | Местное время Europe/Moscow | Следствие
Start | Пятница 9 октября 2026, 16:00 | Открыт первый интервал.
Pause | Пятница 9 октября 2026, 18:00 | Первый интервал равен 2 часам.
Resume | Понедельник 12 октября 2026, 10:00 | Открыт второй интервал.
Finish | Понедельник 12 октября 2026, 12:30 | Второй интервал равен 2 часам 30 минутам.
Итог: активное время 4 ч 30 мин; от старта до завершения 68 ч 30 мин; паузы 64 ч. За период только понедельника активное время равно 2 ч 30 мин, а полная длительность завершённого в понедельник плана для медианы равна 4 ч 30 мин. Без команды Pause выходные вошли бы в активное время.


5 Связь планов и коммитов

Единственный активный план уменьшает неоднозначность, но не доказывает причинную связь с каждым коммитом. В выбранном репозитории могли работать другие люди, автоматизация или параллельный процесс. Атрибуция всегда сохраняет источник и допускает явное исключение.

Правила подтверждённой связи
- Явный маркер в сообщении: отдельная строка Plan-ID: <полный planId>. Маркер считается точным только при однозначном существующем planId того же владельца и репозитории, привязанном к плану. Подстроки и приблизительные совпадения не допускаются.
- Альтернативно пользователь или уполномоченный агент выбирает конкретную пару repositoryId + SHA и подтверждает связь. Записываются автор решения, время и основание.
- Маркер — заявление об отнесении коммита, а не криптографическое доказательство выполненной работы. Явное исключение владельца имеет приоритет; неизвестный план, несколько разных маркеров или неподходящий репозиторий дают конфликт для проверки.

Кандидаты без маркера
Коммит становится кандидатом, если он принадлежит выбранному репозиторию и отслеживаемому ref, проходит авторский фильтр, а committerAt попадает в один из активных интервалов плана. Результат остаётся candidate до подтверждения. Правило не переносит кандидатов в «связанные» молча и не меняет длительность плана.
Авторский фильтр опирается на устойчивый GitHub user ID, когда API его предоставляет. author и committer показываются отдельно. Совпадение имени или email само по себе недостаточно; неопознанный автор и bot-аккаунт дают явную метку. Исполнитель плана хранится отдельно от автора коммита.

Исключения и необычные случаи
Случай | Поведение
Коммит в паузе или после Finish | Не кандидат по времени. Может иметь явную связь по маркеру или ручному решению с видимым основанием; таймер не продлевается.
Один SHA в нескольких refs | Одна запись внутри репозитория; принадлежность refs хранится отдельно. Один и тот же SHA в другом репозитории — другая пара ключей.
Несколько планов для одного коммита | Для MVP подтверждённая связь допускается только с одним планом на владельца. Конфликт требует выбора; автоматического размножения нет.
Squash, rebase, cherry-pick | Новый SHA — новый объект. Связь не переносится по похожему тексту. Старый SHA, если исчез из ref, остаётся в истории с признаком недоступности.
Merge и боты | Помечаются отдельно; фильтр влияет на контекст коммитов, но не пересчитывает время. Политика включения видна рядом с количеством.
Явное исключение | Сохраняется excluded с причиной. Повтор синхронизации не превращает его обратно в candidate или confirmed.

Граница автоматизации
Импорт истории GitHub не восстанавливает реальное активное время: промежутки между коммитами не равны рабочим сессиям. Старые планы допускается зарегистрировать с прежней датой составления, но без измеренных интервалов они помечаются «нет данных о времени» и не улучшают статистику нулями.


6 GitHub и обновление данных


Выбор репозиториев и полномочий
Приложение показывает только репозитории, доступные в проверенном подключении, с owner/name и признаком private. Владелец явно выбирает рабочий набор. Первичный ref — текущая default branch как предлагаемое значение; другая ветка выбирается явно. Выбор сохраняется с GitHub repositoryId, поэтому переименование не создаёт дубликат.
Предпочтителен официальный механизм ограниченного чтения только выбранных репозиториев. Если поддерживаемый путь использует GitHub App или fine-grained token, запросить необходимые read-only Metadata и Contents; точный набор проверить для выбранных API. Широкий классический scope repo, запись кода, issues и pull requests не требуются MVP. Доступ организации может отдельно зависеть от её политики и одобрения. [1–4]
Подключённый GitHub в ChatGPT не считается доказательством наличия runtime-авторизации в Sites. Допускается лишь подтверждённый безопасный способ хранения и обновления полномочий. Создание постоянного доступа выполняется через поддерживаемое согласие владельца, а не через вставку токена в чат.

Синхронизация первой версии
- Запуск при явном «Обновить» и при открытии приложения, если кэш устарел; конкретный интервал свежести назначается после проверки лимитов. Фоновые задания и webhooks не обязательны для MVP.
- Загрузка постраничная, с ограниченной первой выборкой и видимым прогрессом. Курсор и успешный checkpoint фиксируются только после сохранения порции. Повторная порция безопасна благодаря repositoryId + SHA.
- Хранить authorAt, committerAt и observedAt отдельно. В интерфейсе и отборе по времени использовать явно выбранное committerAt; семантику since/until upstream API проверить, применять итоговую фильтрацию в приложении.
- Инкрементальный запрос имеет перекрытие предыдущего диапазона и дедупликацию. Перекрытие не гарантирует обнаружение любой переписанной истории: отдельное ручное обновление ref сверяет доступный диапазон заново.
- При HTTP 429 или ограничении GitHub учитывать Retry-After и reset, делать ограниченные повторы с backoff, не запускать цикл опроса. Ошибка одной страницы не превращает частичную выборку в полную. [5–6]

Состояния подключения
Каждый репозиторий имеет состояние «актуально», «обновляется», «частичные данные», «нет доступа» или «ошибка», а также lastSuccessfulSyncAt. Отзыв прав, отключение подключения и смена видимости останавливают новые загрузки. HTTP 404 приватного репозитория не интерпретируется как доказанное удаление.
Отключение GitHub сохраняет собственную историю планов и времени. Предлагаемая политика для MVP: скрывать кэш приватных commit-данных до повторной авторизации и предоставлять явное удаление кэша. Удаление не должно повреждать интервалы или незаметно менять прошлые итоговые длительности. Политику хранения необходимо подтвердить до публикации.


7 Метрики и аналитические выборки

Главный вопрос — как долго реализуются планы и как эта длительность меняется в сопоставимой работе. Приложение не делает вывода о качестве человека, полезности кода или стоимости труда из количества коммитов.
Показатель | Расчёт и выборка | Как показывать
Активное время за период | Сумма пересечений рабочих интервалов с периодом; выбранные планы без дублирования. | Часы и минуты; разбивка по дням в выбранной зоне.
Завершено планов | COUNT DISTINCT planId с finishedAt внутри периода. | Число и ссылку на перечень планов.
Медиана реализации | Медиана полной Active(finishedAt) завершённых в периоде планов с достоверными интервалами. | Длительность и N; при N < 5 метка «малая выборка».
Время от старта до завершения | finishedAt − firstStartedAt для каждого завершённого плана. | В карточке плана рядом с активным временем; паузы отдельно.
Ожидание начала | firstStartedAt − planCreatedAt при точных согласованных датах. | В карточке, не в главном KPI; отсутствие точности отображается явно.
Связанные коммиты | Количество уникальных подтверждённых repositoryId + SHA; кандидаты отдельно. | Контекст результата. Число коммитов не называется скоростью.
Незавершённые планы | Текущее состояние и накопленное активное время на serverNow. | Отдельный список; не включать в медиану завершённых.

Сравнение и ограничения
В MVP сравниваются отдельные планы и периоды с явной выборкой; без нормализации по сложности нельзя утверждать, что разработка стала продуктивнее. Изменение медианы само по себе не доказывает ускорение одинаковой работы. История длительности полезна для последующего планирования похожих задач.
Функциональность в MVP соответствует одному плану с описанным результатом. Автоматическое выделение фич из коммитов и сравнение по оценке сложности откладываются. Опциональная метка типа работы допустима позднее; она не нужна для честного первого таймера.

Пустые и неполные данные
Нет завершённых планов — показывать «пока нет завершённых планов», не медиану 0. Недоступные GitHub-данные не стирают время реализации. При неполной синхронизации коммитов количество маркируется как неполное, а временные метрики по сохранённым интервалам остаются доступны.
Карточка плана показывает качество учёта: измерено командами, отсутствуют интервалы или есть предупреждение о длинной непрерывной сессии. Без исправлений истории предупреждение само по себе не вычитает часы и не прячет план из выборки. Любое исключение из метрик должно иметь явное основание и быть видно пользователю.

Рабочее расписание исключено
Пользователь отказался от автоматического учёта рабочего расписания. В текущем объёме нет рабочих окон, праздников, автопауз по календарю или автоматического вычитания ночей и выходных. Время в состоянии RUNNING учитывается непрерывно до явной Pause или Finish.


8 Интерфейс и визуальные требования


Экран обзора
Вверху компактный выбор репозиториев и периода, затем текущий план с названием, статусом и главным таймером. Рядом только доступные действия: «Начать», «Пауза», «Продолжить», «Завершить». Текущий RUNNING виден даже вне выбранных репозиториев или периода. При запуске другого плана отображается активный план и предложение открыть его; автоматического переключения нет.
Ниже три показателя: активное время за период, завершённые планы, медиана реализации с N. Один спокойный график активного времени по дням и список планов с названием, статусом, активной длительностью и датой завершения. По умолчанию список содержит планы с активностью внутри периода; нажатие «Завершено» открывает выборку по finishedAt. PLANNED и PAUSED без активности доступны в отдельном фильтре состояния. Детали синхронизации раскрываются по необходимости.

Экран плана
Название и ожидаемый результат; критерии готовности; дата составления и регистрации; репозитории; статус и действия. Дальше компактные активное и календарное время, лента интервалов и событий, раздел коммитов с вкладками «Связанные», «Кандидаты», «Исключённые». У каждой связи доступно объяснение основания и ссылка на GitHub.
При Finish показать итог и короткое подтверждение «Завершить план?» с текущим активным временем. Кнопка в ожидании ответа блокируется визуально, но серверная идемпотентность остаётся обязательной. Если пользователь не уверен в выполнении критериев, он может вернуться в карточку без изменения состояния.

Экран подключений и настроек
Состояние GitHub, перечень выбранных репозиториев и refs, права и время обновления, часовая зона. Здесь же подключения внешних агентов, если путь G4 подтверждён. Секреты не показываются после создания; отключение и удаление локального кэша имеют понятное описание последствий.

Дизайн без перегрузки
- Русский интерфейс; единая сетка, типографическая иерархия, умеренные отступы, спокойные нейтральные поверхности и один цвет акцента для главного действия.
- Статус всегда имеет текст, не только цвет. Красный используется для ошибки или опасного действия. Время показывается одинаково: «4 ч 30 мин» в итогах и часы с секундами только у работающего таймера.
- Не использовать пёстрые KPI-карточки, декоративные графики, leaderboard, громоздкий сайдбар и отдельный экран для каждой настройки. Сложные поля прятать в раскрываемые детали без потери доступности.
- Работа клавиатурой, видимый focus, подписи полей, достаточный контраст и поддержка уменьшенного движения. Цель — WCAG 2.2 AA для основных сценариев. [7]
- Проверить ширины 360, 768 и 1440 px. На телефоне главные действия остаются доступными, длинные SHA и названия не вызывают горизонтальную прокрутку всей страницы.

Обязательные состояния
Первое открытие без подключения, пустой список планов, загрузка, RUNNING, PAUSED, завершённый план, конфликт другого активного плана, устаревшая версия, offline, отозванные права и частичная синхронизация. Ошибка объясняет, сохранено ли действие и какой следующий шаг безопасен.


9 Контракт команд приложения

Это логический контракт, общий для UI и skill. Для агентов исходный транспорт — инструменты Site MCP через POST /mcp с платформенной авторизацией. Имена ниже обозначают будущие доменные операции, а не готовые функции сайта; их schema и отображение в MCP-tools уточняются в G4.
Операция | Вход кроме общего конверта | Ответ
CreatePlan | title, description, acceptanceCriteria, repositoryIds/refs, planCreatedAt + precision + timezone, sourceReference optional | planId, status PLANNED, registeredAt, version.
GetPlan / GetActivePlan | planId либо текущий owner | План, интервалы, рассчитанный итог, version, serverNow.
StartPlan | planId, expectedVersion | RUNNING, firstStartedAt, openIntervalId, version.
PausePlan | planId, expectedVersion, reason optional | PAUSED, closedIntervalId, activeMs, version.
ResumePlan | planId, expectedVersion | RUNNING, openIntervalId, activeMs, version.
FinishPlan | planId, expectedVersion, completionNote optional | COMPLETED, finishedAt, activeMs, calendarMs, version.
UpdatePlanMetadata | planId, expectedVersion, изменяемые поля; reason при смене даты | Обновлённые поля и version; история времени неизменна.
ReviewCommitLink | planId, repositoryId, SHA, confirmed/excluded, basis, reason | Сохранённое решение и версия связи.
SyncRepository / GetAnalytics | repositoryId/ref или rangeStart/rangeEnd/timeZone/repositoryIds | Статус sync либо метрики с определениями выборок и полнотой данных.

Общий конверт изменяющей команды
schemaVersion, commandId, expectedVersion при изменении существующего объекта, payload; опционально sourceReference и actorLabel для отображения. Подлинный actorId и ownerId устанавливаются по проверенным полномочиям. payloadHash вычисляется по канонической структуре команды на сервере. Timestamp клиента не заменяет serverOccurredAt.
Успех возвращает commandId, applied true/false, текущий snapshot результата команды, serverOccurredAt, serverNow и resultingVersion. Повтор выполненной команды возвращает applied false и исходный результат, а не повторяет действие. Для аналитики возвращается asOf, чтобы все открытые интервалы рассчитывались на один момент.

Ошибки как часть протокола
VALIDATION_ERROR — неверные поля; NOT_AUTHENTICATED / FORBIDDEN — нет полномочий; PLAN_NOT_FOUND — недоступный объект; INVALID_TRANSITION — неверное состояние; ACTIVE_PLAN_EXISTS — занят глобальный слот; VERSION_CONFLICT — устаревшее состояние; IDEMPOTENCY_KEY_REUSED — ID использован иначе; SOURCE_UNAVAILABLE — GitHub временно недоступен; RATE_LIMITED — нужна задержка; INTERNAL_ERROR — неизвестный сбой.
Ошибки содержат requestId, безопасное сообщение, retryable и при необходимости retryAfter. Никаких токенов, чужих идентификаторов или содержимого приватных репозиториев. HTTP-коды назначаются по поддерживаемому транспорту; семантика ошибок не зависит от него.


10 Требования к skill для GPT и агентов

Skill должен быть небольшой версионируемой инструкцией с описанием инструментов, предусловий, примеров и обработки ошибок. Он использует общий контракт, не вычисляет время по переписке и не хранит ключи. Наличие инструкции само по себе не означает, что она установлена во всех клиентах или даёт доступ к Sites.

Протокол работы
Шаг | Обязательное поведение агента
1 Создать план | Когда содержательный план составлен, вызвать CreatePlan с явной датой составления, критериями готовности и выбранными репозиториями. Сохранить возвращённый planId в контексте задачи.
2 Проверить доступ | Прочитать GetActivePlan и свой план. При неизвестном owner, недоступном инструменте или неоднозначном репозитории остановить изменение и объяснить, чего не хватает.
3 Начать | Непосредственно перед реализацией вызвать StartPlan и дождаться подтверждения. Подготовка плана не является началом реализации.
4 Работать | Сохранять planId в согласованном маркере коммитов, когда агент уполномочен создавать коммиты. Не менять чужие сообщения коммитов только ради учёта.
5 Поставить на паузу | При явном перерыве, передаче работы или ожидании внешнего решения вызвать PausePlan. Повторяется тот же commandId при неопределённом сетевом исходе.
6 Продолжить | Прочитать актуальную version; вызвать ResumePlan, если глобальный слот свободен. При конфликте не останавливать другой план автоматически.
7 Завершить | Сверить критерии готовности и полномочия; вызвать FinishPlan один раз; передать пользователю сохранённый итог и ссылку на план. Если готовность не установлена, оставить паузу или работающий статус с честным объяснением.

Что считается активной реализацией
Предлагаемое правило MVP: активный интервал охватывает работу по плану, включая необходимые запущенные тесты и сборку, пока исполнитель продолжает эту задачу. Ожидание ответа пользователя, отложенное продолжение и работа над другим планом требуют паузы. Это elapsed-время выполнения плана, а не сумма человеко-часов и машинного CPU-времени.
Если несколько агентов помогают одному плану одновременно, их работа не суммируется: один общий интервал идёт по настенным часам. Потеря связи или аварийное завершение агента не создаёт достоверную паузу задним числом. При следующем открытии приложение показывает незавершённый интервал для проверки.

Пакет skill для приёмки
Должны быть подготовлены инструкция, schemaVersion, декларация операций и полей, пример полного цикла, примеры повторной доставки и конфликта, правила хранения commandId и условия паузы. Как минимум два независимых клиента проходят один набор контрактных тестов. Механизм установки и обновления skill зависит от возможностей конкретных клиентов и проверяется отдельно.


11 Надёжность безопасность и ограничения


Нестабильная сеть и несколько устройств
Таймер продолжает идти по серверному открытому интервалу после закрытия вкладки. При offline UI показывает последнее подтверждённое состояние и предупреждение. Изменяющие команды не объявляются успешными до ответа. В MVP offline-команды не исполняются автоматически позже: это создало бы неоднозначные моменты Start/Pause.
Если запрос ушёл, но ответ потерян, клиент повторяет тот же commandId и при необходимости перечитывает состояние. Нельзя посылать новый Start только потому, что старая кнопка ещё показывает загрузку. После возврата сети все расчёты синхронизируются с serverNow, а новое действие использует актуальную version.

Защита данных
- Серверная проверка ownerId обязательна для чтения, записи, аналитики, синхронизации и прямых ссылок. Приватность проверяется из другой учётной записи и без авторизации.
- Секреты находятся только в поддерживаемом защищённом механизме платформы. В браузере, исходном HTML, экспорте и журнале не должно быть токена GitHub или агента.
- Хранить только нужные метаданные коммитов; не загружать diff и исходники ради таймера. Авторские email не сохранять без обоснованной необходимости; публичное отображение private-данных исключено.
- Описание плана и сообщения коммитов считаются недоверенным текстом: экранирование при выводе, безопасные URL. Текст коммита не может дать агенту команду, сменить репозиторий или расширить доступ.
- Отзыв внешнего доступа и удаление данных — отдельные операции с подтверждением последствий. До публикации определить экспорт, срок хранения журналов и поддерживаемый способ полного удаления пользовательских данных.

Наблюдаемость и восстановление
Журнал связывает requestId, commandId и outcome без секретов. Нужны диагностика конфликтов, ошибок синхронизации, длительности запросов и нарушения инвариантов. После ошибки атомарной команды не остаётся полуоткрытого слота или события без интервала. Итоги можно воспроизвести из данных и сопоставить с историей событий.
Способ резервирования и восстановления зависит от Sites и проверяется G6. Нельзя обещать backup, постоянный cron или webhooks до подтверждения платформой. Для первого релиза требуется хотя бы доказанный способ выгрузить собственные планы, интервалы и события в переносимом формате; приватные GitHub-данные в экспорт включаются только явно.

Предлагаемый тестовый объём и отзывчивость
Для планирования использовать стартовый профиль: 10 репозиториев, 1 000 планов, 10 000 интервалов и 50 000 метаданных коммитов. Это тестовый ориентир, не гарантированный лимит Sites. Цель: UI подтверждает локальное нажатие сразу; обычная серверная команда p95 ≤ 2 с, обзор из кэша ≤ 3 с в зафиксированных условиях. Большой импорт показывает прогресс и не блокирует таймер.
Согласовать реальные пределы после G6. Падение GitHub не должно мешать Start/Pause/Finish, если выбранные репозитории уже зарегистрированы; временные данные сохраняются независимо от доступности внешней синхронизации.


12 Приёмка основных требований

Каждый тест выполняется на опубликованной версии, а не только в предпросмотре. В отчёте фиксируются исходные данные, действие, фактический результат и доказательство. Время в тестах управляется через поддерживаемые тестовые часы или воспроизводимый набор интервалов.
Тест | Требования | Сценарий и критерий успеха
A01 | R01 R10 | Владелец выбирает публичный и разрешённый приватный репозиторий. Другая учётная запись и анонимный запрос не читают приватные данные и планы.
A02 | R02 R03 | Создать план с датой составления за вчера. registeredAt соответствует серверу сейчас; статус PLANNED; нет интервала и активного таймера.
A03 | R03 R05 | Start → 2 ч → Pause → 64 ч → Resume → 2 ч 30 мин → Finish: Active 4 ч 30 мин, Calendar 68 ч 30 мин, Paused 64 ч. Отдельно Finish из PAUSED не добавляет времени; Finish из PLANNED отклонён.
A04 | R04 R08 | Два устройства или агента одновременно запускают разные планы. Ровно один RUNNING и один открытый интервал; второму возвращён конфликт.
A05 | R03 R10 | Доставить один Pause трижды с одинаковым commandId. Одно событие и один закрытый интервал. Затем новый Resume и новый Pause работают.
A06 | R08 R10 | Потерять ответ успешного Finish, повторить тот же ID после других чтений. Возвращён прежний итог без нового завершения; другой payload с тем же ID отклонён.
A07 | R03 R10 | Отправить Resume с устаревшей version. Получить VERSION_CONFLICT; никаких изменений, автопаузы другого плана или скрытого повтора.
A08 | R05 R07 | Пятнично-понедельничный пример: фильтр понедельника даёт 2 ч 30 мин активности и медиану 4 ч 30 мин для одного завершённого плана.
A09 | R01 R05 | Проверить полночь и день смены DST. Интервал на правой границе не включён; выбранный местный день длится корректные 23/24/25 часов.
A10 | R01 R07 | План связан с двумя выбранными репозиториями. Его часы и количество завершённых планов в общей выборке не удваиваются.
A11 | R06 | Коммит другого автора в активном окне остаётся без подтверждения. Кандидат не учитывается как подтверждённый; excluded сохраняется после повторного sync.
A12 | R06 | Точный маркер правильного плана создаёт связь с видимым основанием. Неверный repo, неизвестный planId или два разных маркера дают конфликт.
A13 | R06 R07 | Коммит после Finish с явной связью добавляется в контекст. Итоговое время плана остаётся прежним; незавершённый план не входит в медиану.
A14 | R06 R10 | Повторно импортировать страницы, merge и один SHA в нескольких refs. Нет дубликатов по repositoryId + SHA; новый SHA после rebase не связывается по догадке.


13 Приёмка эксплуатации и планирование

Тест | Требования | Сценарий и критерий успеха
A15 | R05 R09 | Закрыть и открыть вкладку RUNNING. Накопленное время восстановлено с сервера; часы компьютера, изменённые на час, не меняют итог.
A16 | R09 R10 | Offline при Pause и неопределённый ответ. UI не заявляет сохранение; повтор того же commandId после сети разрешает неопределённость без двойной записи.
A17 | R01 R10 | Прервать загрузку на второй странице, получить rate limit. Показаны частичные данные, checkpoint и безопасное ожидание; ложного «актуально» нет.
A18 | R01 R10 | Отозвать доступ GitHub и повторить sync. Новых чтений нет, private-кэш обрабатывается по согласованной политике; планы и время сохранены.
A19 | R08 R10 | Подменить ownerId, запросить чужой planId и передать вредный текст коммита. Нет чтения или записи чужих данных, выполнения скрипта либо инструкции из текста.
A20 | R09 | Пройти основной цикл клавиатурой на 360/768/1440 px. Видны фокус и сообщения состояния; нет перекрытий, обрезанных кнопок и прокрутки всей страницы.
A21 | R07 | Пустая выборка и неполные данные не показывают выдуманные нули. Медиана сообщает N и не включает планы без измеренного времени.
A22 | R08 | Два независимых клиента skill проходят Create/Start/Pause/Resume/Finish и конфликтные сценарии, используя подтверждённый runtime-доступ к Sites.
A23 | R10 | Проверены секреты в собранном frontend и журналах, восстановление после сбоя и переносимая выгрузка планов с интервалами.
A24 | R01–R10 | На согласованном тестовом объёме зафиксированы времена команд и обзора. Ни импорт GitHub, ни ошибки sync не блокируют команды таймера.

Условия начала реализации
1. Зафиксировать результаты G1–G6 и выбрать поддерживаемые механизмы Sites. 2. Подтвердить допущения из раздела 14. 3. Утвердить схемы данных и команд, включая проверки на уровне хранилища. 4. Описать негативные тесты до работы над интерфейсом. После этого оценивать этапы и зависимости; даты и трудозатраты заранее не выдумывать.

Рекомендуемый порядок будущего плана
Сначала доказать приватность и командный доступ, затем собрать вертикальный путь Create → Start → Pause → Resume → Finish с тестами гонок и повторов. Следом добавить GitHub, проверяемую атрибуцию и аналитику. После этого провести визуальную доработку трёх экранов, контрактные тесты skill и сквозную приёмку опубликованной версии.
MVP готов только при прохождении A01–A24 или явно согласованном изменении объёма. «Красивый интерфейс с localStorage» и «работает только в одном чате» не удовлетворяют требованиям постоянного приложения с внешними агентами.


14 Решения перед реализацией и источники


Что требуется подтвердить
Вопрос | Предлагаемое значение для MVP
Кто пользуется приложением | Один владелец, приватный доступ. Командные роли отложены.
Что означает завершить план | Результат соответствует записанным критериям готовности; merge/deploy только если они входят в эти критерии.
Что включать в active elapsed | Выполнение по плану и необходимые тесты/сборка; пауза при внешнем ожидании и переходе к другой задаче.
Репозитории и refs | Один или несколько на план; default branch как начальное значение, другая ветка выбирается явно.
Исправления прошлых интервалов | После MVP. На первом этапе предупреждение о длинной сессии без автоматического вычитания времени.
Приватный кэш после отзыва | Скрыть до повторной авторизации, дать явное удаление; интервалы сохранить.
Реальные объёмы и сроки хранения | Профиль из раздела 11 проверить на платформе; постоянные лимиты и retention согласовать до публикации.
