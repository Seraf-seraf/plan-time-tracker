# Перенос изменяющих данные SQLite-триггеров в приложение

## Контекст и описание задачи

Справочная часть. В plan-time-tracker 24 действующих триггера создают, обновляют или удаляют данные: команды планов, интервалы этапов, снимок первого запуска, очередь и состояние ATLM, очистка checkpoint. Пользователь поручил перенести это поведение в код с транзакциями, событиями, наблюдателями и классами с единственной ответственностью, составить план, реализовать, проверить и отправить изменения в Git.

Наблюдаемый результат: API и MCP сохраняют команды, ошибки, версии, идемпотентность, изоляцию владельцев, измерения времени и прогнозы. Все обязательные записи команды выполняются одной транзакцией приложения. После последней миграции ни один SQL-триггер не изменяет данные.

## Решения, границы и правила исполнения

- Сохраняем существующие Worker, D1 и remote-sqlite, без новых runtime-зависимостей. SqlTransaction собирает prepared statements и один раз вызывает атомарный db.batch. Callback-транзакция с сетевыми чтениями между BEGIN и COMMIT не вводится: текущие адаптеры её не поддерживают.
- TransactionalEvents использует явную таблицу типов событий и порядка наблюдателей. Наблюдатели синхронно добавляют записи в ту же транзакцию; внешние действия из них не выполняются. Обучение продолжает работать через уже имеющуюся устойчивую очередь.
- Контракт транзакции: constructor(db), add(sql,...args), addPrepared(statement), commit(). Обработчик события получает transaction и event с type, ownerId, planId, commandId, nowMs, actorId, values, guard:{sql,args}; stepId добавляется для этапа. guard проверяет свежую квитанцию именно данного выполнения.
- События перед изменением основных строк: plan.starting, plan.pausing, plan.resuming, plan.finishing, plan.deleting, plan.restoring, plan.metadata-changing, step.status-changing. Порядок наблюдателей зафиксирован в composition root, условия проверяются внутри batch по текущим строкам.
- Решение команды и optimistic concurrency проверяются внутри транзакции. Предварительные чтения для разбора Markdown или расчёта прогноза не заменяют атомарную проверку версии, assessment, модели и исходных данных.
- command_receipts получает nullable execution_nonce. Новый код передаёт уникальный nonce во все командные записи; чистый RAISE-guard отвергает записи старого writer без nonce. Повтор commandId возвращает прежнюю квитанцию, без повторных побочных эффектов. Недействительные команды сохраняют прежние коды отказа.
- SQL сохраняет CHECK, FK, уникальные индексы и триггеры, которые только отклоняют недопустимую запись. Исторические миграции не переписываются. Новая 0029_application_transactions.sql удаляет все 24 изменяющих триггера, без сброса планов, оценок, моделей, samples и истории обучения.
- Одна успешная команда, реально меняющая источник ATLM, ставит один refresh. Внутренние поколения отражают логические изменения; точное число прежних промежуточных срабатываний триггеров не является публичным контрактом. Изменение без разницы в исходных полях не инвалидирует модель.
- Совместимость ATLM writers: claim/release использует executor_epoch +3; миграция обновляет чистые RAISE-проверки, запрещает новое owner state со schema_version не 4 и отзывает право прежнего исполнителя на запись (fence +1, executor_epoch +3). RUNNING и срок lease сохраняются для штатного восстановления: после истечения lease оно закроет незавершённую попытку и назначит повтор либо зафиксирует исчерпание попыток. История, snapshot и checkpoint остаются; прежний worker с удержанным fence не может записать sample или активировать модель. Это единственное намеренное изменение существующих job-строк при миграции.
- AtlmOwnerRepository задаёт schema_version=4 явно; новые jobs получают начальный fence из data_reset_at. Счётчики образцов и удаление устаревших частей checkpoint фиксируются вместе с соответствующей записью.
- Прямая административная запись SQL после миграции намеренно не вызывает прикладных побочных эффектов. Поддерживаемые сценарии вызывают application service и события.
- Переключение БД и Worker согласованное: остановить writers и фоновые workers, сохранить резервную копию, применить миграцию и соответствующий Worker, проверить и возобновить запись. Откат только Worker несовместим с удалёнными триггерами. В этой задаче выполняются локальная миграция и push; production deploy не поручен.
- Пользователь поручил выполнить все этапы и push. Повторное разрешение между ними не требуется. Локальные реализационные детали можно уточнять без изменения публичного контракта; существенное изменение требований требует пересмотра плана.
- Один владелец индекса и коммита — основной исполнитель. Параллельная работа разрешена только в указанных непересекающихся файлах. Сохранять чужие изменения. В Git добавлять точные пути, не использовать git add . или git add -A.
- Код, совместимая миграция и регрессионные тесты публикуются одним согласованным коммитом: промежуточную несовместимую комбинацию схемы и Worker не публиковать.
- Для продолжения читать .codex-task-state.md и фактический git status; готовое не повторять. STOP относится к назначенному объёму; здесь назначены все три этапа.

- MODIFY существующие затронутые test/*.test.js и test/fixtures/tracker-db.mjs только для перехода с неявных SQL-срабатываний на явные application operations; исторический смысл старых migration tests сохраняется.

- USE worker/shared/index.js; MODIFY только если нужен известный код несовместимого writer.
- MODIFY docs/atlm.md, docs/plan-documents.md, sites/plan-time-tracker/README.md; CREATE docs/application-transactions.md — владельцы поведения и порядок переключения.

**Действия:**
1. Перенести Create/Start/Pause/Resume/Finish/Delete/Restore/UpdatePlan, SetStepStatus и RecordAssessment в явно выбранные обработчики. Сохранить приоритет ошибок и возвращаемые данные.
2. WorkIntervalObserver и StepIntervalObserver отвечают за интервалы; RequirementsObserver — за материализацию требований. Ни один наблюдатель не фиксирует собственную транзакцию.
3. AtlmPlanObserver фиксирует стартовый snapshot и ставит refresh/инвалидирует использованную модель только по успешному изменению источника. Зафиксировать предикаты источника до изменения основной строки внутри batch.
4. В sample persistence записывать sample и owner counters одной транзакцией; stale generation/fence ничего не меняет. Инициализировать schema/fence явно. Завершение или смена поколения training удаляет старые checkpoint parts в том же batch.
5. Добавить execution_nonce и защиту от старого командного writer; удалить все изменяющие триггеры. Проверить новый schema и upgrade заполненной 0028 без потери данных.
6. Обновить документацию фактического контракта, включая direct SQL и совместимость развёртывания.

**Минимальные примеры приёмки:**
- PLANNED + актуальная оценка + StartPlan → RUNNING, один открытый интервал, один неизменяемый snapshot и refresh; ошибка snapshot/очереди → всё откатилось.
- Повтор успешного commandId → прежний результат, без новых интервалов, samples и поколений.
- Две команды с одинаковой expectedVersion → одна применяется; вторая получает прежний код конфликта, её observers ничего не пишут.
- RUNNING step + повтор RUNNING → версия меняется, второй интервал не создаётся; DONE закрывает первый.
- DeletePlan закрывает только его интервалы, RUNNING steps становятся BLOCKED; Restore не запускает время.
- Finish с незавершёнными steps отвергается; allowIncomplete с причиной сохраняет исключение и завершает атомарно.
- Запись нового sample → dataset_revision +1, first-eligible count только для нового eligible plan; повтор/stale worker счётчики не меняет.
- Миграция заполненной базы → история по значениям сохранена, только действующие leases отозваны; triggers без INSERT/UPDATE/DELETE в телах; старый writer отвергнут.

**Проверки:** из sites/plan-time-tracker: node --test test/simple-model.test.js test/analytics-steps.test.js test/assessments.test.js test/plan-document.test.js test/atlm-storage.test.js test/atlm-start-gate.test.js test/atlm-training.test.js test/atlm-training-history.test.js test/application-migration.test.js test/application-commands.test.js test/remote-transactions.test.js. Добавить управляемые гонки, fault injection и реальный Python SQLite transport в изолированном временном каталоге. Проверить rollback всех связанных таблиц.

**Индекс Git:** перечисленные CREATE/MODIFY пути; каждый действительно изменённый test-файл добавлять отдельно после git diff. Общие tracker/index.js и документацию сводит основной исполнитель; чужие фрагменты не включать. Точные git add команды выводятся из фактического diff без wildcard.

**Фиксация:** один согласованный коммит вместе с TX-001 в QA-003 после успешной приёмки.

**Конец:** команды и обучение работают на новой схеме; нет data-writing triggers; узкие проверки пройдены, ограничения среды записаны.
